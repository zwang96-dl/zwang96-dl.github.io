SARA：解耦推理服务的 SLO 感知资源分配

原文：SARA: SLO-Aware Resource Allocation for Disaggregated Agentic LLM Services（arXiv:2609.26763，2026-09-22）
一句话版本：这篇把 P/D 解耦的配卡问题变成了数学题，算出来的配比又准又快。

人话解读

这事说白了，只回答一个问题。 prefill 和 decode 分开部署后，每边到底该放几张卡。

答案不是瞎试出来的，而是一套排队论公式算出来的。

对你意味着什么：你正在 SGLang 上做 P/D 解耦评估。

以后配卡不用靠枚举跑 benchmark 了。

先拿它的公式算个基准数，再实测微调，省下一大把试错时间。

更关键的是，它的结论是解析推导出来的，不是某次实测拟合的。

换句话说，这条结论换到 MI350 上同样成立。 prefill 吃算力，decode 吃显存带宽。

核心方法

  • 三个阶段用三套排队模型。prefill 是 M/G/k 队列（k 个工位并行干活）。KV 缓存传输是 M/G/1 队列（一条传送带）。decode 是广义生灭过程（请求来去的动态账本）。
  • 尾延迟有闭式解。轻尾重尾两种负载下，TTFT、KV 延迟、TPOT 的分位数都能写成公式。不用跑仿真。
  • 预算先切三段：总延迟预算按边际收益分给 prefill、KV 传输、decode。哪段多给 1 毫秒最划算，就分给哪段。
  • 配卡直接算：从公式反推出每段最少要多少卡。再用二分搜索把 goodput 推到最大。
  • 核心洞察：prefill 的瓶颈是算力，decode 的瓶颈是 HBM 带宽。两边的卡数都随序列长度平方增长。

关键数据

  • SLO 预测很准：阶段延迟分位数的平均相对误差小于 5%。
  • goodput 提升明显：同等部署成本下，比最好的基线平均高 26.6%。
  • 配比算得飞快。SARA 跑完配比最多 1.60 秒。穷举搜索要 1440 秒以上，差了几个数量级。
  • 离最优很近：跟穷举找到的最优配比比，goodput 差距最大只有 3.8%。
  • 基线高峰期掉链子。真实 trace 高峰时段，Splitwise 差 21.5%。混部差 45.6%，经验配比差 57.2%。
  • 卡数按平方增长。prefill 卡数随输入长度平方涨。decode 卡数随输出长度平方涨。
  • SLO 税很贵。严 SLO 下的额外资源能达到稳定性条件的 2 倍。光"能跑"不够，"跑得达标"要翻倍。
  • 实验配置：跑在 SGLang + A100 上。卡费 5 美元/小时，带宽费 0.1 美元/GiB/小时。SLO 达标率目标 95%。

跟你研究方向的关联

你的 SGLang P/D 解耦评估可以直接用这篇当配卡依据。

它的公式输入是工作负载统计、模型结构、硬件参数，输出就是每段要多少卡。

这意味着评估前先算一遍，心里有数再跑实测，不用从零枚举。

它还给出了"平方增长律"：长上下文场景下，卡数需求是按长度平方涨的。

做 MI350 评估时，这条可以当作 scaling 预测的先验。

跟 9/21 的"PD 解耦功率账"笔记对照看。 那篇算的是功率账单，这篇算的是延迟账单。

两篇都是解析配比，一个管电费，一个管 SLO，拼起来就是完整的部署规划。

术语表

  • SLO（服务等级目标）：跟用户签的延迟军令状。比如"95% 的请求首 token 在 0.5 秒内"。
  • goodput（有效吞吐）：衡量"有用"的吞吐。只有满足 SLO 的请求才算数，超时的不算。
  • M/G/k 队列：排队论模型。请求随机到达，服务时间任意分布，k 个工位并行服务。
  • M/G/1 队列：上面 k=1 的版本，一条传送带一次只运一份 KV 缓存。
  • 广义生灭过程：像人口的出生死亡账本。描述 decode 阶段请求不断加入、完成。
  • 尾延迟：最慢的那批请求的延迟，通常看 p95、p99，决定用户体验下限。
  • 轻尾/重尾负载：请求长度分布拖不拖尾巴。重尾就是偶尔冒出一个巨长请求，最难伺候。
  • TTFT：从请求到达，到第一个 token 出来的时间。
  • TPOT：每个输出 token 的平均耗时，决定"吐字"流畅度。
  • 穷举搜索：把所有配比组合都试一遍找最优，准但是慢到没法用。
  • SLO 税：为了达标 SLO 而多付的资源，超过"系统能跑起来"的最低需求。
