py-kvcache：外接 KV 缓存到底值不值？一篇论文讲透了

原文：Building py-kvcache: A Performance Characterization of External KV Caching for vLLM with NVMe SSDs
作者：Joseph Kanichai、Tiziano De Matteis、Animesh Trivedi
链接：https://arxiv.org/abs/2609.11744（arXiv:2609.11744，2026-09-11 发布）
代码：https://github.com/atlarge-research/py-kvcache

一句话人话版

prefix caching（前缀缓存，复用历史 KV）听起来永远赚。

但事实不是这样。

前缀太短、或者卡太快时，重算比从硬盘读缓存还快。

这篇论文把"什么时候该读、什么时候该算"测得明明白白。

顺手造了个 py-kvcache。

80k token 从盘里读，比 LMCache 快 2 倍。

核心论点

  • KV cache（键值缓存，注意力历史的草稿纸）放 GPU 里最快。
  • 放 CPU、NVMe SSD 是"外接缓存"，容量大但读起来慢。
  • 外接缓存不是命中就有赚：读缓存的 IO 时间，可能比 GPU 重算还长。
  • 所以要有一个 break-even point（盈亏平衡点，读和算打平处）。
  • 短于这个点：别读，老老实实重算，反而更快。
  • 论文还发现：瓶颈不只看硬盘带宽，还看传输粒度、中间内存、请求何时进调度。
  • 这个结论适用于任何外接 KV 缓存设计，不只 vLLM。

核心方法：先测，再做

论文不是上来就造轮子，而是先做系统剖析。

第一步：测 break-even 边界（图 6）

  • 固定模型 Llama 3.2 3B，文档从 1k 扫到 80k token。
  • 纵轴是前缀命中比例，横轴是文档长度。
  • 画出三条"边界线"：GPU 缓存、llm-d、vLLM Offload（CPU）。
  • 线上面：读缓存赢；线下面：重算赢。
  • 短文档时边界线很高：大部分情况重算更快。
  • 这就是"外接缓存该不该用"的决策表。

第二步：换算成"硬盘要多快才够"（图 7 的思路）

  • Llama 3.2 3B 每个 token 存 114,688 字节的 KV。
  • 算出"读缓存刚好打平重算"需要的硬盘带宽。

1k token 需要 23.2 GB/s。

8k 降到 10.4 GB/s，80k 只需 3.5 GB/s。

  • 文档越长，prefill（预填充，一次性算完输入）代价涨得越快。
  • 所以长文档里，普通 SSD 也能赢；短文档里，再快的盘也白搭。
  • GPU↔CPU 拷贝 54–56 GB/s，全尺寸都达标，永远赢。

第三步：找出 LMCache/llm-d 慢在哪

  • 拿自研的 simple-profiler 打 trace（图 3），看每段耗时。
  • llm-d 的问题：每个缓存 chunk 单独拷贝、单独提交 IO。
  • 零散小 IO 把 NVMe 的并行能力全浪费了。
  • 这个发现直接决定了 py-kvcache 的设计。

核心方法：py-kvcache 怎么造的（图 9）

调度侧（scheduler side，管决策不管搬运）

  • Manager 做缓存查找，制定 load/store/preload 计划。
  • 它可以"拒绝"一次加载：命中了也未必读。
  • 拒绝的依据就是 break-even 表：预测读比算贵就直接重算。
  • 它不搬 KV 数据，只发紧凑的传输计划。
  • 决策和搬运分离，控制路径不被数据路径拖慢。

工作侧（worker side，管搬运不管决策）

Handler 收到计划。

再调 transfer_async / preload_async 干活。

  • TransferCoordinator 把操作拆成 file job。
  • 单线程 IoReactor 统一调度。
  • io_uring ring（Linux 异步 IO 接口）打底。

再加上有界 CPU staging pool（中转内存池，暂存数据）。

  • 文件用 direct I/O（直连 IO，绕过系统页缓存），读写不看操作系统脸色。
  • vLLM 的批量 block-copy 把数据从 staging 搬进 GPU。

两个杀手锏

scheduler-aware preloading（预加载，排队时先读盘）。

请求还在排队，盘已经开始读，IO 和计算重叠。

  • break-even gate：低于盈亏点直接拒载，外部缓存永远不变成负优化。

共享文件布局

  • 沿用 llm-d 的层级哈希寻址：缓存路径由模型配置 + 前缀块哈希决定。
  • 写时先写临时文件，完成后再 hard link 原子发布。
  • 并发写同一哈希：先到者赢，读者永远看到"完整或没有"，不会读到一半。

关键数据

图 10a：只从盘读（Snellius 节点，H100）

  • py-kvcache 不开预加载：比 LMCache 磁盘后端快约 1.5×。
  • 这是纯异步传输引擎的功劳。
  • 打开预加载：总加速到 2.0–2.5×（80k token 处约 2.0×）。
  • 预加载单独贡献 1.34×。

图 10b：三层全开（GPU + CPU + 盘）

10k / 40k / 80k token 处。

比 LMCache 快 1.19× / 1.53× / 1.23×。 跟 vLLM 原生 KV Offload 比。

40k 处差 1.10×，80k 处差 1.04×。

  • 10k 处反而比原生快 1.12×。
  • 1k token 处四家全挤在 0.12 秒内，顺序还反转了。
  • 1k 就是在 break-even 点之下，读缓存纯属折腾。

真实负载：LongBench、SCBench、多轮对话

  • 不规则前缀链、多轮场景下，加速依然成立。
  • SCBench 里 CPU 池占用和盘吞吐被 trace 验证过。

Bailian 生产 trace 回放：最有意思的结论

弱卡（RTX 4000 Ada 本地节点）。

外接缓存明显改善 TTFT（首 token 延迟）。

  • H100 上：平均请求落在 break-even 点之下，GPU 显存自己就够了。
  • 外接 KV 缓存该不该开，是"按配置准入"的决策，不是默认开关。

跟你的研究方向的关联

prefix caching（前缀缓存）

  • 你一直在跟的 prefix caching，这篇给了它一个"使用说明书"。
  • 命中 ≠ 有赚：短前缀直接重算，长前缀才值得读盘。
  • 以后做缓存策略，break-even 表应该做成离线标定 + 在线查表。

多模态推理优化

多模态的 prompt 本来就长（图 token 堆得多）。

天然落在"读缓存赢"的区间。 但视觉 encoder 的 KV 和文本 KV 混在一起。

break-even 点会跟着变。

  • 论文的剖析方法论可以直接搬过去测多模态模型。

PD disaggregation（预填充与解码分离部署）

P 节点算完 prefill 要把 KV 甩给 D 节点。

本质也是"KV 搬运 vs 重算"的权衡。 py-kvcache 的调度侧/工作侧分离。

跟 P/D 的控制面/数据面分离异曲同工。

  • 预加载思路（排队时先搬）可以直接用在 P→D 的 KV 传输上。

跟你之前看过的内容的呼应

  • KVTC（20 倍压缩 KV）是把缓存"变小"，这篇是把缓存"读快"。
  • 两个叠加：小 + 快，外接缓存才真正划算。
  • CXL 那篇是"跨节点共享缓存"，这篇是"单节点读缓存要不要"。
  • 先回答"要不要"，再谈"怎么共享"，顺序是对的。

关键图表

术语表

  • prefix caching：前缀缓存，复用历史上下文的 KV，省掉重复计算。
  • KV cache：键值缓存，attention 算过的历史，推理时的草稿纸。
  • TTFT：首 token 延迟，从发请求到吐出第一个字的时间。
  • break-even point：盈亏平衡点，读缓存和重算打平的前缀长度。
  • prefill：预填充，一次性算完输入 prompt 的阶段。
  • io_uring：Linux 的异步 IO 接口，一次提交一堆读写不阻塞。
  • direct I/O：直连 IO，绕过操作系统页缓存直接读写盘。
  • preloading：预加载，请求还在排队时就提前从盘读缓存。
  • staging pool：中转内存池，GPU 和磁盘之间暂存数据的 CPU 内存。
  • LMCache：开源的 KV 缓存分发框架，支持跨实例共享。
  • llm-d：Kubernetes 原生的分布式推理项目，带文件系统缓存层。

vLLM KV Offload：vLLM 原生的 KV 外存接口。 （v0.11.0 引入） PD disaggregation：预填充与解码分离。 P 节点算 prompt、D 节点接着生成。

  • hard link：硬链接，同一份文件多个名字，原子发布用它防读到一半。
  • first-writer-wins：先写者赢，并发写同一缓存时只保留第一个。
  • Snellius：荷兰国家超算，论文实验用的 H100 节点。
  • hash-addressed：哈希寻址，缓存文件名由内容哈希决定，天然去重。

一句话总结

外接 KV 缓存不是"有就开"，而是"算过再开"。

短前缀、快卡上，重算就是最优解。

长上下文、弱卡上，py-kvcache 能榨出 2 倍。

靠的就是异步 + 预加载 + 盈亏门这三招。

这篇最值钱的不是代码，是那张 break-even 决策表的方法论。
