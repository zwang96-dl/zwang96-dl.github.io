vLLM #67903：Kimi-K3 的 RecoverSSM 图上限拆了，词间隔降三成

  • 作者：vLLM 团队
  • 文章：[Bugfix][Kimi-K3] Capture all mixed CUDA graphs with RecoverSSM
  • 合入时间：2026-11-17 06:12 PST（2026-11-17 14:12 UTC）
  • 原文链接：https://github.com/vllm-project/vllm/pull/67903
  • 说明：原文是代码 PR，没有配图，本笔记不附图。数字全是 PR 作者自报，没有第三方复现。

一句话

Kimi-K3 开投机解码加 RecoverSSM 时，一道老上限在悄悄扔图。一共扔掉了 24 张。拆掉上限，词间隔从 53.3 毫秒降到 36.2 毫秒。

人话解读

CUDA 图就是把一串操作预先排好。排好的图不用每次现算，直接重放。重放比现算快得多。

混合图是解码步里的一种图。它把一次解码的多个 token 打包进一张图。token 数越大，图越大。

RecoverSSM 是一种恢复式投机解码。投机解码就是小模型先猜，大模型再验。猜错了要回滚重算。RecoverSSM 管的就是这套回滚恢复。

这篇的毛病藏在一道 guard 里。guard 就是一道保险检查，来自 #55774。它只在 RecoverSSM 开着时生效。

这道 guard 规定，混合图的大小不能超过一个上限。上限是最大序列数乘以 1 加投机 token 数。超过上限的图，直接不抓。

不抓的后果是，那些步数只能现算。现算就是 eager 模式，一步一步跑。低延迟那档最吃亏，词间隔直接被拖慢。

具体到这次的配置。最大序列数 128，投机 token 数 4。上限就是 128 乘 5，等于 640。641 到 1024 个 token 的 24 张图，全被扔了。

修法很简单，就是把这道 guard 拆掉。83 张图全抓住了，以前只抓住 59 张。

拆掉是安全的，理由有三条。

第一，RecoverSSM 的验证容量是按请求算的。每个请求只要 num_spec 加 1 个 token。不是按整步算的。

第二，KDA 的元数据构造器会分流。行宽超过 num_spec 加 1 的，走非投机路径。根本到不了 RecoverSSM 的验证口。

第三，KDA 的前向在重放时是 eager 断点。图里不存 RecoverSSM 的形状。

代价是每张卡多占 0.57GB 图池。图池就是存排好的图的显存。

还有个遗留口子。#67590、#58863、#61309 给 GDN 也加了开关。开关管的是 RecoverSSM。如果 GDN 的元数据构造器不分流宽行，GDN 那边还得留着上限。

核心方法

改动只有一处，拆掉 guard。

guard 在混合 PIECEWISE 图的捕获逻辑里。它按 RecoverSSM 单独设上限。

上限等于 max_num_seqs 乘以 1 加投机 token 数。

拆掉之后，混合图按配置的全部尺寸捕获。不再区分 RecoverSSM 开没开。

安全性的三条理由，上面已经讲了。核心是宽行走非投机路径，验证容量按请求算。

测试补了一个单测。跑在 CPU 上，不用 GPU。

单测名字是下面这一串。

test_recoverssm_keeps_mixed_graphs_past_the_decode_token_cap

修之前，这个单测是失败的。混合尺寸 [1, 2, 4] 里，4 通不过 2 乘 3 的上限。修之后，通过了。

关键数据

  • 测试模型：Kimi K3.1 Pro。
  • 测试硬件：GB300。
  • 部署形态：张量并行 8 卡，加 DCP 8 卡。
  • 草稿器：DSpark，k 等于 4。
  • 开关：--use-replayssm。
  • 最大序列数：128。
  • 负载：ShareGPT，每秒 8 个请求。
  • 图捕获：59 张变 83 张。
  • 补回来的图：641 到 1024 个 token 的 24 张。
  • 词间隔：53.3 毫秒降到 36.2 毫秒。
  • 降幅约 32%。
  • 图池代价：每张卡多占 0.57GB。

还有一组对照数，来自变通方案。

变通方案是把最大序列数抬到 208。图就全落在上限里了。

那组词间隔是 31.4 毫秒。首字时间从 2989 毫秒降到 318 毫秒。吞吐从 1378 词每秒涨到 1523 词每秒。

注意，这组是变通方案的数。不是本次修复的数。修复那组只报了词间隔 36.18 毫秒。

跟研究方向的关联

这篇跟 PD 解耦评估直接相关。

第一，Kimi-K3 是评估里的重点模型。投机解码加 RecoverSSM 是它的标准开法。图抓不全，词间隔直接虚高三成。跑 Kimi-K3 的 PD 对照前，先确认版本带这个修复。

第二，词间隔 53.3 到 36.2 毫秒的数能当基线。配置都给了。GB300、TP8 加 DCP8、DSpark k 等于 4。每秒 8 个请求。自己测同一档时，可以先对一下这组数。

第三，修法本身是个提醒。guard 是 #55774 留下的，初衷是保险。保险检查也会误伤。评估里遇到不明原因的词间隔偏高，先查图捕获全不全。

第四，图池代价要进账。每张卡多占 0.57GB。显存紧张的部署，先算好这笔账再开。

第五，GDN 那边还有口子。GDN 的 RecoverSSM 开关如果不分流宽行，上限还得留着。评估 GDN 模型时，单独确认一次。

术语表

  • PD 解耦：读题和生成分到不同机器上跑。
  • 投机解码：小模型先猜，大模型再验。
  • RecoverSSM：恢复式投机解码，管猜错后的回滚恢复。
  • CUDA 图：预先排好的一串操作，重放比现算快。
  • 混合图：一次解码多个 token 打包成的图。
  • PIECEWISE：分段图的一种捕获模式。
  • guard：一道保险检查，条件不满足就跳过。
  • eager：现算模式，一步一步跑，不用预排好的图。
  • TPOT：词间隔，平均每个词要等多久。
  • TTFT：首字时间，第一个词吐出来要等多久。
  • DSpark：投机解码用的草稿器。
  • DCP：解码上下文并行，多卡分上下文算解码。
  • KDA：Kimi Delta Attention，一种线性注意力。
  • GDN：Kimi-K3 里的另一类注意力层。
  • ShareGPT：公开对话数据集，常用来压测 serving。
  • QPS：每秒请求数。
  • 图池：存排好的 CUDA 图的显存。
  • max_num_seqs：最大序列数，一批最多跑多少请求。
