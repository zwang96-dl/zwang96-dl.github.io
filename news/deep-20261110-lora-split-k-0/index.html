LoRA 推理的可复现性：Split-K 原子加法让温度 0 也飘

  • 原文：Dhayaneshwar Balusamy、Ankur Mohan（摩根大通），arXiv:2611.10334，2026-11-07 提交，共 12 页
  • 原文链接：https://arxiv.org/abs/2611.10334
  • 深读来源：21点版简报，11 月 9 日那批新论文

一句话

温度设 0，同一输入，LoRA 模型重复跑。

结果还会变，有时连对错都翻了。

元凶是 Split-K 切分后的原子加法。

人话解读

LoRA 是给大模型外挂小适配器。

推理时要多算一步 shrink。

shrink 就是把低秩小矩阵乘回原维度。

vLLM 默认把这步切成 8 份并行算。

切 8 份叫 Split-K=8。

8 个线程块各算一份，再拼起来。

拼用的是原子加法：谁先到谁先加。

浮点加法不满足结合律。

顺序一变，结果就差几位。

差的那几位平时没事。

但卡在 BF16 舍入边界上，就会翻过去。

翻过去一个词就变了，后面全变。

作者在 vLLM 0.29.0 上实测了这条链。

从一次加法，一直追到最终答案变了。

核心方法

  • 模型是三款：Llama-3.2-3B、Gemma-3-4B。
  • 还有 Nemotron-3-Nano-30B。
  • LoRA rank 是 16 和 32。
  • 权重和适配器都是 BF16。
  • 卡是 RTX PRO 6000 和 H100。
  • 前缀缓存、异步调度、投机解码全关。
  • 每次只跑一个请求，排除 batch 干扰。
  • VLLM_BATCH_INVARIANT 也关了，只看 shrink。
  • 对比三种实现：Atomic SK8、SK1、Deterministic SK8。
  • Atomic SK8 是 vLLM 默认：8 份加原子加法。
  • SK1 是不切分：一个线程块算完整行。
  • Deterministic SK8 是作者自研的 Triton 核。
  • 它用 FP32 暂存 8 份中间结果。
  • 再用完成计数器加固定顺序求和。
  • 最后完成的那个线程块负责合并。
  • 这样并行还在，顺序却钉死了。
  • 任务是 GSM8K 数学、MBPP 写代码。
  • 再加 Civil Comments 的毒性二分类。
  • 每个配置重复跑 10 次，互相比较。

关键数据

shrink 这一步本身，先看有多飘。

Atomic SK8 在 97.61% 的比较里输出不同。

Deterministic SK8 是 0，一次都没变。

SK1 也是 0，但它不切分、没并行。

端到端生成，飘会传到答案上。

GSM8K 上，17.30% 的比较输出变了。

一共 467 次，里面 84 次对错翻转。

MBPP 上，14.96% 的比较输出变了。

一共 404 次，里面 53 次对错翻转。

六组模型加 rank 配置，全都中招。

结构化决策也一样飘。

Civil Comments 上，概率在 81.47% 的比较里变了。

一共 7332 次，平均漂 0.00143。

最大一次漂了 0.05672。

7 次决策翻转，都在初始概率正好 0.5 的评论上。

翻过去后概率约 0.46879，分类跟着变了。

作者一路追踪，画出了传播链。

第一个数值差，出现在读题第 47 个位置。

差只有 1.08×10^-8，小到看不见。

到生成第 36 个词时，KV 缓存已经变了样。

108 个 key 元素、176 个 value 元素都不同。

因果干预那一下，最说明问题。

GSM8K 第 813 题，只改一个坐标。

FP32 差 1.19×10^-7，跨过 BF16 舍入中点。

BF16 差放大到 1.95×10^-3。

第 36 个词从 7 变成 8，正确答案变错误答案。

换 batch 也会变，这点要单独记。

固定 batch 内可复现，不等于 batch 之间一致。

batch 1、16、32、64 之间跑同一批题。

Deterministic SK8 也有 39.06% 的输出不同。

SK1 是 39.58%，Atomic 是 43.75%。

batch 大小还会改动推理栈别处。

只修 shrink 这一个核，是不够的。

性能代价很小，基本白捡。

Deterministic SK8 比 SK1 快 16.8–21.1%。

平均快 19.2%，并行没白给。

比 Atomic 只慢 1.02–2.62%，平均 1.69%。

准确率没有系统性优势，别误会。

Civil Comments 三种实现分别是 94.25%、94.20%、94.30%。

好处是可复现，不是更准。

原文关键图表

图 1：Split-K 是怎么切的。左边 Split-K=1：8 个输出块，每块一个线程块，一共 8 个。右边 Split-K=8：每块再切 8 份，一共 64 个线程块。切得越多，并行越足。但右边的 8 份最后要拼起来，拼的顺序就是飘的来源。

图 2：确定性版是怎么拼的。8 个线程块各算一份 FP32 中间结果，先存进暂存区。完成计数器数到 8，最后完成的那个线程块负责合并。合并按 P0 到 P7 固定顺序加，不用原子加法。并行还在，顺序钉死了。

图 3：一个小数点怎么翻掉答案。左图是 FP32 到 BF16 的舍入边界。两个数只差 1.19×10^-7，刚好落在中点两侧。舍入后差放大到 1.95×10^-3。右图是第 36 个词的抉择：A 是 7，B 是 8。正确那个 7 的分数被压到 0 附近打平，8 就赢了。答案从对变错。

评估方法要改：固定 batch 跑多次，报波动。

只跑一次就报分，等于没测。

注意事项

  • 只测了 vLLM 0.29.0，三款模型。
  • LoRA rank 只测了 16 和 32。
  • MoE 和投机解码都没测。
  • batch 之间仍有差异，修一个核不够。
  • 数字全是作者自报，无第三方复现。
  • 代码链接论文里没给，未核实。

术语表

  • LoRA：给大模型外挂小适配器，只训一小部分参数。
  • shrink：LoRA 推理里把低秩结果乘回原维度的那步。
  • Split-K：把矩阵乘的 K 维切几份，并行算。
  • CTA：线程块，GPU 上一组一起跑的线程。
  • 原子加法：谁先到谁先加的累加方式，顺序不固定。
  • BF16：16 位浮点，省显存但精度比 FP32 粗。
  • 舍入边界：两个 BF16 数正中间的值，差一点就进另一档。
  • KV 缓存：模型读题时记的草稿纸，解码时接着用。
  • Jev-style：vLLM 里一种结构化决策接口，返回概率。
  • batch 不变性：同一请求换邻居，结果逐位不变。
