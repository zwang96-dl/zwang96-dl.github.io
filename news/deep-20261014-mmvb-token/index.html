mmVB：多图推理先分预算，每张图按需给 token

原文：Visual Tokens on Demand: Visual Budgeting for Scalable and Efficient Multi-Image Reasoning in Multimodal LLMs 作者：Aimon Rahman 等 提交：2026-10-13 链接：https://arxiv.org/abs/2610.18858

人话解读

  • 多图问题最烧钱的地方在看图。
  • 每多一张图，就多一大把视觉 token。
  • 视觉 token 就是图片切成的小块编号。
  • 老办法大多在编码之后才删 token。
  • 编码的钱已经花了，省不回来。
  • 这篇把关口提前到编码之前。
  • 先猜每张图最少要看多清。
  • 不重要的图直接降分辨率。
  • 重要的图才给全清待遇。
  • 说白了，先分预算，再干活。

图注：图 1 是原文的动机图。 上半部分列了老办法的六类毛病。 比如剪枝只管单图、要读注意力矩阵。 下半部分是 mmVB 的位置。 它在编码前就分好每张图的预算。

核心方法

  • 模块名字叫 mmVB。
  • 它是个即插即用的小模块。
  • 可训练参数只有 160 万。
  • 底座大模型完全冻结，不重训。
  • 第一步，先粗看所有图和问题。
  • 粗看用的是冻结的小编码器。
  • 第二步，跨图一起比较重要性。
  • 比较用一个两层小 Transformer。
  • Transformer 就是注意力网络。
  • 第三步，给每张图打一个等级。
  • 等级共五档，从 0 到 4。
  • 等级就是这张图的 token 预算。
  • 第四步，按等级缩放图片。
  • 只许降清，不许升清。
  • 最后才把图送进大模型。
  • 整个模块只多花约 2 毫秒。
  • 训练目标是序数分类损失。
  • 标签来自离线找的最低够用等级。

图注：图 2 是 mmVB 的结构图。 左边是多张图和文本问题进来。 中间的小网络负责跨图比较。 右边输出每张图的预算等级。 底座大模型在全程保持冻结。

关键数据

  • 视觉 token 平均砍掉约 9 倍。
  • 首 token 延迟平均快约 5 倍。
  • 首 token 就是第一个字的等待时间。
  • prefill 计算量平均少约 7 倍。
  • prefill 就是先读完输入的那一步。
  • 精度保住全清版本的 94.4%。
  • 这是八个多图基准的平均账。
  • 底座模型用的是 Qwen3.5-4B。
  • 解码方式是贪心，关了思考模式。
  • 以上数字都是作者自报。
  • 本期没有独立复核。

图注：表 1 是原文的主结果表。 它横比了精度、token 数和耗时。 还有 prefill 计算量这一栏。 mmVB 在多数基准上排前二。 它的调和均值也大多最高。 调和均值就是精度和省钱的综合分。

跟你研究方向的关联

  • 这篇动的是 encoder 侧的账。
  • 它和 P/D 解耦是上下游关系。
  • 解耦管 prefill 放哪台机器跑。
  • 它管 prefill 到底要读多少图。
  • 多图请求一多，差别会被放大。
  • 五档预算天生适合自动调参。
  • autotuner 可以把等级当旋钮。
  • 按 SLA 在线搜每类请求的档位。
  • 它还绕开了 FlashAttention 的坑。
  • FlashAttention 是省显存的注意力实现。
  • 它不用读注意力矩阵就能分预算。
  • 所以闭源 API 模型也能外挂它。

局限和要注意的

  • 实验只用了一个 4B 底座。
  • 更大的模型上还没验证。
  • 基准全是多图推理任务。
  • 单图和视频场景没覆盖。
  • 预算等级只有五档，粒度偏粗。
  • 训练标签要离线逐图找。
  • 换新模型可能要重找一遍。

术语表

  • 视觉 token：图片切成小块后的编号序列。
  • token 预算：一张图最多能花多少 token。
  • prefill：模型先读完输入的那一步。
  • TTFT：从提问到吐出第一个字的时间。
  • FLOPs：浮点运算次数，算量的单位。
  • 序数分类：等级有顺序的分类任务。
