新技术与论文

2. P/D 解耦之后，请求分给谁成了新瓶颈（9-14 论文·补报） P/D 解耦是大势所趋：两个阶段各用一组 GPU。 prefill 管理解输入，decode 管逐字往外吐。 但请求到底发给哪个实例，大家还在轮询瞎分。 这篇做了个"学出来的路由器"。 它看四个信号：prompt 长度、预测输出长度、缓存压力、SLO 等级。 算出每个实例的边际成本，把请求发给最便宜的。 关键数据：8 张 A40 卡跑 vLLM。 KV 缓存（草稿纸）用 NIXL 在两组卡之间传。 混合突发流量下，goodput（达标吞吐）0.864，轮询 0.835。 最狠的一句：校准值了 4.5 个点。 用真机 5 分钟测出来的硬件常数，尾延迟优势的四成全靠它。 仿真器算出来的常数差了 7 倍，直接用会翻车。 对你意味着什么：你评估 P/D 解耦时，路由策略可以直接抄这套。 「值得深读」：路由正是 P/D 评估缺的一环，笔记已出。 论文

3. 流水线并行被小看了：agent 任务里它比 P/D 解耦还快（9-16 论文·补报） agent 干活和聊天不一样：它要的不是首字快，而是一整单活儿早点干完。 这篇说：流水线并行（把模型切成几段接力跑）被低估了。 它在 prefill 和 decode 之间找到了更合适的平衡点。 关键数据：在 64 张 H800 上跑两个 360B+ MoE 模型。 任务完成时间（JCT）比 SGLang 快 1.45 倍。 比 vLLM 的流水线快 2.33 倍。 连当下最强的 P/D 解耦部署也快了 1.54 倍。 对你意味着什么：评估 P/D 解耦时，记得把流水线并行拉进来当对手。 论文

4. 百万 token 解码：让每个 query 自己决定看几层 key（9-15 论文·补报） agent 会话跑到一百万 token，KV 缓存只能塞主机内存。 每次解码都要扫一遍所有 key，流量扛不住了。 Fathom 让每个 query 自己决定：key 的每个通道读几位。 打个比方：先看个大概，重要的通道再细看，不重要的就糊弄过去。 关键数据：百万 token、Qwen3-8B，单步解码快 1.67 倍。 用的还是量化 serving 本来就存的 4-bit K，零额外开销。 对你意味着什么：KV 卸载到主机内存的长上下文方案，又多一个趁手工具。 论文

5. MAPS：decode 池老是忙闲不均，靠预测输出长度来治（9-14 论文·补报） P/D 解耦后，decode 池经常忙闲不均。 输出多长事先不知道，调度只能瞎猜。 MAPS 让设备端帮忙：先预估输出长度。 预估和云端 prefill 重叠跑，几乎不占时间。 再按不确定性校准出个上限，调度按上限排队，安全。 关键数据：平均端到端延迟降 42.6%，尾延迟最多降 84.8%。 对你意味着什么：P/D 解耦的调度器设计，这篇给了个能抄的模板。 论文
