主机缓存三选一：混合模型上推测解码差点被缓存坑死

  • 原文：PrimaLabs Engineering，Dipanjan Sengupta、Adarsh Verma
  • 文章：A comparison of host cache tiers for hybrid-model serving
  • 发布时间：2026-11-20
  • 原文链接：https://www.primalabs.ai/blog/host-cache-tiers-for-hybrid-models
  • 说明：数字全是作者自报，独立第三方实测；Qwen3.8-27B-FP8 在一张 RTX PRO 6000 上，Nemotron-3.5-Lightning-30B-A3B 在一张 B200 上

一句话

主机内存里那层缓存，选错方案会直接废掉推测解码。同一模型、同一草稿头，接受率能从 80% 跌到 0.04%。

人话解读

主机缓存就是把 KV 放到 CPU 内存里。KV 是算过的中间结果，留着下次复用。GPU 显存不够大时，多轮对话的前缀可以先存主机里。回来时不用重算，直接从主机搬回来。

这篇测了三套方案。第一套是 vLLM 配 LMCache。第二套是 SGLang 配 HiCache。第三套是 vLLM 自带的主机内存卸载。

三套方案各有各的脾气。LMCache 是独立的缓存服务器。8 个副本可以共用一个。SGLang 的 HiCache 是分层缓存。混合模型要两份池子。一份存注意力条目，一份存递推状态。vLLM 自带卸载最简单。每个引擎自己管自己的主机内存。不用另起服务器，也不跟别人共享。

最吓人的发现跟推测解码有关。推测解码就是小模型先打草稿，大模型再核对。Nemotron 自带多 token 预测头。不接主机缓存时，草稿接受率约 80%。LMCache 一接，接受率跌到 0.04%。718845 个草稿词里，只通过了 278 个。

作者一开始以为是回滚没做好。草稿被拒时，引擎要把状态倒回去。注意力条目倒回去了，递推状态没倒回去。两边一错位，草稿全废。

但他们试了两个补丁，都没用。接受率还是贴着零。更关键的是，接受率从一开始就是零。那时缓存还没提供过任何东西。所以问题不在复用旧缓存。出在连接器一接上，状态就乱了。

换 vLLM 自带卸载，接受率立刻回到 80%。解码只慢了约 5%。低复用语料上，GPU 缓存自己只服务了 5.6% 的提示词。主机那层又补回了 39.3%。两层加起来是 43%。

SGLang 那边是另一个教训：内存分错了池子。官方配方给递推状态留了 42GB。实际只用了 1% 左右。注意力那边只剩 9GB。4 个并发请求，首字要等 31.6 秒。把比例从 4.59 改到 1.87。注意力池子翻到约 59 万 token。首字掉到 1.47 秒。命中率几乎没变，还是约 95%。

图 1：Nemotron-3.5-Lightning 上 MTP 草稿接受率。不接主机缓存约 80%。接 LMCache 跌到 0.04%。换 vLLM 自带卸载回到约 80%。DSpark 配 LMCache 还有 72%。

核心方法

方法分四步。目标是三套方案同台比，流量和种子都锁死。

第一步：模型和硬件锁死。Qwen3.8-27B-FP8 跑在一张 RTX PRO 6000 上。SGLang 是 0.5.14，vLLM 是 0.26.0 到 0.27.1。Nemotron 那组跑在一张 B200 上。vLLM 是 0.30.0，后来升到 0.31.0。

第二步：流量用真实的 agent 轨迹。Qwen 的提示词平均约 7.8 万 token。理论前缀复用约 95%。负载工具是 AIPerf 和 guidellm。两边用同一批数据、同一个种子。

第三步：先把 vLLM 的步长预算拉平。LMCache 那组把每步预算提到 16384 个 token。默认的一块预算会挡住读题，测出来的就不是引擎本身。

第四步：每人解码速度统一口径。总解码除以同时在跑的请求数。AIPerf 自带的每人数字偏高，两边不能混着比。

还有一点值得注意：每格数字都只跑了一次。差几个百分点要当噪声看。单流解码那几组是短跑。网关那组只有 4 个请求。

图 2：Nemotron 配 vLLM 原生主机缓存。并发从 1 拉到 32。每卡解码从 391 涨到 1918 词每秒。每人速度从 593 掉到 82。命中率一直卡在 94% 以上。

跟研究方向的关联

这篇跟 P/D 解耦评估直接相关。

第一，主机缓存就是 PD 拆分里传 KV 的那一层。读题节点算完的 KV，要过主机内存或网络交到解码节点。选哪套方案，先看它跟推测解码合不合得来。

第二，推测解码的接受率，必须带着缓存方案一起测。不带缓存测出来的 80%，接上 LMCache 就变 0.04%。评估里草稿接受率要单列一档，注明缓存方案。

第三，SGLang 的内存比例是个现成旋钮。官方配方给递推状态留太多，读题节点首字直接翻 21 倍。PD 评估里读题节点的这个比例要先调，再报首字。

第四，HiCache 的修补跟 09 点版那条对得上。09 点版报了 SGLang #50469。HiCache 写回时不再堵调度器。这篇用的 0.5.14 还没那修复。两篇连起来看，HiCache 这条线还在快速修。

第五，粘性路由要进评估清单。原生卸载只帮回到同一台引擎的会话。网关随机分流，缓存就白建了。PD 拆分里会话亲和要单独测。

第六，DSpark 是个对照组。它自己管自己的缓存，不写主模型的 KV。所以 LMCache 坑不到它。PD 拆分下草稿 KV 搬不搬运，也要这样分开测。

术语表

  • 主机缓存：KV 放到 CPU 内存里的一层。GPU 显存不够时，回来不用重算。
  • 混合模型：注意力层加 Mamba 递推层的混搭。Qwen3.8 和 Nemotron 都是这种。
  • 递推状态：Mamba 层的状态。恢复前缀时，注意力和递推状态要一起对上。
  • LMCache：独立的 KV 缓存服务器。多个引擎副本可以共用一个。
  • HiCache：SGLang 的分层缓存。GPU、主机内存、磁盘三层。
  • 原生卸载：vLLM 自带的主机内存卸载。每个引擎自己管，不用另起服务器。
  • MTP：多 token 预测。一次猜好几个词，不是逐个猜。
  • EAGLE：一种推测解码算法。SGLang 用它跑 MTP 草稿。
  • DSpark：一种草稿模型。自己管缓存，不碰主模型的 KV。
  • 接受率：草稿词里被大模型通过的比例。越高越省时间。
  • 首字时间：从发请求到第一个词出来，要等多久。
  • 命中率：提示词里从缓存找回来的比例。越高重算越少。
  • 粘性路由：同一个会话的请求，每次都分到同一台引擎。
  • 步长预算：vLLM 每步最多处理多少 token。太小会挡住读题。
