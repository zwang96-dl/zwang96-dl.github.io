DRelay：并行投机解码的"事后纠错"——整块草稿当证据，修早错

  • 原文：https://arxiv.org/abs/2610.01439
  • 作者：Zhuoyu Wang、Junnan Huang、Xinyu Chen（HKUST 广州）
  • 发布：2026-10-01（arXiv 2610.01439）

一句话人话

并行投机解码有个死结：一次前向打出整块草稿。 但验证只能收"从头开始的连续正确前缀"。 第 2 个 token 错了，后面全对也白打。 DRelay 在验证前加一步"修早错"。 拿整块 draft 的全局信息，把选错的位置换成对的那个。 说白了：实习生先交草稿，质检员拿全文通读一遍。 把前面的笔误改了，再送专家签字。

核心方法

  • 痛点：一个早期选择错误，后续预测全作废。
  • 更糟的是：后续预测是基于错 token 条件出来的，错上加错。
  • 诊断实验发现三个机会：

- 首次出错时，正确答案 94% 以上还在 top-16 候选池里。 - DFlash 94.0%、Domino 95.1%。 - 实际 serving 序列里 88.8%。 - 后面的预测能帮选对的候选：真实后缀比乱拼的对照准 53.5/44.4 个百分点。 - 修一个错平均多收 1.65/1.22 个 token。 - 分别是 DFlash 和 Domino 的数字。

  • Global Read：先把整块的候选分布做 top-16 槽位混合。
  • 再做候选专属读取，给每个候选拼一份"全局上下文"。
  • Causal Selector：逐个位置决定 KEEP 还是 REPAIR。
  • Gate 分支问"值不值得换"，Rank 分支问"换成谁"。
  • 修完一个，修复后的 token 进入已选前缀，影响后面的决策。
  • 联合训练：draft 主干学"把正确答案放进候选池"。
  • 选择器学"该修就修"，修复损失按前缀价值加权。
  • 前缀价值 = 修这个位置能多收多少连续 token。
  • 选择器只有 3506 万参数，不重复全词表投影。
  • 每轮多花 0.55ms，选择很克制。

关键数据

  • Qwen3-4B/8B × 8 个数据集（数学/代码/对话）。
  • 硬件：单 H800，框架：SGLang serving 实测。
  • 端到端加速最高 4.49×（相对自回归解码，MATH-500）。
  • 相对基线：比 DFlash 快 14.7%–16.8%。
  • 比 Domino 快 8.7%–9.3%。
  • 比 DSpark 快 8.1%–9.3%。
  • 平均加速超最强基线 7.8–9.9%。
  • 并发 serving 吞吐最高 4.38× AR。
  • 并发 32 时，Qwen3-4B 在 AIME25 上 2.34×。
  • HumanEval 上 2.27×。
  • Qwen3-8B 同设置 2.63×/2.89×。
  • 每轮延迟：验证 4.99ms + 起草 1.10ms + 选择器 0.55ms。
  • 总计 6.93ms，比 DFlash 多 8.6%。
  • 比 Domino 的 6.99ms 还低一点。
  • 消融：去掉 Global Read，接受长度 7.58→7.16。
  • 去掉 selector 监督，7.58→7.22；均匀加权，7.58→7.19。
  • 说明"学什么时候修"和"按前缀价值加权"都关键。

术语表

  • speculative decoding（投机解码）：小模型先打草稿。
  • 大模型只负责改错。
  • parallel drafting（并行起草）：一次前向同时预测多个位置。
  • accepted prefix（接受前缀）：验证轮里从头连续正确的那一段。
  • draft block（草稿块）：一次起草产生的一组候选 token。
  • candidate pool（候选池）：每个位置保留的 top-K 备选。
  • KEEP/REPAIR：保留原预测 / 换成候选池里的另一个。
  • prefix-value weighting（前缀价值加权）：
  • 按"多收多少连续 token"给损失加权。
  • anchor token：上一轮被目标模型确认的 token，当新一轮的起点。
