EAServe：encode 不再当甩手前台——它来管控整个 EPD 三段流水线

原文：EAServe: Encode-Aware Disaggregated Serving for Multimodal Large Language Models，佐治亚大学等（PACT '26），arXiv:2609.31551
原文链接：https://arxiv.org/abs/2609.31551

一句话人话版

多模态推理分三段走：encode 先把图转成向量，prefill 算一遍，decode 逐字生成。 问题出在第一步：encode 是所有流量的入口，可它的 GPU 天天摸鱼。 EAServe 干脆让 encode 当调度总管：下游何时放行、prefill 在哪算、GPU 怎么分，全它说了算。 效果很直接：同样的延迟要求下，能吃的请求量是 Dynamo 的 4.3 倍、vLLM 的 1.7 倍。

为什么这事值得看

结构性矛盾摆在那儿：每个请求必须过 encode 才能进下游。 但单次 encode 的算量很小，一张卡根本喂不饱。 作者实测发现：满负载下 encode 的计算和显存带宽双双躺平。 它自己不忙，却让下游的 prefill 和 decode 排队等饭吃，尾延迟爆炸。 现有的方案都没解决：纯文本 P/D 系统根本没有 encode。 NVIDIA Dynamo 把 encode 当甩手掌柜：一个请求一个请求地喂，不管下游死活。 P/D 解耦调配比已经够头疼，EPD 三段更是三个旋钮互相牵制。 这篇把 encode 扶正成控制点，等于给三段流水线找了个总调度。

核心方法

两层设计：上层 HAS 搜配置，下层三个 runtime 机制执行。 HAS 搜出的三个数，正好被 runtime 机制逐一兑现。

1. encode 当控制点，管三个耦合维度

  • encode 是管线入口，天然卡着流量命门。
  • 它管三件事：下游什么时候放行，prefill 在哪算，GPU 怎么分。
  • 三个维度互相牵制：乱调一个，另外两个跟着乱。
  • 打个比方：encode 是餐厅前台。不光登记，还管后厨何时开火、哪个灶台归谁。

2. 负载自适应的 micro-batching：按流量调攒批的耐心

  • encode 一次算一个请求太亏，攒成 batch 才划算。
  • 但攒太久耽误延迟，攒太短 GPU 吃不饱。
  • 固定超时两种流量都伺候不好：忙时失灵，闲时空等。
  • 他们从请求到达规律里直接推公式：g = κ / λ。
  • 流量大就收紧耐心，流量小就放宽，全自动，不用人工调。

3. 同机 prefill 偷闲：限速 offload

  • encode 的卡闲着也是闲着，顺手算一部分 prefill。
  • 但必须限速：deficit-counter router（记账式路由器）按比例 s 分流。
  • 账算清楚：encode 延迟不受影响是底线。
  • 打个比方：前台闲时帮忙打包外卖，客人来了立刻让位。

4. 动态 SM 切分：同一张卡上两任务分灶台

  • 用 libsmctrl（NVIDIA 的 SM 切分工具）把计算单元按比例切开。
  • 每个 micro-batch 查离线标定的表，动态调切分比例。
  • encode 吃饱就行，多余的算力拨给 local prefill。
  • 注意：切的是计算单元，显存带宽切不开。作者明说了这一点。

5. HAS（Hybrid Auto Selection）：配卡搜参两步走

  • Stage 1 画像剪枝：先给每个阶段单独测容量，建个排队论小模型。
  • 拿小模型给每种配卡打瓶颈分，不均衡的直接砍掉。7 种候选留 3 种。
  • Stage 2 TPE 贝叶斯优化：留下的候选真机试跑。
  • TPE（Tree-structured Parzen Estimator，越搜越往好地方钻的算法）沿好方向接着搜。
  • 搜参空间就三维：三阶段配卡、encode batch 上限 B、offload 比例 s。
  • 关键洞察：配卡好不好是单调的。某阶段饿死，怎么调 B 和 s 都救不回来。
  • 所以第一步只剪配卡，第二步专心搜 B 和 s，两步加起来几十次试跑就收敛。

关键数据

  • 环境：8 卡服务器；三档模态全覆盖：LLaVA-v1.6-34B 跑图，Qwen2.5-VL-32B 跑视频，Ultravox-v0.6-27B 跑音频。
  • 中等 SLO 档：图像 goodput 1.11 涨到 1.93，视频 1.32 涨到 1.90，音频 2.77 涨到 4.17。
  • 峰值：4.3 倍于 NVIDIA Dynamo，1.7 倍于 vLLM。
  • 延迟改善很夸张：2 req/s 时，图像 P99 TTFT 从 Dynamo 的 233.8 秒掉到 10.8 秒。
  • 视频 P99 TTFT 144.8 秒降到 18.0 秒。不是排版错误，Dynamo 的 encode 队列真的会无限堆。
  • P99 TPOT：图像 764 毫秒降到 72 毫秒，音频 869 毫秒降到 49 毫秒。
  • encode 卡利用率：Dynamo 不到 10%，EAServe 拉到约 80%。
  • 增益拆解：大头来自自适应 batching 和配卡，local prefill 是锦上添花。
  • 模态差异：视频上 HAS 直接选 s=1。多帧 encoder 自己占 90% 以上 SM，本地 prefill 没意义。
  • 音频上选 s<1。Whisper encoder 很轻，卡上有空位给 local prefill。
  • 搜参速度：HAS 到达 99 分位最优，图像 1.7 小时、视频 1.3 小时、音频 1.7 小时。随机搜在 30 轮预算内根本到不了。
  • 跨平台也成立：LLaVA-1.6-34B 在 RTX 6000 Ada 上 1.95 req/s，是 EPDServe 的 4.24 倍、HydraInfer 的 3.36 倍。A100 上 4.91 req/s，是两者的 4.86 倍和 3.25 倍。

跟你的研究方向哪里相关

  • 你在评估 SGLang 的 P/D 解耦：这篇是 P/D 解耦的多模态三段版，思路完全平行。
  • encode 当流量控制点可以直接借鉴。你的评估里可以试一层 encode 感知的 dispatch。
  • HAS 的"画像剪枝加贝叶斯搜参"，就是你 AI 自动调参系统的雏形。
  • 排队论先算个靠谱起点，TPE 再真机微调，这个两步走可以直接抄。
  • 注意局限：同卡切 SM 隔离不了显存带宽，搜参时别把这一维想得太美。
  • 视频场景 local prefill 收益为零。模态不同，搜参空间的有效维度不一样。
  • 跟 SARA 那篇连起来看：SARA 纯公式配卡，这篇公式剪枝加真机搜参，一静一动的升级版。

术语表

  • EPD：Encode-Prefill-Decode 三段管线，多模态推理的标准拆法。
  • encode：把图/视频/音频转成语言模型能读的向量，前台登记员。
  • prefill：模型把输入一口气算完、生成第一个字，厨房备第一单。
  • decode：逐字往外蹦答案，厨房逐道上菜。
  • goodput：达标吞吐，满足延迟要求的请求数除以时间。
  • TTFT：首 token 时间，敲回车到第一个字蹦出来。
  • TPOT：token 间延迟，字和字之间蹦的间隔。
  • SM：GPU 的计算单元大块，切分就是分灶台。
  • offload 比例 s：多少 prefill 放到 encode 卡上顺手算。
  • TPE：一种贝叶斯搜参算法，越搜越往好的地方钻。
  • micro-batching：把小请求攒成一桌再算，凑桌吃饭。
  • Poisson 到达：请求随机到来的经典数学模型，顾客随机进店。
  • libsmctrl：NVIDIA 生态的 SM 切分工具，给进程划地盘。
