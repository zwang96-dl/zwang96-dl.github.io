FastMTP：把模型自带的 MTP 头，调成投机解码的"神枪手"

原文：Optimize vLLM speculative decoding with FastMTP heads
出处：Red Hat Developer（Speculators v0.6.0 实战指南），2026-09-08 发布
链接：https://developers.redhat.com/articles/2026/09/08/optimize-vllm-speculative-decoding-fastmtp-heads
相关论文：Cai et al. *FastMTP*，arXiv:2509.18362

一句话人话版

  • 有些模型自带"多 token 预测头"（MTP 头，能一次猜好几个 token）。
  • 投机解码（speculative decoding，先让小模型打草稿、再让大模型批改的加速法）正好需要这样一个打草稿的。
  • 但直接拿来用会"水土不服"：训练时只学了一步，推理时却要连打好几步。
  • FastMTP 就是一套微调配方，专门把这个头调成"连发神枪手"。
  • 调完直接用 vllm serve 跑起来，不用改推理引擎。

背景：原生 MTP 头为什么直接用不好

  • 自回归解码（autoregressive decoding，一个 token 一次前向的生成方式）是访存瓶颈：每次都要把几十亿参数过一遍。
  • 大部分时间花在搬权重上，而不是算。
  • DeepSeek、Qwen3-Next 这类模型训练时学了多 token 预测。
  • 于是 checkpoint 里顺带留下了 MTP 头，本来是现成的 draft 头。
  • 但训练时它只负责"下一个 token"，输入还是标准答案。
  • 推理时引擎却让它递归连打：打一个，再拿自己的输出接着打。
  • 误差越滚越大，第二、三个 token 的接受率直线掉。
  • 这就是 train/serve mismatch（训练和上线用法对不上）。

核心方法

FastMTP 式微调：按上线的方式重新练一遍

  • 只取原生 mtp.* 权重起步，不用从零训练。
  • 训练循环照搬上线：teacher-forced 的递归 loop。
  • 第 k 步：token 嵌入 + 当前 hidden state 融合，MTP 层出 hidden state。
  • lm_head 出 logits，loss 目标是 input_ids[t+k+2]。
  • 再把输出的 hidden state 喂回去，当第 k+1 步的输入。
  • 每步 loss 按指数衰减加权：beta=0.6、3 步时权重是 0.51、0.31、0.18。
  • 逻辑很直白：越靠前的 token 越容易被接受，多给点权重。

四个工程细节，决定它能直接落地

  • 全词表 draft 头：跟 verifier（主模型）共用 embed_tokens 和 lm_head。
  • 没有词表裁剪，没有单独的输出投影要对齐。
  • 权重格式跟 vLLM 期望的 mtp.* 键完全一致。
  • 微调完 stitch 回 checkpoint，一个标准 vllm serve 就能跑。
  • 只读 verifier 最后一层的 hidden state 来训练。
  • 所以它是所有 speculator 里最轻的：离线数据小、在线训练快。
  • 在线训练直接连一个 live 的 vLLM server 现场抽 hidden state。

什么时候该用它：三问自查

  • 你的 verifier 自带 MTP 头吗？（目前支持 Qwen3-Next、Qwen3.5，含 MoE）
  • 没有的话换 EAGLE-3、DFlash 或 P-EAGLE。
  • 你的 workload 是垂域的吗？（数学、代码这类）
  • 在垂域数据上微调，头会打得更准。
  • 内存和算力预算够吗？MTP 是开销最小的一档。

关键数据

  • 模型：Qwen/Qwen3-Next-80B-A3B-Instruct，GSM8K 上训、GSM8K 上测。
  • 接受率 pos 0：0.897 → 0.912（本来就高，提升小）。
  • 接受率 pos 1：0.719 → 0.776。
  • 接受率 pos 2：0.476 → 0.616（提升近 14 个百分点，递归误差被压住了）。
  • 端到端：median inter-token latency（ITL，token 间延迟）全 RPS 区间都更低。
  • 最高加速 1.25×，见下图。
  • 训练成本：Qwen3.5-9B 在 GSM8K 上，2×H200 跑了约 443 秒。
  • 实测工具链：GuideLLM 0.16.0 + vLLM 0.24.0。

图注：横轴是每秒请求数（RPS），纵轴是中位数 token 间延迟（ITL，毫秒）。黑线是原生 MTP 头（base），绿线是 FastMTP 微调后（finetuned）。微调后整条曲线都在下方，说明各并发下延迟都更低；两线之间的色带表示加速比，最高到 1.25×。曲线随 RPS 上扬是正常的：请求一多，排队和批处理开销都会涨。

跟你的研究方向的关联

  • 你正在评估 vLLM，speculative decoding 是 vLLM 官方重点推的加速路线之一。
  • 这篇是 vLLM 生态（Speculators 项目）的官方实战配方，不是第三方野路子。
  • 核心矛盾跟 P/D 解耦评估相通：都是"训练/上线用法对不上"带来的效率损失。
  • 443 秒、2×H200 的微调成本很低，意味着可以在自己的垂域数据上复刻。
  • 如果以后在 MI350 上跑 vLLM 做 spec decoding，这套流程是直接可用的起点。

术语表

  • MTP（multi-token prediction）：一次预测好几个未来 token 的训练目标。
  • Speculative decoding（投机解码）：小模型打草稿、大模型一次性批改的加速法。
  • Draft/verifier：打草稿的小模型 / 负责验收的大模型。
  • Acceptance rate（接受率）：草稿 token 被大模型接受的比例。
  • Teacher forcing：训练时喂标准答案、而不是模型自己的输出。
  • ITL（inter-token latency）：相邻两个 token 吐出的时间间隔。
  • Stitch：把微调好的头"缝"回主模型 checkpoint。

实操配方速查（原文四步）

  1. 准备数据：scripts/prepare_data.py --model Qwen/Qwen3.5-9B（5000 样本、seq-len 8192）。
  2. 起 verifier：scripts/launch_vllm.py Qwen/Qwen3.5-9B --target-layer-ids 32。
  3. 微调：scripts/train.py --speculator-type mtp --num-speculative-steps 3 --step-weight-beta 0.6 --epochs 3。
  4. 缝合上线：vllm serve ./output/stitched --speculative-config '{"method":"mtp","num_speculative_tokens":3}'。
