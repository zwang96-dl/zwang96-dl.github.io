别猜了，直接问工具：agent 工具调用的进度，serving 系统应该读

原文：Ask the Tool, Don't Guess: Agent Tool Calls Hold Their Progress, and the Serving System Should Read It（arXiv:2609.18849v1 [cs.DC]，2026-09-16；清华刘毅鹏 + 阿里云团队）
⚠️ 阅读前说明：学术论文，不是生产部署指南。数据来自作者自建的 harness 和生产引擎插件实验。四个 agent 数据集都是公开语料（mini-SWE-agent、OpenHands 等）。结论在你自己的 agent 负载上还需验证。

人话解读

agent 干活有个老毛病：调工具的时候干等。 装个包、编译个项目、跑个测试套件，几分钟眨眼就没了。 等的这段时间，请求的 KV 缓存（草稿纸）一直占着显存，谁也用不了。

serving 系统这时候要做选择题：缓存留着？踢出去腾地方？还是提前搬回来？ 今天它靠"猜"：看工具名字、翻历史耗时、读调用前声明的时长。 但工具跑多久，调用前根本看不出来。 同一条命令，机器负载一变，耗时能差一个数量级。

论文的观点很直接：别猜了，问工具自己。 跑着的工具其实知道进度，只是被"消音"了。 harness 把进度条关了，agent 把输出 pipe 到 tail -5，serving 就两眼一抹黑。 作者的办法是加一条旁路：工具照常跑，agent 看到的东西一点不变。 serving 在旁边偷偷读工具的进度，拿来做 KV 缓存决策。

核心方法

  • 三层"消音"，三层破解。第一层是基础设施和 agent 的习惯：环境变量关掉 pip 和 tqdm 的进度条，输出用 tail 只留几行。第二层是工具"不问不开口"：得加 verbose 开关它才报进度。第三层是 agent 自己生成的脚本：本来就没进度可言。harness 逐层破解：重开进度输出但只走旁路、替 agent 去问工具要详细输出、给生成的脚本自动加进度上报行。
  • 一次执行，两个消费者。agent 走的老路原样不动：调用、执行、原格式返回。新加一条状态路：进度探针读工具的原始输出和它在磁盘上留下的文件，按 call_id 上报进度。serving 控制器根据"预计还剩多久"做决策，KV 引擎执行留、踢、搬回。
  • 信号分两档。强信号直接报剩余工作量，比如"编译 40/66 个文件"。弱信号只报"快结束了"，比如 pip 装完最后一个包前的提示。强信号拿来做精确调度，弱信号至少能触发"提前搬回"。
  • 进度报告当"不可信输入"处理。工具可能乱报，serving 把它当参考而不是圣旨。机制上有防范，但这部分论文着墨不多，生产落地要自己补。

关键数据

  • 长调用是少数，但占了大头。不到一成的工具调用，占了约三分之二的工具等待时间。优化就盯这几分钟的大家伙，短调用不值得折腾。
  • 信号覆盖不小。四个 agent 数据集普查：强信号占工具时间的 38–51%。加上弱信号，能到 59–72%。剩下的才是真没辙的。
  • 精度碾压"猜"。调用中点做"踢谁"决策：进度流的中位误差约是调用时长的五分之一，历史最佳预测是三分之一。调用 90% 处做"何时搬回"决策：进度流误差不到 10%，历史预测是 80%。差了几倍到一个数量级。
  • 生产引擎实测。接进生产引擎只改了几个小地方：工具调用后的 p90 TTFT（首 token 时间）降 20.7%（纯显存）和 20.8%（显存+内存），吞吐还涨约 2%。四个已发表的方法在这个场景下基本没带来延迟收益。离全知先知基线已经不远。
  • 调用越长，赚得越多。60 秒以上的工具调用，TTFT 降 34–35%。短调用本来也等不了多久，收益自然小。
  • 对 agent 零打扰。harness 不改 agent 看到的任何东西，benchmark 分数没测出变化。试点成本很低。

跟你的研究方向的关联

  • KV 缓存管理的 agent 场景补丁。你在评估 SGLang 的 P/D 解耦，解的是 prefill 和 decode 的资源分配。这篇补的是另一块：agent 等工具时，decode 上下文的 KV 缓存怎么管。两者互补，不是替代。
  • "问进度"可以先在评测 harness 里试点。不用动 serving 引擎，先给 agent 的执行包装器加个旁路探针。看自己的 agent 负载上强弱信号各占多少，再决定值不值得往引擎里接。
  • 跟前缀缓存是同一笔账。工具调用前后是同一个请求，缓存的复用逻辑跟前缀缓存相通。这篇的"何时搬回"触发器，可以跟你之前读的前缀缓存笔记对照着看。

术语表

  • TTFT（Time To First Token，首 token 时间）。请求发出去到第一个字蹦出来的耗时。交互体验的第一指标。
  • KV cache（KV 缓存，草稿纸）。解码时缓存的键值，后续 token 不用重算。占显存大户。
  • LRU（最近最少使用）。缓存满时先踢掉最久没碰过的。论文里的对比基线。
  • HBM（高带宽显存）。GPU 片上的高速显存，又贵又小。
  • harness（执行包装器）。包在工具外面跑的壳，负责执行和采集，不改变工具行为。
  • side channel（旁路通道）。跟 agent 主流程并行的一条信息通道，agent 感知不到。
  • oracle（先知基线）。假设全知全能的最优决策，用来量理论天花板。
  • P/D 解耦（prefill/decode 解耦）。把"读题"和"答题"拆到不同 GPU 池，流水线分工。
