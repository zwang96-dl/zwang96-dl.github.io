H100 上 vLLM vs SGLang 实测：没有永远的赢家，只有跟负载走的瓶颈

文章：vLLM vs SGLang on H100: The Winner Depends on the Workload
作者：Oluwatosin O. Ayeni（2026 年 9 月，Medium）
原文：https://medium.com/@ayenioluwatosinolawale/vllm-vs-sglang-on-h100-the-winner-depends-on-the-workload-9a11d8646adf
（Benchmark A；作者预告了 Benchmark B——20 轮 agent 多轮对话、Benchmark C——持续流式数据注入，后续值得跟）

一句话人话版

同一块 H100、同样的 Qwen2.5-7B。低并发时 SGLang 延迟更低，高并发时 vLLM 吞吐更高。两者的性能曲线在中间交叉了。所以"vLLM 和 SGLang 谁更快"是个伪问题。真问题是"你的负载长什么样"。

它解决什么问题

选 serving 框架时，网上的 benchmark 结论经常互相打架。有人说 SGLang 快，有人说 vLLM 快。这篇文章的价值在于不追求一个"总冠军"。而是把并发度这个变量扫了一遍。找到两条性能曲线交叉的位置。并解释交叉背后是谁在拖后腿。

实验设置很干净，结论可复现：

  • 模型：Qwen2.5-7B-Instruct，输入 2048 tokens、输出 256 tokens
  • 硬件：H100 NVL 94GB（PCIe）和 H100 SXM 80GB（SXM 高带宽）各一块
  • 负载：并发 1（单用户）和并发 128（高压）两个极端 + 中间采样
  • 指标：TTFT（首字延迟：请求发出到看到第一个字的时间）p50/p95、decode 吞吐、请求吞吐、GPU 利用率
  • 测试脚本和 JSON 结果已开源（见原文末尾）

核心发现一：TTFT 在并发升高时"反转"

图注（人话解读）：H100 NVL 94GB。单用户时 SGLang 的 TTFT p50 是 33ms。vLLM 是 37ms。SGLang 快约 11%。decode 吞吐也高 3.4%（182 vs 176 tok/s）。但并发拉到 128 时。vLLM 的 TTFT p50 是 504ms。SGLang 是 583ms。vLLM 反而快了。请求吞吐 vLLM 27.6 req/s。比 SGLang 的 25.0 req/s 高约 10%。两条曲线交叉：低并发看延迟选 SGLang，高并发看吞吐选 vLLM。注意：SGLang 的 TTFT p95 是 807ms。仍略好于 vLLM 的 819ms。说明只看一个指标容易被带偏。

核心发现二：高并发下 SGLang 的 GPU 利用率"塌了"

图注（人话解读）：这是整篇文章最有信息量的一张图。64 用户时。vLLM 的 GPU 利用率仍 ~100%。SGLang 掉到 ~48%。128 用户时 vLLM 还是 ~100%，SGLang 只剩 ~8%。GPU 大量空转。作者的解释：这个负载下瓶颈已经不在 GPU 算力。而在调度/排队/批处理/请求管理。vLLM 的 continuous batching（连续批处理）加 KV 管理。把 GPU 喂饱了。而 SGLang 的调度器没能把 batch 组好。这个负载"前后缀共享很少"。作者也强调：这不代表 SGLang 的调度器 universally 差。比如 prefix 共享高的 agent 负载。RadixAttention 反而是优势。换负载结论可能反转。

核心发现三：硬件带宽的红利，低并发才吃得到

图注（人话解读）：同样单用户。换到 HBM 带宽更高的 H100 SXM 80GB。vLLM 的 TTFT 从 37ms 降到 22ms（-40%）。SGLang 从 33ms 降到 28ms（-15%）。说明低并发时瓶颈在 GPU 侧（显存带宽/内核效率）。更好的硬件直接转化为更低的延迟。但高并发时两套硬件的请求吞吐都收敛到 ~27 req/s。瓶颈已经移到调度/队列。再快的 GPU 也喂不进去。类比：早高峰前修宽马路有用。早高峰时堵的是收费站，路再宽也没用。

跟你的研究方向的关联

  1. 框架选型直接参考。你在评估 SGLang 的 prefill/decode 解耦。P/D disaggregation 就是"读题"和"答题"拆到不同 GPU 池。像分工流水线。这篇的结论是单框架内的，但逻辑可迁移。P/D 解耦的价值：把"低并发延迟敏感"和"高并发吞吐敏感"两类负载分开优化。做 P/D 评估时，建议照着这篇的方法论：至少扫并发度。同时看 TTFT p50/p95 + 吞吐 + GPU 利用率。别只报一个 tokens/s。
  2. RadixAttention 的适用边界。SGLang 的 RadixAttention 是前缀树缓存。相同开头的请求，复用已算好的 KV cache"草稿纸"。在前缀共享高的负载下是优势。比如多轮对话、agent。这篇的混合 batch 前缀共享少，优势发挥不出来。你的多模态场景里"同一张图被问不同问题"正是前缀共享的典型场景。选 SGLang 做多模态时。这个测试维度值得自己复测：prefix hit rate vs 并发。
  3. Benchmark B/C 预告：作者接下来要做两件事。一是 20 轮 agent 多轮对话。context 从 2K 涨到 12K。看 prefix/KV 复用对 TTFT 的影响。二是持续流式注入。这两个正是 agent serving 和实时多模态的场景。出了值得跟进。

术语表

  • TTFT：Time To First Token，首字延迟。从发出请求到看到第一个 token 的时间。主要由 prefill（"读题"）决定。
  • TPOT：Time Per Output Token。之后每个 token 之间的平均间隔。由 decode（"答题"）决定。
  • p50/p95：延迟分布的分位数。p50 是中位数。p95 是"95% 的请求都比它快"的线。看长尾体验。
  • Continuous batching：连续批处理。请求随到随加入正在执行的 batch。不用等整批凑齐。是现代 serving 框架的标配。
  • RadixAttention：SGLang 的前缀缓存机制。用 radix 树索引跨请求的共享前缀。复用已算好的 KV cache。
  • H100 NVL vs SXM：NVL 是 PCIe 版（94GB）。SXM 是 SXM 版（80GB，HBM 带宽更高）。同代 GPU 里 SXM 的访存带宽明显占优。
  • GPU 利用率塌陷：GPU 空转、算力没被用上。通常意味着瓶颈在 CPU 侧的调度/排队。而不是 GPU 本身不够快。

一句话总结

别再问"vLLM 和 SGLang 谁更快"。延迟敏感、低并发 → SGLang；吞吐优先、高并发 → vLLM。真正的工程问题永远是"瓶颈现在在哪"。而瓶颈会随并发度搬家。
