Nari Labs 自研 Qwen3-TTS 推理引擎：凭什么说 vLLM/SGLang 不适合多模态推理

原文：Show HN: Nari Qwen3-TTS and Qwen3-ASR – High accuracy, low latency and cost（Hacker News，2026-09-14，62 points / 19 评论）
引擎仓库：nari-labs/nari-qwen3-tts（已开源）
⚠️ 阅读前说明：这是一家语音 AI 公司的自荐帖。所有数据都是"自报"的。基准对比的基线调优是否到位，外人无法验证。数字和思路可以借鉴。但别当成同行评审过的结论。

人话解读

Nari Labs 去年做了 Dia。Dia 是第一个能自然对话的开源语音模型。从那以后，开源语音模型越来越多。但市场还是闭源模型的天下。他们认为这是个推理问题。原话是这么说的：现有系统比如 vLLM/SGLang，不适合多模态推理。为了证明这点，他们给 Qwen3-TTS 专门写了个推理引擎。还开源了。数据很能打。单块 H100 上，10 个并发请求，首音频延迟 p95 不到 50 毫秒。在 Coval 语音基准上，他们的 TTS 端点延迟排第 2、准确率排第 1，价格还最低。

他们到底做了什么

  • 只做一件事：专跑 Qwen3-TTS 1.7B CustomVoice 这一个模型。不做通用框架。只做单机单 H100。
  • 接口对齐 OpenAI：POST /v1/audio/speech 长得跟 OpenAI 的语音接口一样。只支持 wav 和 pcm 输出。语速只支持 1.0 倍。
  • 流式优先：除了普通 HTTP，还有 WebSocket 接口。文字可以边进边说。不用等整句话输完。
  • 三个性能档：ttfa（首音频优先）、balanced（默认，兼顾）、throughput（吞吐优先）。用环境变量或启动参数切换。
  • Docker 一键跑：官方镜像 + 命名卷缓存模型和编译好的 kernel。启动时做完 CUDA Graph 捕获和热身请求，/ready 才变绿。

核心方法（能抄的工程点）

  • 延迟导向的调度。ttfa 档用"先让第一个请求出声"的调度策略。不是"让所有请求平均快"。语音场景里，用户只关心"多久听到第一声"。
  • Codec 首块切小。Codec 是把 token 变成声音波形的模块。第一块音频切小一点。首音频延迟直接下来。后面的块再正常大小，保证连续播放。
  • CUDA Graph 全程捕获。CUDA Graph 是把一串 GPU kernel 调用录下来。之后一次发射，省掉每次调度的开销。启动时就录好。热身跑通才对外服务。
  • 文本增量流式。WebSocket 接口支持文字流式输入。LLM 那边 token 一个个吐。这边攒够一小段就开始合成。两段流水线重叠。
  • 配置即代码。三个档位的参数全写进 YAML。启动时打印完整配置和 SHA-256。调优结果可复现。

关键数据

  • TTFA（首音频延迟）：10 RPS 下 p95 < 50ms。20 RPS 下 p95 < 80ms。单块 H100 SXM。
  • Coval 语音基准（YC S24 的第三方语音评测）：TTS 端点延迟第 2、准确率（WER）第 1。对比对象包括 11Labs、Cartesia 等。价格全场最低。
  • ASR 端点：延迟全场最低。准确率第 2，只比第 1 差 0.1%。价格第二便宜。
  • 官方对比：阿里官方的 Qwen3-TTS 端点，在准确率和延迟上都不如他们。但他们公开感谢了 Qwen 团队开源模型。

他们的论点 vs 冷静看

他们的论点：通用推理框架是为"纯文本 LLM"设计的。多模态管线里，文本生成只是第一步。后面还有 codec 解码、音频拼接、流式 chunking。通用框架的调度器不懂这些阶段的诉求。所以端到端延迟做不下去。

冷静看，有三点要打折：

  • 只跑一个模型。Qwen3-TTS 1.7B，参数量小。通用框架要伺候几十种架构。拿专用引擎打通用框架，有点像"短跑运动员跟十项全能比百米"。
  • 基线可能是"裸奔版"。vLLM-Omni 和 SGLang-Omni 的官方多模态分支被拉来当基线。但有没有按语音场景调优过，外人不知道。社区评论里也有人质疑这点。
  • 硬件和语言都受限。只测了 H100，只测了英文。换卡、换语言，数字未必成立。

但有一点值得认真对待：他们敢把 vLLM-Omni 和 SGLang-Omni 列为基线，还列在自家仓库的"感谢"里。这说明争论的焦点不是"通用框架行不行"。而是"多模态管线里，文本之外的阶段谁来管"。这正是你现在评估 SGLang P/D 解耦时要回答的问题。

跟你研究方向的关联

  • P/D 解耦的"第三阶段"视角。语音管线天然是三段式：LLM 生成 token（类 prefill/decode）、codec 解成音频、流式输出。Nari 的优化全在后两段。这提示你：评估 SGLang P/D 解耦时，别只看文本 token 的吞吐。多模态场景下，encoder 和 decoder 侧的资源分离可能是更大的优化空间。
  • "延迟导向调度"可以借鉴。P/D 解耦里，decode 节点的调度目标通常是吞吐。但交互式多模态场景（语音、实时字幕），TTFA/TTFT 比吞吐更重要。Nari 的 ttfa 档就是"为首包延迟牺牲一点吞吐"的实例。
  • 专用 vs 通用的决策框架。你的 MI350 benchmark 是在 vLLM 通用框架上跑的。如果未来要上语音/多模态业务，这篇是个反例：专用引擎在单模型上能把通用框架甩开一个数量级。选型时要算"一个模型吃透"和"一套框架通吃"的账。
  • Benchmark 方法论。他们用 Coval 第三方基准 + 自家 p95 负载曲线。两份证据互相印证。你以后做 P/D 解耦的对比测试，也可以学这套：第三方基准定"准不准"，自家负载曲线定"稳不稳"。

术语表

  • TTFA（time-to-first-audio）：从发请求到听到第一声的耗时。语音服务的核心延迟指标。
  • RPS（requests per second）：每秒请求数。并发压力的度量。
  • p95：95 分位延迟。100 个请求里，95 个都比它快。比平均值更能反映"大多数人"的体验。
  • WER（word error rate）：词错率。语音识别/合成准确率的指标。越低越好。
  • Codec：编解码器。这里指把 token 变成声音波形的神经网络模块。
  • CUDA Graph：把一串 GPU kernel 调用录下来复用。省掉每次发射的调度开销。
  • Coval：YC S24 的一家公司。做的语音 AI 基准测试。引用率很高。
  • Diarization：说话人分离。"这段是谁说的"的技术。他们说下一步要做。
