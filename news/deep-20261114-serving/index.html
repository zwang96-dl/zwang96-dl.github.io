评测分数背后的 serving 账：同一模型，换套 serving 分数差一倍

  • 原文：Will Youzhi Zou，Geodesic engineering
  • 文章：Great Pizzas Need Great Ovens: Why LLM Evaluation Depends on Serving Quality
  • 发布时间：2026-11-13
  • 原文链接：https://medium.com/@willyouzhizou/great-pizzas-need-great-ovens-why-llm-evaluation-depends-on-serving-quality-ac81709c9be9
  • 说明：数字全是作者自报，没有第三方实测；Medium 拦了直接抓图，两张图按原文数据重绘

一句话

同一模型，同一批题。只换 serving，通过率从 24% 涨到 46%。分数不光看模型，也看烤箱。

人话解读

Terminal-Bench 是给 agent 的考试。发一台 Linux 机器、一道任务、一个倒计时。agent 自己敲命令、跑代码、交结果。时间一到就判分。

时钟一直在走。等模型回话的时间也算在里面。模型回得慢，agent 能试的次数就少。试得少，通过率自然低。

作者一开始用的是慢 serving。一张 H200，还跟 RL 训练共用。64 个 agent 一起挤。引擎一次只能跑 42 个请求。排队的一直有 9 个左右。前缀缓存命中只有 55%。30K 词的长对话，一轮要等 100 到 170 秒。

换成快 serving 之后，同一模型涨了 22 个点。8 张 H100 的专用节点。4 个 SGLang 引擎，各管 2 张卡。每个 agent 固定钉在一个引擎上。对话历史一直留在那台引擎的缓存里。命中率 93.5% 到 94.6%。

烤箱的比喻很贴切。同一位厨师，同一团面。弱烤箱出夹生饼，好烤箱出脆皮饼。agent 考试也一样。模型是厨师，serving 是烤箱。

图 1：同一模型 Qwen3.6-27B，跑 Terminal-Bench 2.1。只换 serving，通过率从 24.4% 涨到 46.4%。超时率从 57% 掉到 12.3%。Tmax 公开记录是 43.6% 和 12.8%，跟快 serving 贴得很近。

核心方法

方法分三招。都围着一个问题转：分数里有多少是 serving 的功劳。

第一招：定义 serving 质量，分四项报。每位 agent 的速度：等模型时每秒拿到多少词。响应：首字时间，排队和重算都会拉长它。吞吐：所有 agent 加起来每秒多少词。容量：一次能跑多少请求，缓存里还剩多少。

第二招：慢快两套 serving 同题对比。慢的那套：1 张 H200，SGLang，64 个 agent 共用。快的那套：8 张 H100，4 个 SGLang 引擎，40 个 agent。模型、题库、判分规则都不变。只换 serving。

第三招：反事实重放，算时间账。拿快 serving 里通过的 trial 重算时间。按慢 serving 每秒 9.3 词算。命令执行时间不变。只看有多少 trial 会超时。结果是 41% 的通过 trial 会超时。约等于全场 46.4% 里的 19 个点。

还有一招值得抄：全程仪表盘。每次 rollout 都盯着看板。数据、基线、评测、RL 每步都有。看板上画了两条参考线。Tmax 公开记录是红线。慢 serving 是灰线。

关键数据

  • 训练任务 20 道：慢 serving 通过率 24.4%。快 serving 46.3%。
  • 全场 88 道题：快 serving 46.4%（204/440）。Tmax 论文报 43.6% ± 1.9。
  • 超时率：慢 serving 57%，快 serving 12%。Tmax 记录 12.8%。
  • 每位 agent 速度：慢 serving 9 词每秒。快 serving 78 词每秒。Tmax 记录 41 词每秒。
  • 总吞吐：快 serving 1347 词每秒。Tmax 记录约 92 词每秒。
  • 前缀缓存命中：慢 serving 55%。快 serving 93.5% 到 94.6%。
  • 首字时间：快 serving 中位数 130 毫秒，P90 是 226 毫秒。
  • 词间延迟：快 serving 中位数 12.7 毫秒，P90 是 14.8 毫秒。
  • 超时 trial 里 77% 的时间在等模型，只有 8% 在跑命令。
  • 思考是大头：每 trial 约 3 万词。45% 的词花在超 16384 词上限被截掉的调用上。
  • 41% 的通过 trial 在慢 serving 上会超时。最多要 7 倍时间。
  • 速度的甜点区：每位 agent 41 到 78 词每秒，超时率基本不动。
  • 再往上提速，瓶颈换成上下文窗口。40 到 60 分钟的长任务，一半卡在 65K 上限。

图 2：左图是每位 agent 等模型时的速度。慢 serving 只有 9 词每秒，快 serving 78 词每秒。右图是前缀缓存命中率。慢 serving 55%，快 serving 94%。速度差 8 倍多，命中率差近 40 个点。

每次评测都该报的六项清单

这是全文最值得抄的部分，照原文翻过来。

  1. 硬件和引擎：卡的型号和数量、引擎和版本、精度、并行方式。
  2. 负载：同时跑几个 agent、引擎的并发上限、缓存命中率。
  3. 实测速度：每位 agent 每秒词数。等模型时和全程都要报。总吞吐、首字和词间延迟，报 P50 和 P90。
  4. 词预算：上下文长度、每轮上限多少词、超了怎么办、思考开没开、留不留。
  5. 限制和结果：时间倍数、调用上限、命令超时、超时率、上下文截断率、截断调用率。
  6. 沙箱：后端、每任务的 CPU 和内存。

跟研究方向的关联

这篇跟 PD 解耦评估直接相关。

第一，评估口径可以直接抄。PD 评估里读题和吐词分开跑，更要分开报速度。按这四项报：每位 agent 的速度、首字时间、词间延迟、缓存命中率。

第二，缓存命中率是第一指标。94% 对 55%，直接决定分数。PD 评估清单里，命中率要按池子分开报。读题池和解码池各报各的。

第三，速度有甜点区。41 到 78 词每秒之间，超时率不动。PD 评估不用一味追速度。先找到甜点，再看别的瓶颈。

第四，上下文窗口是下一个瓶颈。serving 快了，长任务卡在 65K 上限。PD 评估里，长上下文任务要单独列。别跟短任务混在一起报。

第五，RL 训练也要这套账。rollout 服务器配弱了，慢 serving 直接把奖励打成 0。奖励量的不光是策略，还有集群。PD 评估的 rollout 项，可以直接抄这套看板。

第六，思考 token 的账要单独列。45% 的算力花在被截掉的调用上。PD 评估里，截断调用率要单列。别让它悄悄吃掉预算。

术语表

  • Terminal-Bench：给终端 agent 的考试基准。一台机器、一道任务、一个倒计时。
  • serving 质量：serving 系统伺候每个 agent 的好坏。分速度、响应、吞吐、容量四项。
  • 每位 agent 速度：agent 等模型时，每秒拿到多少词。决定一轮考试能试几次。
  • 首字时间：从发请求到第一个词出来，要等多久。
  • 词间延迟：两个词之间隔多久。越小读着越顺。
  • 前缀缓存命中率：多少提示词不用重算，直接从缓存里拿。
  • 反事实重放：假设换个条件，把历史数据重算一遍。看结果会差多少。
  • P50 / P90：一半 / 九成的情况比这个数好。看长尾要盯 P90。
