LCLM：上下文压 16 倍的端到端压缩器

原文链接

  • 论文：End-to-End Context Compression at Scale（arXiv:2606.09659）
  • 报道：VentureBeat：Context compression finally works in production
  • 代码：github.com/LeonLixyz/LCLM；模型：huggingface.co/latent-context
  • 团队：NYU、Columbia、Princeton、Maryland、Harvard、LLNL

人话解读

长上下文推理最卡的是内存。KV 缓存（注意力中间结果的缓存）跟着上下文一起疯长。

老办法是先把草稿纸写满，再撕掉几张。LCLM 反过来：先缩写，再交卷。

0.6B 的小编码器先把输入读一遍，压成潜 token（压缩后的隐向量块）。4B 解码器直接读潜 token，它这辈子没见过原文。

压缩发生在 prefill（首轮前向，把 prompt 一次算完）之前。16 倍压缩约等于 prefill 算力直接砍到十六分之一。

训练下了血本：350B token，4×/8×/16× 三档各训一版。架构搜索有个反直觉结论：放大解码器比放大编码器更划算。

结果很硬：16× 压缩 RULER 拿 75.06%。同压缩比的 KV 缓存方法全被甩开。TTFT（首 token 延迟）快 8.8 倍。

划重点：KV 缓存压缩得先算完全量 prefill。压缩这步省不了 prefill 的时间。LCLM 在 prefill 之前就把序列缩短。上下文越长，省得越多。

核心方法

  • 输入分块：长输入切成窗口，每窗至多 1024 token，编码器一次吞一窗。
  • 编码：0.6B 编码器读原文，输出每个 token 的隐状态。
  • 池化：mean pooling（取平均池化）把每 N 个隐状态压成 1 个潜 token。
  • 适配：一个小 MLP（多层感知机投影）把潜 token 对齐到解码器维度。
  • 解码：4B 解码器直接读潜 token，当上下文做推理。
  • 训练分四段：先热身适配器，再解冻编码器，再端到端联调，最后 SFT（监督微调）。
  • 数据有三类：交错式持续预训练、SFT 问答推理、重建辅助任务。
  • 重建任务是让模型照着压缩块默写原文，逼编码器留住细节。

关键数据

  • RULER（4k 上下文）：4× 压缩 91.76%，不压缩 94.41%，只掉 2.65 个点。
  • 16× 压缩 75.06%：KVzip 62.73%、Attention Matching 69.21%，同压缩比全败。
  • 8× 压缩 85.42%：4×/8×/16× 三档全是新的 Pareto 前沿（精度速度双优线）。
  • TTFT：RULER 4k 快 8.8×，LongBench 64k 快 5.2×，H200 单卡实测。
  • GSM8K：整道题全部压缩，各压缩比下都是全场第一。
  • 1M token：16× 版在单卡 H200 上内存不爆，KV 缓存方法早 OOM 了。
  • Agent 玩法：智能体先读压缩版，需要时再展开指定块，长程任务更省。

跟你的研究方向的关联

  • 这是 prefill 侧的压缩：序列在进解码器前就变短了。
  • prefill 算力按压缩比直接砍，KV 搬运量也同比例降。
  • 跟你在评估的 P/D 解耦（prefill/decode 分离部署）走的是同一条路：给 prefill 降本。
  • 可以叠加：压缩后的短序列再走 P/D 解耦，prefill 机器压力更小。
  • 同赛道还有 LatentPress（arXiv:2609.01507）：只训 0.1% 参数的轻量路线，适合快速验证；LCLM 是重训路线的天花板。
  • 作者自己提醒：推理链（reasoning trace）的在线压缩还没做，agent 长思考场景先别指望。

术语表

  • LCLM：Latent Context Language Model，潜上下文语言模型。
  • 潜 token：压缩后的隐向量块，解码器直接读它。
  • TTFT：Time To First Token，首 token 延迟。
  • RULER：长上下文基准，专考"大海捞针"式检索推理。
  • KV 缓存：注意力层的中间结果缓存，随上下文线性涨。
  • prefill：首轮前向，把 prompt 一次算完的阶段。
  • mean pooling：取平均池化，把 N 个向量压成 1 个。
  • Pareto 前沿：精度和速度都没人能同时赢你的那条线。
  • SFT：监督微调，拿问答对教模型听话的阶段。
