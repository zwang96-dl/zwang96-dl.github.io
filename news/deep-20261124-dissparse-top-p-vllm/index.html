DisSparse：top-p 稀疏注意力进 vLLM，批量开到 8 倍

  • 原文：DisSparse: Pipelined Top-p Sparse Attention for Long-Context LLM Serving
  • 作者：Nurlan Nazaraliyev、Elaheh Sadredini、Nael Abu-Ghazaleh，加州大学河滨分校
  • 提交：2026-11-21，arXiv:2611.28522
  • 原文链接：https://arxiv.org/abs/2611.28522
  • 说明：数字全是作者自报。
  • 端到端只在 2 张 A100-40GB 上测过。
  • 只测到 32K 上下文。

一句话

长上下文解码只读关键 token。

批量能开到稠密版的 8 倍。

精度基本不掉。

人话解读

长上下文推理卡在 KV 缓存上。

KV 缓存就是解码时留的草稿纸。

上下文越长，草稿纸越厚。

读一遍的带宽比算本身还贵。

稀疏注意力只读关键 token。

像开会只听重点发言。

以前大家用固定 top-k 选 token。

每层每头固定挑 k 个块。

可每个头的注意力分布不一样。

有的头只盯附近几个词。

有的头要扫全场。

固定数量要么多算，要么漏关键内容。

top-p 是按累计概率动态选。

注意力集中就少选，分散就多选。

更贴合实际，但一直难进生产系统。

有两个系统层面的拦路虎。

第一，算分太贵。

top-p 要算全部 token 的真实分数。

才能知道累计到哪里够数。

算分的代价比省下的带宽还大。

第二，显存用量不定。

vLLM 的调度器要提前分好块。

top-p 选多少块，跑起来才知道。

提前分多了浪费，分少了不够。

这篇把两个拦路虎一起解决了。

完整接进了 vLLM。

核心方法

  • 预填和解码分开跑，放在两张卡上。
  • 16K 平均长度下，解码占总时间约 78%。
  • 另外留一份 INT4 的 key 缓存副本。
  • 只给稀疏分析器算分用。
  • 是 FP16 主缓存的八分之一大小。
  • 预填完第一词后，用 NCCL 异步传给解码引擎。
  • 算分用两个新核。
  • INT4 GEMV 核先给每个块打分。
  • 直方图 top-p 核再一遍选出块。
  • 以前要多轮二分搜，现在一遍搞定。
  • 选块和算注意力分两条流并行。
  • 选块流永远超前一层。
  • 用上一层的隐藏状态猜下一层要选什么。
  • 相邻层隐藏状态余弦相似度 0.87 到 0.951。
  • 猜得准，就不用等。
  • 块分配拆成两半。
  • 调度器只管新生成的词和元数据缓存。
  • 执行器管每步临时抓来的稀疏块。
  • 每步结束时两边同步一次。
  • 执行器没空位了，对应请求先停住。
  • 批量配置不用改。
  • 预填完还做一次 token 重排。
  • 按预填时每个 token 被看的次数排。
  • 被看得多的 token 挪到前面的块里。
  • 分段排，段内还按原来顺序。
  • 位置信息已经在 key 里了，重排不丢位置。

关键数据

  • 选块比同类方法快 1.17 到 1.8 倍。
  • 8K 长度、批量 64 时最快到 1.8 倍。
  • 64K 长度时是 1.17 到 1.43 倍。
  • 选块召回率不低于 97%。
  • 对照是 FP16 精确 top-p。
  • 覆盖的注意力质量还略高一点。
  • 同等显存下，批量最多开到 8 倍大。
  • Llama-3.1-8B 上，稠密版批量 4 就爆显存。
  • DisSparse 能开到 32。
  • 峰值吞吐是稠密版的 2 倍。
  • Phi-3-mini 上，稠密版批量 2 就爆显存。
  • DisSparse 能开到 8。
  • 峰值吞吐是稠密版的 2.5 倍。
  • token 重排让关键块数少 7.2% 到 14.1%。
  • LongChat-7B 上最多，少了 14.1%。
  • LongBench 上精度基本没掉。
  • Llama-3.1-8B 在稠密版上下 0.5% 以内。
  • LongChat-7B 反而比稠密版高 4.7%。
  • 只用了 170 个 token 的预算。
  • 固定 top-k 在这上面翻车了。
  • GSM8K 上 Quest-128 只拿 0.40 分。
  • 稠密版是 0.78 分。
  • DisSparse 拿 0.779 分，基本打平。
  • 检索任务 RULER 上离满分注意力不到 0.8 分。
  • 单针检索两边都是满分。
  • 小批量时有个短板。
  • 稠密版每词耗时快约 1.5 倍。
  • 原因是双流管线接不上 CUDA Graph。
  • 作者说这是工程问题，不是原理问题。

关键图表

图 1：双流管线的分工。左边 Stream 0 是计算流，一层一层跑注意力和 MLP。右边 Stream 1 是选择流，永远超前一层。先分析下一层要哪些块，再提前把块取回来。两条流并行，选块的耗时藏在算力后面。选下一层用的查询，来自上一层的隐藏状态。

图 2：vLLM 里新增的两块。调度器那边管新生成的词和 INT4 元数据缓存。执行器那边多了一个模型块分配器，管每步临时抓来的稀疏块。两边每步同步一次，调度器还管生命周期：释放内存和前缀缓存。

图 3：稀疏分析器的耗时对比。横轴是批量 1 到 64，四张小图是 8K、16K、32K、64K 四种长度。紫色柱子是 DisSparse，斜纹柱子是 Quest 加 Twilight。柱子越矮越好，柱子上的数字是加速比。8K 长度、批量 64 时到 1.8 倍。64K 时降到 1.17 到 1.43 倍。

图 4：端到端三项指标对批量。上面是 Llama-3.1-8B，下面是 Phi-3-mini。左中右分别是吞吐、每词耗时、端到端延迟。蓝色虚线是稠密 vLLM，红色实线是 DisSparse。粉色区域写着稠密版爆显存，红色区域只有 DisSparse 能跑。Llama-3.1-8B 在批量 4、Phi-3-mini 在批量 2 就爆了。

跟研究方向的关联

  • 稀疏注意力是 KV 缓存优化的另一条路。
  • 跟前缀缓存、PD 解耦拼起来才是完整账。
  • top-p 比 top-k 更贴合真实注意力分布。
  • 固定预算的坑，这篇用 GSM8K 翻车实锤了。
  • INT4 元数据缓存是便宜的打分办法。
  • 只花八分之一显存，召回率还有 97%。
  • 双流超前一层是藏延迟的通用套路。
  • 相邻层相似度 0.87 以上才敢这么猜。
  • 混合分配是调度器和执行器分工的新样子。
  • PD 解耦评估里，解码节点的块分配要单列。
  • 批量开到 8 倍，吞吐账要按批量分段报。
  • 小批量短板要记下来。
  • CUDA Graph 接不上，双流方案都有这笔账。
  • IndexerStage 是同一批的另一篇。
  • 那篇把 DeepSeek 稀疏注意力的索引态搬出显存。
  • 两篇对照看，稀疏注意力的系统账就全了。

术语表

  • 稀疏注意力：只读关键 token 的注意力，省带宽。
  • top-k：固定挑 k 个块，不管分布什么样。
  • top-p：按累计概率动态挑，集中少选、分散多选。
  • KV 缓存：解码时留的草稿纸，存 key 和 value。
  • 元数据缓存：INT4 的 key 副本，只用来算分。
  • 直方图核：一遍数出分布，再定阈值的选块核。
  • 双流管线：计算流和选择流并行，选块藏在算力后。
  • token 重排：把被看多的 token 挪到前面的块里。
  • 召回率：选中的关键块占真实关键块的比例。
  • CUDA Graph：把一串核打包一次下发，省启动开销。
  • TPOT：每输出一个词的平均耗时。
  • RULER：长上下文检索能力的评测集。
  • LongBench：长上下文理解能力的评测集。
