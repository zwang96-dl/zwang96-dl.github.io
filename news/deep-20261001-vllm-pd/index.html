vLLM 官方 P/D 解耦实战手册：什么时候拆、怎么搭、坑在哪

  • 原文：vLLM 官方博客《Taking vLLM Apart: A Practical Guide to Disaggregated Serving》
  • 发布时间：2026-09-29（19 分钟长文）
  • 链接：https://vllm.ai/blog/2026-09-29-disaggregated-serving-guide
  • 适用版本：vLLM v0.30.0 及以后

人话解读

  • 一个 vllm serve 进程同时干三份互不相干的活。
  • prefill 读整个 prompt，一次性吃完，算力密集，决定首字延迟。
  • decode 一个 token 一个 token 吐。
  • 它卡在显存带宽，决定字间延迟。
  • 第三份是 CPU 杂活：切词、拼模板、解析工具调用。
  • 一个长 prompt 进来，几十个正在吐字的请求全被卡住。
  • 因为 prefill 和 decode 在抢同一张卡。
  • 解耦就是分工：prefill 一批卡，decode 一批卡。
  • 中间传 KV cache（草稿纸：每个 token 的注意力键值）。
  • CPU 杂活搬到无 GPU 的前端机器，引擎只认 token。

核心方法

  • prefill 和 decode 跑成两个实例。
  • 中间用 KV connector 传草稿纸。
  • connector 是 vLLM 里搬 KV 的插件，上游已有十几种。
  • NIXL 是英伟达的高速传输库，走 RDMA。
  • 还有 LMCache、Mooncake、FlexKV。
  • 还有 AMD 的 MoRI-IO，MultiConnector 可以串联多个。
  • 跑起来要三个进程：prefiller、decoder、proxy。
  • prefill 算完 KV 攒着，proxy 告诉 decode 去哪取。
  • proxy 只是示例，生产环境用 llm-d 或 Dynamo。
  • 聊天多轮场景开双向传输：decode 手里的新 KV 传回 prefill。
  • 下一轮 prefill 只算新增 token，不用全重算。
  • 前端不用 GPU：/render 把请求翻成 token ID。
  • /derender 把输出 token ID 翻回标准响应格式。
  • 模板和解析器都搬走，引擎变成纯 token 进、token 出。
  • 多模态 encoder 解耦：图片解码和预处理放 render 层。
  • 处理完的 tensor 给 encoder。
  • 只把 metadata 给 prefill。
  • MoE 还有 AFD 插件：attention 和 FFN 也能拆开。

关键数据

  • 实验环境：两张 L40S（PCIe、无 NVLink）、Qwen2.5-7B。
  • 8k token prompt、输出 256 token、泊松到达。
  • 负载到 0.4 req/s，collocated 的 p99 翻了 7 倍。
  • 从 23 ms 跳到 169 ms。
  • 同一负载下 P/D 的 p99 只有 29 ms，全程压在 25–52 ms。
  • 2 req/s 时 collocated p99 冲到 263 ms。
  • P/D 全程压在 52 ms 以内。
  • 1 req/s 内中位数两边差不多，都是 21–24 ms。
  • 划重点：解耦救的是尾延迟，不是中位数。
  • AMD MoRI-IO 实测：单节点 8 张 MI300X。
  • 模型是 Qwen3-235B-A22B-FP8。
  • 8 req/s 下，73 个请求同时达标。
  • 目标是 1 s 首字加 50 ms 字间。
  • collocated 只有 30 个达标。
  • goodput 差了约 2.4 倍。
  • llm-d 集群实测：16×H200 上 gpt-oss-120b。
  • 平均端到端延迟降 59%，P95 降 67%。
  • 反例：没 RDMA 的机器，KV 传了 1.3 秒。
  • 那是 8k prompt 的 470 MB。
  • P/D 中位首字延迟 2.2 s，collocated 只有 0.7 s。
  • 首字目标全挂：每个首字都要为传输买单。

决策表：什么时候拆、什么时候别拆

  • ITL p99 达不到 SLO：拆，这是主场景。
  • 长 prompt 高并发：拆，前提是 KV 传得快。
  • 聊天或 agent 多轮：拆，加双向传输，配共享 KV。
  • 模板切词占了 GPU 机器的 CPU：把 render 层拆出去。
  • 首字延迟是硬约束：别拆，或者先实测。
  • KV 传得慢：先修传输，或者别拆。
  • 流量小、突发、不敏感：别拆。
  • 先看 decode 的 KV Transfer metrics 那行。
  • Avg xfer time 几百毫秒的话，先修这个再谈别的。

跟你研究方向的关联

  • 你正在评估 SGLang 的 P/D 解耦，这篇是 vLLM 官方实战手册。
  • 对照着看：两家拆分的维度、传输方案、调参旋钮直接可比。
  • 核心结论先记住：解耦买的是 goodput，不是峰值吞吐。
  • 同样的卡，不设延迟目标时吞吐不一定涨。
  • 你的 autotuner 评估 P/D 时，目标函数该用达标率。
  • 不要只看 tokens/s，否则会得出"拆了没用"的错误结论。
  • 多模态 encoder 解耦跟你的 encoder 侧优化直接相关。
  • 预处理搬到 CPU render 层，prefill 只收 metadata。
  • 两个调参旋钮记一下：kv_lease_duration 默认 30 秒。
  • 它是 prefill 攒着 KV 等 decode 来取的超时，高负载下要调。
  • kv_load_failure_policy 管传输失败怎么办。
  • fail 直接报错，recompute 让 decode 自己重算。
  • 重算慢，但请求能活下来。

坑：推理模型开双向传输会出静默错误

  • decode 的 KV 里含着它自己生成的思考链。
  • 下一轮如果模板把思考链丢了，prompt 和 KV 就对不上了。
  • 结果不是变慢，是直接算错，而且 vLLM 目前不检查。
  • 官方 issue #43094 挂着，开双向传输前先对齐 chat 模板。

术语表

  • P/D 解耦：prefill 和 decode 分卡跑，各干各的。
  • KV cache：草稿纸，每 token 的注意力键值。
  • TTFT：首字延迟，prefill 阶段决定。
  • ITL：字间延迟，decode 阶段决定。
  • goodput：达标吞吐，延迟目标内能扛的请求速率。
  • p99：99% 的请求都比它快，尾延迟的看板。
  • NIXL：英伟达的 KV 高速传输库，走 RDMA。
  • connector：vLLM 里搬 KV 的插件，十几种。
  • RDMA：网卡直读内存，不经过 CPU 的高速传输。
  • llm-d / Dynamo：生产级 P/D 调度框架。
  • render / derender：跑在 CPU 上的前端。
  • 它是请求和 token ID 的翻译官。
