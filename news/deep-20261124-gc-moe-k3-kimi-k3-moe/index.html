GC-MoE K3：Kimi K3 的 MoE 解码，一张图里跑完

  • 原文：Yong Li、Haoyu Wang、Kan Liu、Tao Lan，阿里巴巴
  • 文章：GC-MoE K3: A Green-Context Role Graph for Latent Mixture-of-Experts Decode
  • 提交时间：2026-11-23
  • 原文链接：https://arxiv.org/abs/2611.30542
  • 说明：数字全是作者自报；GB200 单层重放，合成输入；vLLM 那组是历史数据，不是同轮重测

一句话

Kimi K3 整层前馈塞进一张 CUDA 图。算和传各占一半 GPU。比 SGLang 同轮快 1.13 倍。

人话解读

Kimi K3 是个潜空间 MoE 模型。MoE 就是专家混合，每个 token 只找少数专家算。K3 有 896 个路由专家。每个 token 挑 16 个。再加 2 个共享专家，人人都要过一遍。

以前的 GC-MoE 只管专家那一段。这篇把边界扩到整层前馈。从读题后的输入开始。到归一化、投影、加共享结果，全包进来。

Green Context 是 CUDA 的切分功能。一块 GPU 切成两个区。一个区算数。一个区传数据。两边同时跑，互不抢卡。

整个计算排成一张 CUDA Graph。CUDA Graph 就是把一串核函数录好，一次下发、反复重放。省掉了每次下发的开销。

框架那两条路是分段跑的。SGLang 先调 Mega MoE 算路由专家。共享分支放另一条流上。vLLM 更串一些。共享分支在主流程里后算。GC 把两条分支都塞进同一张图里。分发还没传完，共享分支已经开始算了。

通信分区干完活也别闲着。条件角色 Routed Assist 会接手一部分路由计算。等于传数据的核，顺手帮着算了点活。

图 1：GC-MoE K3 的角色图。上面是计算分区。下面是通信分区。Role 1 到 Role 5 是基本角色。Role 6 和 Role 7 是条件角色。实线是图依赖。虚线是数据就绪信号。橙色虚线是有条件才走的边。

核心方法

方法分五步，外加两个条件角色。

第一步：Front 合并前投影。门控权重和下投影权重拼成一个矩阵。一次算完。门控列存成 FP32 的分数。潜空间列直接量化成 FP8。省掉了一次单独的 staging。

第二步：Router 选专家。每个 token 一组线程。扫一遍分数。加上专家修正偏置。取 sigmoid 后最高的 16 个。平局取编号小的。权重归一化后写好。

第三步：Dispatch 发 token。源 rank 数好自己的路由。把 token 槽位写进目标 rank 的区间。目标 rank 按专家分块。块满了就通知计算分区开工。不用等全部传完。

第四步：Compute 一起算。共享分支和路由分支共用一个任务调度。共享先算 W1，再算 W2。路由等输入块就绪了再算。两边抢同一个任务队列。

第五步：Finalize 收尾。等各 rank 的专家结果回来。按 token 加权求和。再归一化、投影、加共享结果。残差前缀也在这里加进来。

条件角色一：Routed Assist。通信分区传完数据后，抢路由任务来算。不抢共享任务。环形缓冲快绕回时不启用。

条件角色二：Reduce。输出投影拆成两半算时，负责把两份结果加起来。

图 2：GB200 上 24 组配置的实测。上图是解码延迟。绿线是 GC-MoE K3，全程最低。下图是加速比。紫色方块对 SGLang。橙色三角对 vLLM。虚线是 1 倍。注意 vLLM 那组是历史数据。

关键数据

  • 硬件是 GB200，设备名 L20A。
  • 专家并行分三档：EP8、EP16、EP32。
  • 每档 8 个 token 数：每 rank 1 到 128 个 token。
  • 一共 24 组配置，GC 全赢。
  • 对 SGLang 是同轮实测，PyTorch 2.13。
  • 平均加速 1.1324 倍。
  • EP8 平均 1.1102 倍，EP16 平均 1.1354 倍。
  • EP32 平均 1.1514 倍，峰值 1.2222 倍。
  • 峰值在 EP32、每 rank 2 个 token：128.456 对 156.994 微秒。
  • 大批量时优势收窄：EP32、128 个 token 只剩 1.0413 倍。
  • 对 vLLM 是历史数据，PyTorch 2.14。
  • 平均加速 1.3651 倍，峰值 1.5404 倍。
  • 峰值在 EP32、每 rank 1 个 token。
  • 数值验证过了 142 个用例、2936 次 rank 检查。
  • 最差余弦相似度 0.999995410。
  • 最大相对 L2 误差 0.003025480。
  • 计时只含单层算子重放，不含注意力。
  • 请求处理、权重变换、首次建图都不在计时里。

跟研究方向的关联

跟 PD 解耦评估直接对口。角色图就是现成的对照。

第一，通信和计算分区可以抄进清单。Dispatch 占 8 到 16 个 SM。其余全给计算。读题和解码拆开后，传 KV 那一侧也可以这样分。

第二，延迟账要按 token 数分段报。小批量优势最大。大批量只剩 1.04 倍。只报平均会掩盖这个收窄。

第三，vLLM 对比是历史数据。抄 1.3651 这个数时要标出来。两边软件环境不一样。

第四，单层重放不是端到端 serving。想拿它当 serving 结论，还得另测整条链路。

第五，共享专家那条支路值得单列。框架是把它放图外的。GC 是把它塞进图里的。这就是 1.13 倍的主要来源。

第六，K3 的结构本身就是混合模型。潜空间路由加共享专家。跟 GLM-5.3-Flash、Qwen3.5 同类。评估清单里的模型可以加 K3 一档。

术语表

  • Green Context：CUDA 的分区功能，把一块 GPU 切成两个区，各跑各的核。
  • CUDA Graph：把一串核函数录下来，一次下发、反复重放，省去逐个下发的开销。
  • EP：专家并行，路由专家的权重分到多个 rank 上。
  • Mega MoE：DeepGEMM 里把路由交换和专家计算合在一起的调用。
  • DeepGEMM：英伟达的 FP8 分组矩阵乘法库，MoE 推理常用。
  • SiTU：K3 用的门控激活函数，tanh 和 sigmoid 的组合。
  • split-K：把一次矩阵乘法沿 K 维切成几份，并行算完再加起来。
  • FP4 / FP8：4 位和 8 位浮点数，权重和激活的压缩格式。
  • rank：并行组里的一个位置，通常对应一张卡或一个进程。
  • Top16：每个 token 从 896 个专家里挑 16 个。
  • 潜空间 MoE：先把 token 投到更窄的空间，再进专家算，省算力。
  • 共享专家：所有 token 都要过的专家，不参与路由挑选。
  • TMA：张量内存加速器，负责把数据搬进共享内存。
  • TMEM：张量内存，SM 内的高速缓存，存累加结果。
