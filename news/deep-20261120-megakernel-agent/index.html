每个模型一个 Megakernel：让 Agent 给每个模型写专属解码核

  • 作者：Anthropic 团队，用 Claude Opus 5.5 和 Fable 5.2 跑框架
  • 原文：Anthropic 工程博客《A Megakernel per Model》，2026-11-19 发布
  • 原文链接：https://dangxingyu.github.io/megakernel（全文镜像）
  • 代码与复现工具：https://github.com/dangxingyu/megakernel-zoo
  • 深读：2026-11-19 17点版（Anthropic 刚发，专治解码尾部卡顿）

人话解读

通用引擎像中央厨房。

一把菜刀切所有菜，什么模型都能跑。

代价是每步要发几百次 kernel launch。

CPU 每发一次，GPU 就要等一回。

Megakernel 反过来，只伺候一个模型。

整个解码循环写进一个 GPU 程序。

中间一次都不回 host。

Agent 负责写这个程序，人只负责出题和判分。

结果是单序列解码比最快的通用引擎快 1.13 到 1.77 倍。

生产流量下，几乎所有请求都达标。

SGLang 只有八成多，差距主要在长 prompt 造成的卡顿。

但这套打法适用面很窄。

最多 8 个并发，上下文最多 2048 个 token。

高并发下还是 SGLang 更能打。

核心方法

  • 一个 kernel 跑完整步：注意力、矩阵乘、归一化全在里面。
  • token 循环也在 kernel 里，grid barrier 分隔各阶段。
  • 权重按 tensor core 的读取顺序排布。
  • 当前层算着，下一层权重已经预取好了。
  • 空闲的 thread block 提前进下一阶段。
  • 中间结果不经过显存往返。
  • Track A：数据流不动，只改计算组织方式。
  • Track B：函数精确不变，存储方式可以换。
  • 比如权重从 BF16 无损压成 12 位。
  • 12 位编码只存符号、4 位指数码、7 位尾数。
  • 每行先乘一个精确的 2 的幂。
  • 寄存器里解码，再送进 tensor core。
  • 每 token 权重流量少四分之一。
  • LM head 用低精度 sketch 先筛候选。
  • 只有可能当 argmax 的行才用精确 head 重算。
  • 第 0 层按 token id 预先算好查找表。
  • 验证框架比 kernel 本身更重要。
  • Agent 改不了 test suite，通过了才计时。
  • Reference 用 FP64 算，容差按 BF16 实现标定。
  • 隐藏测试集 agent 看不到，只报通过或失败。
  • 计时跑的 logits 事后要和 reference 对上。
  • Batch 倒序重跑，logits 必须逐位相同。
  • 发布前独立 agent 审源码，跑自己的实验复现分数。

关键数据

  • 8 个模型，8B 到 594B 参数，H100 和 B200 上测。
  • 64 token prompt，生成 1024 个 token，贪心解码。
  • Batch 1 时 Track A 比最快通用引擎快 1.13–1.77 倍。
  • Track B 最高到 2.05 倍。
  • Batch 8 时加速比收窄，North Mini Code 只剩 1.02 倍。
  • Qwen3-8B 上 H100，单 token 5.13 毫秒。
  • 读 15.1GB 权重的理论下限是 4.52 毫秒。
  • 也就是达到了带宽上限的 88%。
  • 生产 trace 用 Mooncake 的工具调用 trace。
  • 平均 prompt 约 9000 个 token。
  • Inkling-2-Small 在 4 张 B200 上。
  • 每秒 1、2、4 个请求时 SLO 达成率 100%。
  • 每秒 8 个请求时 99.2%，SGLang 是 82–85%。
  • 最长卡顿 0.08–0.15 秒，SGLang 是 2.3–4.4 秒。
  • Qwen3-8B 单张 H100 上，达成率 95–97%。
  • 同条件下 SGLang 和 vLLM 是 68–75%。
  • 但 32 并发时 SGLang 每秒 3338 个 token。
  • Steady-decode 引擎只有 1427 个。
  • 32K prompt 的首 token，serving 引擎 0.70 秒。
  • SGLang 是 0.41 秒，megakernel 反而更慢。
  • 19 个 run，458 个 agent-hour，675 次提交。
  • Qwen3-8B 约 3 小时就超过通用引擎。
  • Inkling-2-Small 和 Qwen3.8-27B 用了 7 和 19 小时。

局限与提醒

  • 数字全是作者自报，单节点、两到三轮。
  • Steady-decode 引擎最多 8 个序列。
  • 上下文上限 2048 个 token。
  • Prompt 每个 pass 只读一个 token。
  • 采样在 kernel 外面做，慢 1–11%。
  • 高并发和长 prompt 下 SGLang 仍占优。
  • Serving 引擎的首 token p99 是 3.4–4.6 秒。
  • SGLang 是 2.0–2.2 秒，尾部反而更差。
  • Token 间隔中位数 28–60 毫秒，SGLang 是 9–18 毫秒。
  • 审计发现 evaluator 放过的问题，原文都列出来了。
  • 比如 Qwen3.8-27B 有两个计时 prompt 陷入重复循环。
  • Draft 能预测重复，分数虚高，改报自然文本的数。
  • 三个标逐位相同的 track B 引擎其实不是。
  • 已重跑或改标注，靠逐位比对拦住。
  • Qwen3-8B 高负载下 17 次有 12 次 token 不一致。
  • 正在排查，根因还没定。

跟研究方向的关联

  • 解码尾部卡顿是 PD 评估的老对手。
  • 这篇证明卡顿主要来自 prefill 插队。
  • 读题和生成分开跑，卡顿能压到 0.1 秒级。
  • 跟 PD 解耦是同一条思路，换了实现。
  • Megakernel 是把调度也搬进 GPU 里。
  • 12 位无损权重值得抄进量化清单。
  • 同一行权重只跨几个 binade，冗余是真的。
  • 效果按模型分档，已压缩的模型收益很小。
  • 验证框架的设计可以直接借鉴。
  • 自动调参也要防 agent 钻 evaluator 的空子。
  • 隐藏测试集加独立审计，两道锁缺一不可。
  • 但别照搬结论：高并发仍是通用引擎的地盘。
  • 评估里单序列和 32 并发要分开报。

术语表

  • Megakernel：一个 GPU 程序跑完整个解码循环。
  • Steady decoding：一次 launch 跑很多个 token 的解码。
  • Track A：数据流不变，只改计算组织方式。
  • Track B：函数精确不变，存储方式可以换。
  • Grid barrier：kernel 内各阶段之间的同步点。
  • MBU：显存带宽利用率，实测字节除以峰值带宽。
  • DFloat11：一种无损 12 位权重格式的同类做法。
  • Head sketch：LM head 的低精度副本，先筛候选。
  • SLO 达成率：首 token 和词间隔都达标的请求占比。
  • Argmax：概率最大的那个 token。
  • Binade：相邻两个 2 的幂之间的区间。
