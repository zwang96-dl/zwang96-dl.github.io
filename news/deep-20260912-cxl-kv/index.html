CXL：给 KV 缓存修了个"跨节点共享网盘"

原文链接：arXiv:2609.10790（2026-09-11；PDF：https://arxiv.org/pdf/2609.10790v1）

作者：Hongjian Fan、Kevin Zhang、David Habinsky、Sean Dykstra（Seagate 相关团队）

人话解读

一句话：以前各节点的 KV 缓存（模型的"草稿纸"）都是"各玩各的私家抽屉"。

这篇论文用 CXL（一种跨机器共享的高速内存技术）造了个"公共网盘"。

两台机器的推理实例，都能直接从同一块内存读 KV 缓存。

请求被负载均衡甩到另一台机器时，也不用重新做 prefill（"读题"阶段）。

划重点：这是从硬件层解决"跨节点 KV 缓存共享"问题。

作者自己强调：这只是可行性研究，不是正式性能评测。

所以后面的数字，你得按"小规模验证"来读，别当产品级承诺。

核心方法

方案 = K8s 原生驱动 + vLLM 共享内存连接器 + CXL 内存盒。

  • DRA（K8s 的动态资源分配机制）驱动：把 CXL 内存变成集群可调度资源。
  • 工作负载像申请 GPU 一样，申请一块可共享的 CXL 内存。
  • 申请单叫 ResourceClaim（要内存的申请单）。
  • 声明要多大、几台机器共享、QoS 等级。
  • 这些声明写在 annotation 里，调度器按设备类挑一整块内存板。
  • 调度器挑的是"板"，不是按字节算容量，这点跟直觉不太一样。
  • 被选中的节点上，驱动按需"组装"（compose）出内存区域。
  • 组装好的区域在各节点挂载成 DAX 设备（绕过页缓存直访内存的设备）。
  • 两台机器各看到一个 /dev/dax0.1，背后是同一块物理内存。
  • 同一个 CDI（容器设备接口）名字注入到各节点 pod，路径完全统一。
  • 数据面没有传输协议，直接用普通内存读写指令（load/store）。
  • 指令走 PCIe 电气层直达 CXL 内存，不经过网络协议栈。
  • 跟 RDMA（一种要走网络协议的内存访问技术）那种"先封包再解包"完全不同。
  • vLLM 侧用"共享内存连接器"。
  • 它对接 OffloadingConnector（vLLM 的分层存储接口）。
  • 读、写 KV 缓存块都走这块共享内存，vLLM 本体不用大改。
  • 元数据目录直接嵌在共享内存里，不需要外部元数据服务。
  • 类比：网盘自带目录索引，不用再搭个数据库记文件在哪。
  • 目录分两块：魔数头 + 配置 JSON + slot 位图。
  • 再加 key 数组 + 每槽 CRC32。
  • CRC32（一种数据校验码）用来抓物理损坏，key 数组用来防哈希碰撞误报。
  • 命中条件三件套：位图置位、key 对上、CRC 校验通过，缺一不可。
  • 数据路径是"主机中转"式，不是零拷贝，这是个诚实的设计选择。
  • 写分两步：GPU 显存 → cudaMemcpy 到 CPU 中转区。
  • 再 memcpy 进 CXL 区域。
  • 读：CXL → CPU 中转区 → cudaMemcpy 回 GPU，反向走一遍。
  • 第一个映射的进程负责格式化区域，后来的进程直接挂载，无需协调者。
  • 作者特意声明：两个副本都跑完整引擎，这是"内存解耦"。
  • 千万别跟 prefill/decode 解耦搞混，那是另一回事。

关键数据

实验环境：两节点 + 512 GiB CXL 内存盒。模型 Qwen2.5-7B-Instruct。

  • 图 1：CXL 共享内存读延迟 461–507 ns，带宽 27 GB/s。
  • 比本机 DRAM（内存）慢约 4.5 倍，但它是唯一能跨节点共享的低延迟方案。
  • 跟 RoCEv2（一种走以太网的远程内存技术）网卡方案比。
  • 延迟低 2.4 倍，带宽多 2.2 倍。
  • 跨节点复用时：GPU 前缀缓存、CPU 内存卸载全部退化成全量重算。
  • 因为缓存都在另一台机器上，等于压根没有缓存。
  • CXL 共享层：TTFT（首 token 延迟）2K 前缀降 5.5 倍。
  • 8K 前缀降 12.7 倍。
  • 16K 前缀降 21.8 倍，32K 前缀降 36.6 倍，前缀越长收益越大。
  • 外部命中率 95.4%–99.5%，前缀越长命中率越高。
  • "共享损耗"只有 1%–4%，跨节点读跟同节点读几乎一样快。
  • 说白了：网盘放自己桌上还是隔壁桌上，拿文件速度差不多。
  • 本机复用有溢价：走 CXL 比直接走本机缓存慢最多 1.7 倍。
  • 但换来"跨节点不重算"，否则代价是 6–63 倍的重算惩罚。
  • 读延迟拟合公式：TTFT ≈ 104ms + 每 token 6.90μs。
  • 复用的盈亏平衡点在几百个 token，太短的前缀不值得走共享层。
  • 首次触碰成本：每个进程第一次读 CXL 要付约 420ms。
  • 来自 DAX 缺页 + 中转区初始化，付一次就好，后面不再交。
  • 正确性：约 1.2 TB 跨节点写入，CRC32 零不匹配。
  • 控制实验：12298 次查不存在的 key，零误报。
  • 小插曲：10 次相同提示跑两台机器，6 次输出字节完全相同。
  • 4 次分叉是因为 bf16（一种半精度浮点格式）舍入差异，最多差 1 ULP。
  • ULP（浮点最小精度单位）是衡量舍入误差的最小刻度。
  • 作者说：CRC 防的是"数据损坏"，不防"合理舍入差异"，实际影响可忽略。

跟你的研究方向的关联

划重点：这是过去两天三条线的"第三块拼图"，同一个问题的三种解法。

  • 路由层（午间版）：AWS 的前缀感知路由，把相同前缀请求路由到同一台机器。
  • 存储层（晚间版）：vLLM 官方博客的分级 KV 仓库。
  • KV 下沉到低层存储，实现跨节点共享。
  • 硬件层（这篇）：绕开路由和存储，直接让两台机器"看到同一块内存"。
  • 三层对比：路由层最便宜，改负载均衡器就行，但请求分布不均就吃亏。
  • 存储层最通用，但多一次存储 IO，延迟天花板摆在那。
  • 硬件层延迟最低（纳秒级内存语义），但要买 CXL 硬件、改 K8s 驱动。
  • 跟你评估的 SGLang P/D 解耦（"读题答题"分开跑）：两者正交，可以叠加。
  • P/D 解耦解决"算力分工"，这篇解决"缓存共享"，不打架。
  • 想象一下：P/D 解耦的 prefill 池挂上 CXL 共享层。
  • 命中率还能再往上走。
  • 多模态视角：多模态请求的系统提示词（图像 token + 指令）通常很长。
  • 前缀越长这篇收益越大（32K 时 36.6 倍），多模态场景想象空间不小。
  • 务实提醒：这篇是两节点 + 7B 小模型的验证，别直接外推到生产。
  • 调度器现在没有容量记账，两个申请可能撞到同一块空闲内存。
  • 多节点扩展、故障恢复都还没验证，作者自己都承认。

原图（配中文图注）

图 1 人话解读。横轴是读延迟，纵轴是读带宽，三个点是三种方案。本地 DRAM（内存）最快，但只能本机用（空心圆）。RoCEv2 网卡能共享，但走网络协议，延迟最高。CXL（蓝点）是实心圆里唯一能跨节点的，只比本机内存慢 4.5 倍左右。作者用这张图立论：CXL 是"又快又能共享"的那个甜点位。

图 2 人话解读。上：K8s 控制面。工作负载发 ResourceClaim（要 512GB、两台机器共享），调度器按设备类挑一块内存板。中：两台 worker 节点。claim 控制器选出"组装负责人"，通过 cfm-service 让内存盒切出一块区域。下：CXL 内存盒。同一块物理内存同时映射到两台机器，挂载成同名的 /dev/dax0.1。两个 vLLM 副本看到的路径一模一样，数据面走普通内存读写，不走网络协议。

图 6 人话解读。横轴是共享前缀长度，纵轴是复用请求的 TTFT（p50）。三条高线（T0 全量重算、T1 GPU 前缀缓存、T2 CPU 内存卸载）在跨节点场景下完全重合。因为缓存都在另一台机器上，等于没有缓存。蓝线（T4，CXL 共享层）独自分开，32K 前缀时快了 37 倍。换句话说：没有共享层，跨节点复用就是个伪命题。

术语表

  • CXL（一种跨机器共享的高速内存技术）：走 PCIe 的内存互联，多台主机可同时访问同一块物理内存。
  • DRA（K8s 的动态资源分配机制）：Kubernetes 里让 pod 申请 GPU 这类特殊设备的标准机制。
  • KV cache（模型的"草稿纸"）：推理时缓存的注意力键值，复用它可以跳过 prefill 重算。
  • prefill（"读题"阶段）：模型第一次处理全部输入 token 的计算密集阶段。
  • TTFT（首 token 延迟）：从请求发出去到第一个 token 出来的时间。
  • DAX（绕过页缓存直访内存的设备）：直接读写持久内存/设备内存，不经过操作系统页缓存。
  • CDI（容器设备接口）：K8s 里把宿主机设备注入容器的标准方式。
  • RoCEv2（一种走以太网的远程内存技术）：走网卡做内存直读，延迟比 CXL 高一个量级。
  • RDMA（一种要走网络协议的内存访问技术）：远程直接内存访问，数据要先封包再解包。
  • bf16（一种半精度浮点格式）：大模型常用的 16 位浮点数，精度比 fp32 低。
  • ULP（浮点最小精度单位）：衡量浮点舍入误差的最小刻度。
  • CRC32（一种数据校验码）：用来检测数据在传输/存储中是否损坏。
  • P/D 解耦（"读题答题"分开跑）：把 prefill 和 decode 拆到不同节点跑的分工流水线。
  • prefix caching（前缀缓存）：相同开头的请求复用已算好的 KV，跳过重复计算。
