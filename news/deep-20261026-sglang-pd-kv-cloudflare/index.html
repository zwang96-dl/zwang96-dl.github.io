SGLang PD 解耦 KV 串话：Cloudflare 协同披露精读

人话解读

  • Cloudflare 今天公开了一次串话事故。
  • 事故发生在 Workers AI 平台。
  • 受影响模型是 GLM-5.3。
  • 别人的回答里混进了你的内容。
  • 根源在 SGLang 的 PD 解耦路径。
  • PD 解耦就是分工流水线。
  • prefill 负责读题和算草稿。
  • decode 负责接着草稿写答案。
  • KV cache 就是那份草稿纸。
  • 草稿纸被读错，答案就串了。
  • 这篇正对你评估的方向。
  • 它给了一整套自查清单。

事故账本

  • 暴露窗口是 8 月 27 日到 9 月 9 日。
  • 一共 155 条回答受影响。
  • 受影响的都是超长提示。
  • 长度都超过 681280 个 token。
  • token 是模型计字的单位。
  • 没有发现有人故意利用它。
  • 9 月 8 日研究者报告了问题。
  • 报告人是 Knostic 的 Gadi Evron。
  • Cloudflare 次日就下线了模型。
  • 当晚修好配置又恢复了服务。
  • 今天是三方协同披露日。
  • 三方是 Cloudflare 和 SGLang 等。

核心方法：两个错叠在一起

  • 第一个错是配置对不上。
  • 上下文上限设成了 1048576。
  • prefill 的 KV 池只有 681280。
  • KV 池是放草稿纸的格子总数。
  • 池子装不下，却没人拦住。
  • 团队上线前其实知道这个差。
  • 他们只测了状态码和速度。
  • 他们没测回答内容对不对。
  • 第二个错在引擎拒绝路径。
  • 装不下的请求本该被拒绝。
  • 引擎把它换成一 token 占位。
  • 占位请求本该直接报错退出。
  • 单机模式下这条路是对的。
  • 解耦模式下它却被放行了。
  • 它只传了一页真的 KV。
  • decode 却预留了八页位置。
  • 其余七页还是上个用户的旧稿。
  • decode 照着旧稿继续生成。
  • 于是回答里混进别人的内容。
  • 而且返回的是 200 成功码。

图1 是 Cloudflare 的事故示意图。 它画了被拒请求穿过交接的全程。 重点看 decode 读了没写过的页。 那几页留着上一个用户的数据。

姊妹问题：中止竞态

  • SGLang 帖讲了更普遍的一类。
  • 请求中途断开也会串话。
  • 断开包括超时和传输故障。
  • KV 是用 RDMA 直传过去的。
  • RDMA 是绕过 CPU 的直抄。
  • 已发出的直抄没法撤回。
  • 旧实现一断开就释放格子。
  • 格子马上分给下一个请求。
  • 迟到的直抄正好落进新格子。
  • 新请求就读到了旧请求草稿。
  • 这类错被叫分布式释放后使用。
  • 它从 0.4 时代就潜伏着。

图2 是 SGLang 的竞态示意图。 请求 A 中止后格子被释放。 请求 B 拿到了同一批格子。 A 的迟到写入落进了 B 的草稿。

图3 画的是调度器下面的传输栈。 中止只能停还没发出的块。 已交给网卡的写入收不回来。 接收方 CPU 根本看不见写入。

修复：延迟释放

  • 修复思路叫延迟释放。
  • 英文是 deferred KV release。
  • 说白了就是先别急着腾格子。
  • decode 中止后先把格子扣住。
  • 它等 prefill 回一个确认。
  • 确认叫 ABORT_ACK 排空信号。
  • 所有一路都确认排空才释放。
  • 等不到确认就等到超时为止。
  • 默认超时是 30 秒兜底。
  • 建议把超时设到 60 到 120 秒。
  • 失败时只许延长扣住时间。
  • 绝不许因为失败提前释放。

图4 是延迟释放的流程图。 decode 先扣住 A 的全部格子。 prefill 排空后逐路回确认。 最后一个确认到齐才真正释放。

  • 还有一道更早的准入修复。
  • 被拒请求在排队口就退场。
  • 它不进 bootstrap 握手环节。
  • bootstrap 是交接前的对暗号。
  • 它也不分配任何 KV 格子。
  • 修复编号是 38935 和 36988。
  • 两条都已进正式版 0.5.22。
  • 另有可选的 KV 校验和。
  • 开关是 disaggregation-enable-kv-checksum。
  • 它在生成前核对草稿完整性。
  • 页级标签方案还在开发中。
  • Cloudflare 原型开销不到百分之一。

关键数据

  • 复现实验用了两张 H200。
  • 拓扑是两个 prefill 共一个 decode。
  • 受害请求先数对到 80。
  • 之后就吐出对方的提示原文。
  • 开启扣住后输出逐字恢复正常。
  • 中止压力测试一共跑了 132 次。
  • 没有崩溃，格子全都归还了。
  • 性能测试在两张 H100 上跑。
  • 一共 21 轮，1024 个请求。
  • 并发 256，每组重复七次。
  • 修复前后吞吐差在正负百分之二。
  • 置信区间全都跨过零点。
  • 也就是统计上看不出变慢。
  • H200 上另测默认开启的代价。
  • 结果是负百分之零点三八。
  • 同样不显著，可以放心开。

跟你研究方向的关联

  • 你正在评估 SGLang 的 PD 解耦。
  • 这篇就是解耦的安全底线课。
  • 第一课是先核池子和上限。
  • 每次改量化或并行都要重核。
  • 第二课是版本必须到 0.5.22。
  • 更早版本默认不带完整保护。
  • 第三课是盯延迟释放指标。
  • 指标名带 deferred_kv_release。
  • 健康时应几乎全走 drained。
  • drained 是确认排空后释放。
  • 若大量走超时就要查确认链。
  • 第四课是传输批次要设上限。
  • 800K 请求单次可传 30 GB。
  • 一次卡死就拖住一大批写入。
  • 这些都该进你的评估清单。

术语表

  • PD 解耦：prefill 和 decode 分开部署。
  • KV cache：注意力算过的草稿纸。
  • KV 池：能同时存放的草稿总量。
  • RDMA：绕过 CPU 的内存直传。
  • Mooncake：常用的 KV 传输引擎。
  • 延迟释放：确认写完才腾格子。
  • ABORT_ACK：prefill 的排空确认。
  • KV 校验和：交接时核对草稿指纹。
  • KV canary：埋点检测草稿被污染。
  • 分布式释放后使用：远程还在写就复用。
