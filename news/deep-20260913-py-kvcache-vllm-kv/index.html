py-kvcache：给 vLLM 外挂 NVMe SSD 做 KV 缓存，值不值？

原文：Building py-kvcache: A Performance Characterization of External KV Caching for vLLM with NVMe SSDs
作者：Joseph Kanichai、Tiziano De Matteis（阿姆斯特丹自由大学）、Animesh Trivedi（IBM Research Zurich）
发布时间：2026-09-10（arXiv 2609.11744）
原文：https://arxiv.org/abs/2609.11744
代码：https://github.com/atlarge-research/py-kvcache

一句话人话版

缓存命中不等于赚到。短 prompt 或卡太快时，重算比从盘里读还快。这篇论文回答了一个问题：什么时候该读缓存。答案是一条盈亏线。作者还做了个 vLLM 外挂，叫 py-kvcache。80k tokens 下，它从盘里读 KV 比 LMCache 快 2 倍。

它解决什么问题

先说 prefix caching（前缀缓存）。很多请求开头都一样，比如反复问同一份长文档。第一次 prefill 算出的 KV 可以存下来。后面请求直接复用，省掉重算。这就是前缀缓存。

GPU 显存不够大时，KV 得搬到 CPU 内存或 NVMe 盘上。这叫外部 KV 缓存。LMCache、vLLM 自带的 KV Offload 都在做这事。但它们有个共同毛病：只要缓存命中，就默认读缓存一定划算。真的是这样吗？论文说不是。

短 prompt 时，GPU 几毫秒就重算完了。你却要花几百毫秒从盘里读，这叫帮倒忙。卡越快，重算越便宜，读盘越不划算。所以缺的不是存取机制，而是"值不值得读"的判断。要做这个判断，得先把开销花在哪儿刻画清楚。

图 6 人话解读。三张热力图，对应三条缓存路径。从左到右：GPU 显存、llm-d 读盘、vLLM Offload 读内存。横轴是文档长度，纵轴是可复用前缀占比。绿色越深，从缓存读越划算。红色越深，重算越快。那条曲线就是盈亏线。线以上读缓存赢，线以下重算赢。注意两点。第一，短文档的盈亏线高得吓人。8k tokens 要 77.8% 的前缀复用才回本。第二，文档越长线越往下掉。80k tokens 时只要 7.8% 复用就划算。因为 prefill 是平方级变贵，读盘只是线性变贵。长上下文天然偏向读缓存。

核心方法：四个设计原则

论文先花大力气做刻画，结论是缓存性能不只看盘带宽，还看三件事。

第一是传输粒度。llm-d 给每个小 chunk 单独发一次拷贝和 I/O。小块太多，启动开销吃掉带宽。第二是中间内存占用。不加限制地用 CPU 内存做中转，会跟别的东西抢资源。第三是传输什么时候进调度。请求被调度了才开始读盘，读盘就躺在 TTFT 的关键路径上。

基于这三点，他们做了 py-kvcache。它是 vLLM KV Offload 的一个连接器。四个设计原则如下。

  1. 用普通文件系统布局。KV 按哈希寻址存成文件。多个 vLLM 实例能共享同一份缓存。
  2. I/O 走大块直读。用 io_uring（Linux 异步 I/O 接口）加 direct I/O（绕过系统页缓存的直接读写）。不用一堆线程，几个大读就够了。
  3. 中间 CPU 内存有上限。有界共享 staging（中转区）。请求再大，中转内存也不爆。
  4. 不值得就别读。离线先测出每台机器、每个层级的盈亏点。线上查表，预测读比算贵就直接拒绝加载，让 vLLM 重算。

最妙的是调度器感知预取（preload）。请求还在排队等 GPU 时，就开始从盘里读它的 KV。等请求真正开始执行，盘已经读了一大半。读盘时间被藏进了排队等待里。

图 9 人话解读。左边是 vLLM 调度器，只管查缓存、做计划，不管搬数据。中间 Manager 坐在调度器这边。它做三件事。lookup 查缓存，prepare_load 准备加载，preload 预取。它还能看到接下来 N 个排队请求，提前读盘。右边是 worker 这边。Handler 接到计划。TransferCoordinator（传输协调器）把它拆成文件任务。IoReactor（单线程 I/O 反应器）用 io_uring 读写盘。数据先到 CPU staging pool（中转内存池）。最后经 swap_blocks 进 GPU。注意那条虚线。Manager 觉得不划算，就 declined load（拒绝加载）。vLLM 老老实实重算，不浪费一次读盘。

关键实验数据

测试配置：用 vLLM v0.22，模型是 Llama 3.2 3B。跑在 Snellius 节点，50 并发。纯盘那组关掉了 GPU 前缀缓存和盈亏门，专测盘路。

图 10 人话解读。左图是纯盘场景。蓝条开预取，橙条不开，绿条是 LMCache。81,920 tokens 时，LMCache 要 52.08 秒。py-kvcache 不开预取 34.82 秒，开了 26.08 秒。右图是盘加内存两层全开，还多了 vLLM 原生 Offload（绿条）。注意 1k tokens 那组，四个配置全挤在 0.5 秒内，顺序还反了。这正好印证盈亏线：太短了，读缓存就是不如重算。

数字总结：

  • 纯盘 80k tokens：不开预取，py-kvcache 比 LMCache 快约 1.5 倍。这是异步传输引擎的功劳。
  • 打开预取：总加速到 2.0–2.5 倍。预取单独贡献：40k tokens 时 1.66 倍，80k 时 1.34 倍。80k 时 CPU 到 GPU 的拷贝太大，盖掉了一部分预取收益。
  • 三层全开（GPU、CPU、盘）：10k、40k、80k 下比 LMCache 快 1.19、1.53、1.23 倍。跟 vLLM 原生 Offload 比，40k 和 80k 只差 1.10 倍和 1.04 倍，10k 时反而快 1.12 倍。纯 Python 写的连接器，追平了原生实现。
  • 真实负载 LongBench：比纯重算快 6.02–7.43 倍。比只用 GPU 前缀缓存快 2.02–2.12 倍。比 LMCache 快 2.77–3.64 倍。比原生 Offload 快 1.22–1.79 倍。
  • Bailian（阿里云）真实 trace 回放：弱卡（RTX 4000 Ada）上收益明显。但 H100 上平均请求长度掉到盈亏线以下，只用 GPU 显存就够了，外部缓存白搭。

论文的结论很诚实：外部 KV 缓存不是装上就赢，而是看配置下菜的准入决策。

跟你研究方向的关联

  • P/D 解耦的兄弟问题。你在评估 prefill/decode 解耦。这篇解决的是 prefill 内部的"算还是读"。两者都是把 TTFT 拆开看，方法论可以直接借：先画盈亏线，再决定架构。
  • 盈亏思维通用。任何缓存优化，先问"命中就一定赢吗"。P/D 解耦跨节点传 KV 也有类似问题：短请求上，传输开销可能不如本地重算。
  • 预取思路可迁移。请求排队时提前读盘，等于把 I/O 藏进等待。多模态场景里，ViT 编码时提前 prefetch 文本 KV，异曲同工。
  • 弱卡场景。你的 4090 重算速度介于两者之间。做长文档 RAG 时，可以按这篇的方法，在自己机器上标定一条盈亏线。
  • break-even gate 是现成设计。离线标定、线上查表拒绝。这个模式简单有效，值得抄。

术语表

  • prefix caching（前缀缓存）：复用之前算过的 KV，开头相同的请求不用重算。
  • KV cache：attention 算出的 key 和 value 存下来，像"草稿纸"，decode 时反复查。
  • TTFT（time to first token）：首 token 延迟，用户看到第一个字要等多久。
  • LMCache：开源跨实例 KV 缓存系统，支持 CPU、盘、远端存储。
  • KV Offload：vLLM 自带的外部缓存机制，把 KV 搬到 CPU 或盘。
  • llm-d：Kubernetes 原生的分布式推理项目，它的盘 KV 连接器被用作对照。
  • io_uring：Linux 的高性能异步 I/O 接口，一个线程就能发很多并行读写。
  • direct I/O：绕过操作系统页缓存的读写，性能可预测，不怕缓存污染。
  • staging pool（中转池）：盘和 GPU 之间的 CPU 内存缓冲区，数据先落这里再进 GPU。
  • preload（预取）：请求还在排队就提前读盘，把 I/O 藏进等待时间。
  • break-even point（盈亏点）：读缓存和重算一样快的前缀长度，低于它就别读。
  • LongBench：长上下文评测集，多文档问答、代码理解等任务。
  • SCBench：共享上下文评测，多轮对话共享前缀的场景。
  • Snellius：荷兰国家超算，论文实验用的集群。
  • Bailian：阿里云百炼的 trace，真实生产请求的回放数据。
