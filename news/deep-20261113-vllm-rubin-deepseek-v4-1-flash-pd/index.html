vLLM 在 Rubin 上跑 DeepSeek-V4.1-Flash：PD 解耦的机架级实测

  • 原文：vLLM 团队（Inferact 主导，NVIDIA 协作），官方博客
  • 原文链接：https://vllm.ai/blog/2026-11-12-deepseek-v41-flash-vera-rubin
  • 发布：2026-11-12
  • 说明：数字全是 vLLM 自报，无第三方复现
  • 说明：这是 DeepSeek-V4.1-Flash 系列第三篇
  • 说明：前两篇是首日上线和 GB300 机架版

一句话

同一套 vLLM 栈，从 GB300 搬到 Rubin。

每卡每秒 170 万 token，用户还分到 387 个。

比 GB300 快 58 倍，但要看清是在哪个服务点上。

秘诀是三件套：内核重写、机架共享内存池、路由改按负载分。

人话解读

先讲这篇在测什么。

模型是 DeepSeek-V4.1-Flash。

跑在 72 张卡的一整个 Rubin 机架上。

评测用 SemiAnalysis 的 AgentX。

它回放真实 agent 会话，不是瞎编的提示词。

数是怎么算的，要先说清。

吞吐里算了三种 token。

缓存命中的输入、没命中的输入、吐出来的词。

三样全算进去，再除以卡数。

所以 170 万这个数，不是纯吐词的速度。

这点后面还会提， headline 别直接当结论。

再讲 Rubin 这块卡跟以前有啥不一样。

第一，每张卡有两个内存区。

自家区读得快，跨区读得慢。

带宽敏感的东西，放错区就亏。

第二，SM107 的矩阵指令更宽。

一次能做两倍的活，专吃 FP4 这种 4 位量化。

第三，72 张卡连在一个 NVLink 大家里。

跨两层托盘做张量并行，几乎不额外花钱。

vLLM 的打法分四组。

读题内核、解码内核、低延迟专线、机架内存池。

读题和解码本来就分开跑，这叫 PD 解耦。

读题就是把提示词算成草稿纸。

解码就是一个词一个词往外吐。

这篇最值钱的是第四组。

机架内存池加按负载路由。

高并发下前缀命中率还保在 96.5% 到 97%。

这才是能直接抄进你评估清单的东西。

核心方法

1. 读题内核：围着两个内存区和宽指令改

先说 MegaMoE 的 tile 怎么定尺寸。

vLLM 读题时不给空闲 rank 补 token。

86% 的步骤里，闲 rank 按自己的小 token 数定 tile。

可它的专家却在帮忙 rank 干活。

现在 tile 按本地和全机架平均里大的那个定。

40 步回放里 MegaMoE 时间少 55%。

旁边有闲 rank 时，单请求首字快 13% 到 39%。

再说 Mega-mHC 的残差流。

读题时它受显存带宽卡脖子。

每 token 要流过约 100KB 的四路残差。

残差现在分池放在两个内存区里。

每个 SM 先吃自己区的，再帮邻居。

32K token 时，单次调用从 354 微秒降到 317 微秒。

再说注意力那块。

MegaAttn 以前等加载等得发慌。

现在空闲 warp 先发下一批要算的东西。

KV 生产者提前把下一块的索引读进来。

每组通道自己算完自己的 key。

softmax 不用再经共享内存倒手。

16K 到 32K 时快 15%，4K 时快 23%。

最后说 MegaGate 的过滤。

路由器以前给 384 个专家全算一遍分。

现在先算个门槛，只有能进前 6 的才细算。

平均只有 7 个专家过关。

32K 时从 77 微秒降到 68 微秒。

整套读题优化加起来，DEP2 读题单步快约 28%。

2. 解码内核：权重放对区，通信只跑一趟

解码受专家权重读取卡脖子。

第一招，权重按输出列分到两个内存区。

每个 SM 只读自己区的 tile。

批量 32 时解码前向快 10.1%。

第二招，Wide-EP 分发只跑一趟 NVLink。

以前每个 token 要跑两三趟。

现在所有远程加载先发出去，再统一存。

专家数量用不回包的原子操作发出去。

DEP8 下 MegaMoE 从 192 微秒降到 160 微秒。

第三招，合并那步不等栅栏了。

合并缓冲先填满哨兵值。

哪个 CTA 自己的活干完了，马上合自己的。

只重读还留着哨兵的那几组。

跨 rank 的尾巴栅栏挪到下次启动时再等。

解码各尺寸下快 3.5% 到 10.8%。

第四招，小批量 GEMM 用 split-K。

每 rank 只有几十行时，启动的块太少。

把 K 维拆到一个 SM 簇里并行算。

GEMM 快 10% 到 38%。

第五招，推测解码的验证核也改了。

DSpark 每步每请求送 5 到 6 行去查索引。

现在拼成一个 192 宽的大 tile。

加上 SM107 的 K=128 指令，一次算完。

快 15% 到 22%。

整套解码优化加起来，DEP32 解码单步快约 25%。

3. 低延迟专线：TP8 跨两层托盘

单用户最在乎延迟，不在乎总吞吐。

这条专线把模型铺到两层托盘上，TP8。

跨托盘一次 all-reduce，只比托盘内贵 0.3 微秒。

每卡读的权重几乎减半，基本白赚。

单步因此快 35%。

FP4 权重分段也变了。

SM100 的共享内存只放得下 7 段。

SM107 的打包格式同样空间放 11 段。

每步省 57 微秒。

共享专家以前是每层尾巴，80% 的层都拖它。

行数少于 16 时，直接塞进路由 GEMM 里算。

每步省 220 微秒。

两次 all-reduce 和 mHC 合成一趟。

接收核一边加总，一边做归一化和路由。

每步再省约 30 微秒。

Engram 的 all-gather 也从 NCCL 换成自家融合核。

每步省约 40 微秒。

实测单用户从 1117 涨到 1844 token 每秒。

中位数，DSpark 每步接受 3.51 个词。

单用户峰值 1810 token 每秒，P90 口径。

4. 机架内存池：KV 和 Engram 表全机架共享

这是跟你评估最对口的一组。

Rubin 算得快，并发比 GB300 高得多。

所有 agent 会话的活前缀，加起来超出一台 rank 的缓存。

GB300 那套是每 rank 自己存一份 CPU 缓存。

会话钉死在一台 rank 上。

并发一高，有的 rank 闲着，有的在排队。

现在改成整个机架一个池子。

Mooncake 池子管 KV。

Engram 池子管两张 94.4GB 的 n-gram 表。

路由改成按负载分，不再钉死会话。

先说 Mooncake 池子。

一台 Mooncake 商店横跨所有托盘的内存。

KV 先放内存，不够再用各卡空闲的显存。

读都走 RDMA，哪个 rank 都能读到。

读题调度等池子的方式也改了。

查表异步在进程外跑，不堵调度。

本地显存已命中的，直接跳过查表。

查到就马上开始加载，不等下一步。

等查表卡住的步骤时间，从 6% 到 14% 压到 0.5% 以下。

等 KV 加载的，从 13.5% 压到 1%。

再说 HBM 池子。

DeepSeek-V4.1-Flash 小，KV 每 token 也小。

每台读题卡只留够一次最长请求的 KV。

剩下的显存预算自动划给 Mooncake 当 HBM 段。

池子从内存延伸到每张卡的空闲显存。

这块目前还是实验性的。

再说 Engram 池子。

解码那边早就把两张表拆到各 DP rank 上。

读题这边以前每台实例自己在主机内存里存一份。

一托盘就要 378GB 主机内存。

现在 18 张卡组成一个对等组。

每张卡只存 10.5GB，剩下的走 NVLink 去邻居显存里读。

比从主机内存读还快。

省出来的主机内存，能多装约 1500 个会话的前缀。

最后说按负载路由。

前缀都在共享池里了，会话不用再钉死。

Dynamo 把每个请求发给未缓存工作最少的 rank。

这只是改配置，不用改代码。

三台 DEP2 实例、并发 4800 时。

请求数多 68%，首字中位数从 29.8 秒压到 4.2 秒。

命中率从 91.8% 涨到 96.1%。

12 台 DEP2 的仿真里。

rank 空等的时间从 10.3% 降到 1.3%。

首字 P90 从 0.98 秒降到 0.38 秒。

跟研究方向的关联

这篇跟你的 PD 解耦评估对得上四处。

第一处，机架共享 KV 池加按负载路由。

这是最能直接抄的一组。

评估清单里可以加两项。

一是高并发下前缀命中率能不能保住。

二是会话钉死和按负载分，TTFT 差多少。

这篇给的数是 29.8 秒到 4.2 秒。

第二处，Engram 表的分片思路可以借。

大表别每台实例都存一份。

分片加对等组读，比复制省内存。

你的评估里若有大表结构，可以问同一句话。

第三处，PD 交接的等待开销要单列。

查表卡住和等 KV 加载，各占步骤时间多少。

这篇把两项分别从 6% 到 14%、13.5% 压到 0.5%、1%。

分开报，才知道瓶颈在哪。

第四处， headline 倍数要按服务点分档报。

58 倍只在 387 词每用户那个点成立。

低速点 2.7 倍，高速点 60 倍。

评估里报倍数不报服务点，等于没报。

但要注意三点不能直接搬。

一是 SM107 的宽指令是 Rubin 专属。

MI355X 上没有 K64 FP4 这套东西。

内核那组的招数只能借思路，不能抄数字。

二是吞吐口径里算了缓存命中的输入。

纯吐词的速度没这么高。

三是 HBM 池子还是实验性的。

只测了一个模型，一台机架。

术语表

  • PD 解耦：prefill/decode disaggregation，读题和吐词分开跑
  • 读题：prefill，把提示词算成草稿纸
  • 解码：decode，一个词一个词往外吐
  • DEP：disaggregated expert parallelism，解耦的专家并行
  • Wide-EP：专家并行铺得很宽，很多卡一起分专家
  • 草稿纸：KV cache，存着历史 token 的键和值
  • 首字：TTFT，从发请求到第一个词出来的时间
  • 吐词间隔：TPOT，每吐一个词的平均时间
  • P90：90% 的请求都好于这个数
  • 托盘：tray，机架里一层计算单元
  • 内存区：memory domain，一张卡里的两块内存区域
  • MMA：矩阵乘加指令，GPU 算矩阵的核心操作
  • FP4：4 位浮点量化，权重只有原来八分之一
  • MegaMoE：DeepSeek 那套 MoE 内核
  • MegaAttn：DeepSeek 那套稀疏注意力内核
  • Mega-mHC：多头合并那步的内核
  • MegaGate：路由器打分那步的内核
  • DSpark：推测解码，小模型先打草稿、大模型再改
  • 接受率：草稿里多少词被大模型收下
  • Engram：DeepSeek 的 n-gram 预测表，猜下一个词
  • Mooncake：开源 KV 缓存池，跨节点共享草稿纸
  • RDMA：远程直接内存访问，网卡直接读写对面内存
  • NVLink：英伟达卡之间的高速互联
  • all-reduce：多卡之间汇总数据
  • TP8：张量并行拆成 8 份
  • split-K：把矩阵乘的 K 维拆开并行算
  • 哨兵值：sentinel，一个不可能出现的占位值
  • AgentX：SemiAnalysis 的 agent 会话回放评测
  • GB300：Blackwell Ultra 机架，Rubin 的上一代

局限与提醒

  • 数字全是 vLLM 和 Inferact 自报，无第三方复现
  • 58 倍只在 387 词每用户的服务点成立
  • 吞吐口径含缓存命中的输入，不是纯吐词速度
  • 只测了 DeepSeek-V4.1-Flash 一个模型
  • 只测了一台 Rubin 机架
  • HBM 池子还是实验性的
  • SM107 宽指令是 Rubin 专属，不能搬到 AMD 卡上
  • GB300 对照数来自 InferenceX 的公开提交
