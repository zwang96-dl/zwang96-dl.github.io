61 亿请求、一年生产 trace：前缀缓存到底怎么玩

  • 论文：*A Year in LLM Serving: Workload Evolution, Caching and Load-Balancing*（Nixon 等，arXiv:2608.13573）
  • 解读文章：Covaratech《Six Billion Requests Later: What a Full Year of LLM Serving Actually Looks Like》
  • 论文链接：https://arxiv.org/abs/2608.13573
  • 解读链接：https://medium.com/@xyttu/six-billion-requests-later-what-a-full-year-of-llm-serving-actually-looks-like-16be3101e173

一句话人话

  • 有人拿了某 serverless 推理平台一整年的真实流量。
  • 61.2 亿请求，一个都没采样，全看。
  • 结论很实在：前缀缓存就认三件事。
  • 复用集中在 15 分钟内，命中率双峰，简单淘汰算法就够。

数据规模

  • 时间跨度：2025 年 4 月到 2026 年 4 月。
  • 61.2 亿请求，31.5 万用户，9174 个模型。
  • 35.8 万亿输入 token，2.5 万亿输出 token。
  • 作者承诺公开这份 trace，届时能拿来做基准。

核心发现

1. 负载一直在变，按请求数扩容会翻车

  • 日请求量 2025 年中爬升，夏末秋初见顶。
  • 2026 年初又回落，像个山丘。
  • token 量走势和请求量不完全同步。
  • 同一天请求数相同，实际工作量可能差很远。
  • 模型也在换：早期 DeepSeek 系占大头。
  • 后期 Qwen3-32B 等新模型接棒。
  • 结论：一周的测量值，规划不了一年的容量。

2. prompt 越来越重，输出越来越短

  • 输入大多几百到几万 token，长尾很长。
  • 输出集中在几十到几千，紧得多。
  • 一年里输入长度大体稳定。
  • 输出中位数从几百 token 掉到 100 以内。
  • 压力在从 decode 滑向 prefill。
  • 三个代表模型画风完全不同。
  • MiniMax-M2.5：输入重、输出短，典型 agent 画风。
  • DeepSeek-R1：长思考输出。
  • DeepSeek-V3.2：接近平均的聊天画风。
  • 同一个平台，三种完全不同的成本结构。

3. 前缀缓存命中率是双峰

  • prefix cache（前缀缓存）：之前算过的 prompt 片段直接复用。
  • 一个请求，要么几乎全命中上轮前缀。
  • 要么从零开始。中间地带很少。
  • 多轮对话：要么接着聊，要么新开一局。
  • MiniMax-M2.5 的命中分布更宽，高命中更多。
  • agent 式调用回合间隔短，前缀反复用。
  • 模型的可缓存性跟调用方式绑在一起。

4. 99% 的复用发生在 15 分钟内

  • 同一用户同一模型，前后两次请求。
  • 约一半间隔不到 0.1 秒。
  • 约八成在 10 秒内。
  • 99% 在 15 分钟内。
  • 所以 TTL 不用设很长。
  • 几秒的 TTL 就能抓住大头。
  • 分钟级的 TTL 基本全收。
  • KV 没必要囤几小时。

5. 简单淘汰算法赢了花哨的

  • eviction（淘汰）：缓存满了，决定踢谁出去的规则。
  • 作者把 trace 回放到缓存模拟器里比。
  • 比了 FIFO、LRU、ARC、S3FIFO、GDSF 等。
  • 结论：FIFO 和 LRU 打平或击败复杂算法。
  • LRU（最久没用先踢）、FIFO（先进先出）。
  • ARC（自适应替换缓存）在中等缓存下明显更差。
  • 原因：复用极度偏向"刚产生的前缀"。
  • 刚用完就复用，热度衰减极快。
  • 花哨的准入淘汰逻辑反而添乱。
  • 但离线的 Belady 最优还有差距。
  • Belady 最优：知道未来的上帝视角淘汰策略，当上限参考。
  • 说明 LLM 专用的缓存设计还有空间。

6. 缓存和负载均衡天生打架

  • 想命中缓存：把用户的请求发回同一台机器。
  • 想均衡负载：把请求打散。
  • 低负载时：用户自然集中在一台实例上，命中堆积。
  • 高负载时：路由器把用户打散到多台。
  • 命中要靠多台实例各存一份前缀来维持。
  • 容量烧了，还挤掉别人的前缀。
  • 作者测了四种路由策略。
  • round robin（轮询）、load first（发给最闲的）。
  • sticky（把同一用户钉在同一台机器）。
  • cache first（发到前缀复用最多的那台）。
  • cache first 只付了约 5–7% 的负载不均。
  • 因为单轮请求多，路由器拿它们去填坑。
  • 前缀亲和的代价比想象中便宜。

7. 别乱搬 KV

  • 10 万 token 的 MiniMax-M2.5 上下文约 27GB KV。
  • KV cache（推理时的"草稿纸"，存着算好的注意力状态）。
  • 10GB/s 链路单向搬要 2.7 秒。
  • 复用窗口只有几秒时，搬运比收益贵。
  • 留在本地显存、容忍一点不均，往往更划算。

跟你研究方向的关联

  • 你在评估 SGLang 的 P/D 解耦。
  • P/D 解耦：prefill 和 decode 分开跑不同 GPU。
  • 它的核心代价就是 KV 搬运。
  • 这篇给了生产级答案：别乱搬。
  • 复用集中在分钟级，搬运窗口很窄。
  • 27GB KV 搬 2.7 秒，很多场景下是亏的。
  • 跟 Crusoe MemoryAlloy 是同一套语言的两个答案。
  • 一个说"本地留着别搬"，一个说"让大家共享别搬"。
  • P/D 解耦评估里，KV 搬运的账要按这个算。
  • 另一个参考：昨天收的 H200 实战笔记。
  • 那篇的结论也是"按挤占的 KV 缓存评估优化"。
  • 两篇互相印证。

术语表

  • prefix cache（前缀缓存）：之前算过的 prompt 片段直接复用，不用重算。
  • TTFT（首 token 延迟）：从发请求到第一个字蹦出来的时间。
  • eviction（淘汰）：缓存满了，决定踢谁出去的规则。
  • LRU（最久没用先踢）、FIFO（先进先出）、ARC（自适应替换缓存）。
  • Belady 最优：知道未来的上帝视角淘汰策略，当上限参考。
  • sticky 路由：把同一用户的请求钉在同一台机器。
  • cache first 路由：发到能复用最多前缀的那台机器。
  • TTL：缓存条目的存活时间，过期就扔。

诚实说明

  • 只有一家 serverless 平台的数据，agent 和 API 用户为主。
  • 不代表第一方聊天产品的流量形状。
  • 缓存 token 日志只覆盖最后两个月。
  • 会话是靠启发式重建的，没有真实 session ID。
  • 论文是 v1 预印本，trace 承诺公开但还没放出。
  • Medium 解读是第三方转述，关键数字已对照论文核过。
