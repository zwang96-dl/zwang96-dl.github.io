DLFP：不建模，直接看延迟调 prefill 块大小——小模型上灵，大模型上翻车

原文：Decode-Latency Feedback Prefill: A Model-Free Controller and Its Generalization Limits
arXiv:2609.38386v1，2026-09-29 发布
作者：Gaurav Agarwal、Ashish Garg、Isha Singhal
原文链接

人话解读

同机混跑推理有个经典坑：正在吐字的请求，突然来个长 prompt 做 prefill，全机人一起卡一下。

prefill 是算力型，decode 是访存型。同一批里混着跑。 长 prompt 的 prefill 会拖慢正在 decode 的请求。

业界做法是 prefill 切块（chunked prefill）。 块越大 prefill 越快，decode 越卡。最优块大小跟模型、硬件、负载、SLO 都有关，调参很烦。

这篇的办法是：别建模，直接看延迟。延迟超标就把下一块切小，延迟富余就放大。这就是 DLFP。

类比：像开车不看仪表盘预测油耗，只看油表指针，指针掉得快就松油门。

*图注：c_t 是当前 prefill 块大小，T 是目标混合迭代延迟，L̂_t 是实测延迟。实测超目标就缩小块，低于目标就放大。floor_128 按 128 token 取整，防抖动。只在有活跃 decode 时生效，没有 decode 就不限制。*

核心方法

  • 只动"叠在一起"的那部分 prefill：有 decode 在跑时，下一块 prefill 才受限。
  • 没 decode 在跑的纯 prefill，随便跑多大，不管。
  • 反馈信号是实测延迟：上一个调度周期的混合迭代耗时 L̂_t。
  • 超目标 T 就按比例缩小，低于就放大。比例控制器，不建模。
  • 取整防抖：块大小按 128 token 取整，避免来回微调。
  • 上下限钳住：c_min=1024，c_max=6144，防失控。
  • 复位逻辑：decode 一清空，控制器复位到 c_initial=3072。
  • 孤立 prefill 不受限，吞吐优先。
  • 实现改的是 vLLM V1 调度器：判断运行中的请求是否做完 prompt。
  • 有活跃 decoder 时，新请求的 prompt token 按 cap 切块。
  • decode 调度、权重、精度、attention 后端全都不动。

关键数据

  • P99 token 间隔延迟降 27.7%：三个配对试验分别降 24.8%、30.1%、28.2%。
  • 95% 置信区间 21.0%–34.3%，每轮都过了预设的 10% 门槛。
  • SLO 全过：300 个请求 300 个达标，输出逐 token 完全一致，零失败。
  • 代价是首字延迟涨 34.8%：P99 TTFT 上涨，但仍在 SLO 内。
  • P99 端到端延迟涨 7.8%。token 更顺滑，第一个字来得慢一点。
  • 测试配置：Qwen3-0.6B BF16，单张 A100 80GB，vLLM 0.17.1。
  • Agent 负载：16384 输入 / 256 输出。

Poisson 到达，1 请求/秒。

  • 固定块大小的对照翻车：4096 token 的固定 cap 过不了 10% 门槛。
  • 2048 的 cap 能降延迟。

但 SLO 通过率从 300/300 掉到 287/300。

  • 说明固定值要么不够狠，要么狠过头。自适应才两头兼顾。

泛化翻车：大模型上不灵

  • Qwen3-8B 上反效果：0.10 请求/秒时 P99 ITL 从 19 ms 涨到 281 ms。
  • SLO 通过率从 10/20 掉到 7/20。控制器把延迟挪来挪去，没修好。
  • Qwen3-32B 上也一样：P99 TTFT 从 18.07 涨到 21.64 秒。
  • token 能耗涨 4.7%，两边 SLO 全是 5/12，打平但没赢。
  • 双卡 tensor 并行也翻车：P99 TTFT 涨 44.1%。

SLO 通过率从 110/300 掉到 101/300。

  • 根因是反馈信号不准：控制器用的是"调度器被调用的时间间隔"。
  • 小模型上这个间隔跟 GPU 真实迭代时间碰巧相关，大模型上异步调度把相关性打碎了。
  • 更深一层：把一个大卡顿拆成几个中等卡顿，反而让更多 token 间隔摸到 P99。
  • 作者的结论很诚实：这只是 0.6B 单卡上的可复现原型，不是通用方案。
  • 下一步该做"按 GPU 完成时间计时"的控制器。

跟你的研究方向的关联

  • 跟你评估的 P/D 解耦是同一道题的两种解法：干扰的根子是 prefill 和 decode 抢同一批 GPU 时间。
  • P/D 解耦是物理分开，各跑各的。这篇是软件限流，decode 忙时 prefill 少吃点。
  • 单卡、边缘端、没条件拆两池时，这篇的思路是备选项。
  • 干扰公式可以直接抄：

L_t ≈ L_decode(D_t) + L_prefill(p_t, D_t) + L_overhead

  • 这就是 P/D 解耦收益的理论底座。你的评估报告里可以用它解释"为什么拆开能赢"。
  • autotuner 的现成雏形：观测延迟→调 prefill 块大小，这就是"线上诊断+自动改参"。
  • 跟 20 点版的 Herschel 笔记同路：Herschel 是改 kernel，这篇是调调度参数。
  • 负结果的价值：调度器调用间隔≠GPU 完成时间，这个坑你的 autotuner 也会踩。
  • 做反馈控制时，信号一定要取自设备完成事件，不能拿主机侧计时糊弄。
  • Qwen3 系列实测数据：0.6B/8B/32B 三档在 A100 上的 P99 ITL 基线都在这篇里。
  • 你的 MI350X/H100 评估可以拿来做量级对照。

术语表

  • prefill：处理提示词的阶段
  • 把 prompt 全部 token 一次算完，算力密集，顺手生成 KV 缓存。
  • decode：逐 token 生成的阶段
  • 一次吐一个 token，访存密集，对延迟抖动敏感。
  • ITL（inter-token latency）：相邻两个 token 的时间间隔
  • 决定打字机效果顺不顺滑。P99 ITL 是最卡的那 1%。
  • TTFT（time to first token）：首字延迟
  • 从发请求到第一个 token 出来的时间。
  • chunked prefill：把长 prompt 的 prefill 切成小块
  • 每块跟 decode 轮流跑，避免一次 prefill 独占太久。
  • 比例控制器：误差多大就调多大幅
  • 不建模、不预测，只看实测跟目标的差距。
  • SLO：服务等级目标
  • 本文：TTFT ≤ 5 秒、平均 ITL ≤ 35 ms、端到端 ≤ 14 秒。
  • Poisson 到达：请求按泊松过程随机到达
  • 模拟真实流量的随机性，不是等间隔喂。
  • guarded scheduling cycle：带保护的调度周期
  • 控制器先让一个周期按当前 cap 跑完，再根据实测调下一周期。
  • tensor 并行：一张卡的模型切两半放两张卡上
  • 每层都要通信同步，延迟行为跟单卡不一样。
