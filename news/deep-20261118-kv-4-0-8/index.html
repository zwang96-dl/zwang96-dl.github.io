投机解码的草稿 KV 压到 4 位，接受率只掉 0.8 个点

  • 作者：Saksham Gupta、Michael Li，卡内基梅隆大学
  • 文章：Memory-Efficient Speculative Decoding with Quantized Draft KV Cache
  • 提交时间：2026-11-16（arXiv:2611.20565v1，NeurIPS 2026 AXIOM 研讨会）
  • 原文链接：https://arxiv.org/abs/2611.20565
  • 说明：数字全是作者自报，没有第三方复现。质量实验用假量化，速度还没实测。

一句话

投机解码要存两份草稿纸。

小模型那份压到 4 位，接受率只掉 0.8 个点。

大模型那份不动，输出质量就不变。

人话解读

投机解码就是小模型先打草稿。

大模型再验一遍，错了就改。

草稿模型也要存一份 KV 缓存。

以前这份也是 16 位，占地方。

这篇只压草稿模型那份。

大模型那份保持 BF16 不动。

验算规则没变，输出就不会变。

省的是显存，赌的是草稿质量。

结果赌赢了，接受率几乎没掉。

更有意思的是一个反常识的发现。

以前大家都说 key 比 value 更怕压。

这篇证明，这个结论是量化姿势带出来的。

换个分组方式，结论就反过来了。

key 和 value 到底谁更娇气。

不能只看数值，得看你怎么分组。

核心方法

只压草稿 KV，目标 KV 保持 BF16。

记号 KaVb 的意思是 key 用 a 位。

value 用 b 位。

主推档是 K4V4。

key 和 value 各 4 位。

key 按通道分组。

32 个 token 一组，每通道一个 scale。

value 按 token 分组。

每个 token 一组，自己算 scale。

最近 128 个 key 不压。

留在 BF16 里当残差窗口。

量化用仿射格式。

每组存一个零点和一个 scale。

为什么 key 以前显得娇气。

朴素的按 token 量化，一行共用一个 scale。

某个通道的 outlier 一冒头。

整行的 scale 都被它撑大。

其他通道的数就全被压扁了。

换成按通道分组。

outlier 只影响自己那一列。

key 也就不娇气了。

关键数据

测了 6 对目标加草稿模型。

Qwen2.5 3B 配 1.5B、7B 配 3B。

Qwen3 8B 配 4B。

Llama 3.1 8B 配 3.2 3B。

OLMo 2 7B 配 1B。

SmolLM2 1.7B 配 360M。

576 条 FineWeb-Edu 提示词。

每条 1024 个 token。

草稿每轮最多提 4 个词。

每轮生成 16 个词。

K4V4 的省钱账。

草稿 KV 少 66.20%。

两份加起来少 23.95%。

各对之间是 11.30% 到 33.17%。

接受率 57.93% 掉到 57.14%。

只掉 0.79 个百分点。

相对只掉 1.36%。

KL 散度 0.00730。

top-1 一致率 95.99%。

长上下文收益更大。

16K 和 32K 上下文。

两份加起来少约 31%。

接受率只掉 0.94 和 0.73 个点。

打包实测的数更实在。

32K 上下文，Qwen2.5-1.5B 草稿。

BF16 要 896.0 MiB 每条序列。

K4V4 打包后只要 260.2 MiB。

一条序列省 635.8 MiB。

几何翻转的数也很干净。

朴素量化下，K8V4 比 K4V8 高 10.87 个点。

换按通道 key 后，差距变到负 0.25 个点。

控制实验只换 key 的量化器。

差距从正 28.70 变到负 0.33 个点。

16K 取针任务上。

K4V2 对 K2V4 的差距。

从 81.25 个点缩到 16.15 个点。

诚实提醒

这篇的短板，作者自己写得很直白。

原型机反而更慢了。

打包的 K4V4 比 BF16 投机解码慢 18% 到 33%。

连目标模型单独跑都比它快。

峰值显存也没降。

打包只在 BF16 预填充之后做。

高峰那一刻，BF16 的份还在。

批量验证器还不精确。

端到端的时间先当初步数。

质量实验用的是假量化。

解压回 BF16 再算，只量质量不量速度。

256 词续写和原型机。

只测了一对模型，batch 只有 1。

长上下文实验的提示词也比 1K 那组少。

跟研究方向的关联

这篇跟投机解码评估直接相关。

第一，草稿 KV 是一笔独立的账。

PD 拆开跑时，草稿放哪一侧。

这笔账就跟谁走。

评估清单里可以单列一项。

第二，K4V4 档可以直接抄进清单。

省 66% 草稿 KV。

接受率代价不到 1 个点。

长上下文场景先算这笔账。

第三，量化姿势的教训值得记下来。

key 要几位，不能只看数值敏感度。

得分组方式一起看。

以后看到 K8V4 比 K4V8 好的结论。

先问一句，分组方式是什么。

第四，落地前先看清短板。

原型机还慢，融合内核没到位。

提速之前，别指望它省时间。

它现在只省显存。

第五，跟 vLLM 的 DBO 和 DSpark 是同一条线。

草稿越便宜，验证行的成本越低。

PD 评估里草稿 KV 的压缩档。

可以跟验证行成本一起报。

术语表

  • 投机解码：小模型先猜，大模型再验的加速办法。
  • 草稿模型：负责先猜的小模型。
  • 目标模型：负责验算的大模型。
  • KV 缓存：存着历史 key 和 value 的草稿纸。
  • BF16：16 位浮点格式，没压缩的默认格式。
  • K4V4：key 和 value 各 4 位的量化档。
  • 接受率：草稿提的词里，大模型收下的比例。
  • 按通道量化：每列单独算 scale 的分法。
  • 按 token 量化：每行单独算 scale 的分法。
  • 仿射量化：每组存零点和 scale 的量化格式。
  • 零点：量化后 0 对应的原始数值。
  • scale：量化时每档代表多大的步长。
  • 残差窗口：最近的 token 不压，留在高精度的窗口。
  • 假量化：解压回 BF16 再算，只量质量不量速度。
  • outlier：数值大得离群的个别元素。
  • KL 散度：两份概率分布差多远的量。
  • top-1 一致率：最可能那个词跟原来一致的比例。
  • passkey retrieval：长文里找一串密码的取针任务。
  • FineWeb-Edu：教育类网页文本数据集。
  • WikiText-2：维基百科文本数据集。
