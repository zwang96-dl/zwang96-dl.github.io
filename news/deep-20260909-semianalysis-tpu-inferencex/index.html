SemiAnalysis：Google TPU 推理外部化实战调优笔记（InferenceX）

文章：TPU Inference Externalization Full Steam Ahead - InferenceX
来源：SemiAnalysis（第三方实测，约 2026-09-07）
原文：https://newsletter.semianalysis.com/p/tpu-inferencex-full-steam

一句话人话版

Google 正在把自家 TPU 推理技术，从"只服务内部"转向"卖给外部客户"。SemiAnalysis 拿到了第一批第三方实测数据。TPUv7 Ironwood 跑 FP8。每美元性能比 B200 高 50%。还披露了大量"别人是怎么调出来的"工程细节。

背景：为什么这事重要

十多年来，Google 的 TPU 只服务内部。搜索、广告、YouTube、Gemini 都用它。现在风向变了：

  • Anthropic 已承诺 100 万+ TPU。40 万直接购买，60 万租 GCP。2029 年用量将超过 DeepMind 自身。
  • Ironwood（TPUv7）是第一代"为别人的推理负载而战"的 TPU。可以直接买，也可以走 GCP 租。
  • 软件栈 TorchTPU，也就是 TPU 上的原生 PyTorch。预计 10 月开源。vLLM/SGLang 的 TPU 后端有望进入 day-0 支持名单。现在只有 NVIDIA 是 day-0，AMD 算"勉强可用"。

注意两点诚实声明：

  1. 纯裸性能 TPU 并没有赢。赢的是"性能每美元"（TCO 更低）。买芯片的人关心的是赚钱效率，不是跑分。
  2. 高并发 256 时，TPU 的 TTFT 是 5.41s。B200 是 3.75s，TPU 不如它。这是延迟和吞吐的经典权衡。

另外：TPUv7 没有原生 FP4，FP4 场景 NVIDIA 仍领先。但 TPUv8i 会补上 FP4，直指 Rubin NVL72。

原文关键图

图 1 人话解读。横轴是"交互性"（每用户每秒多少 token，越往右并发越高）。纵轴是每百万 token 成本。蓝色 TPU7x 的线，在整个区间基本都压在下面。B200 是深绿，B300 是浅绿。不是某个点赢，是整条曲线赢。测试配置：Qwen3.5-397B、FP8、8k 输入/1k 输出。注意 B200 的线在高交互性段陡然上翘（成本爆炸），TPU 的曲线更平缓。

图 2 人话解读。低交互性（20 tok/s/用户）下的原始吞吐对比。TPU7x 每芯片 9,364 tokens/s。B200 是 8,903，B300 是 8,925。TPU 不仅便宜，裸吞吐还快了约 5%。配合更低的每小时成本，算下来：每美元 token 数比 B200 多 50.4%。比 B300 多 96%。

图 3 人话解读。横轴是端到端延迟（用户从提问到拿到完整回答的时间）。纵轴是每百万 token 成本。这是经典的"延迟 vs 成本"权衡曲线，越往左下越好。TPU 的曲线整体在最左下。在中位响应 20 秒那档：TPU $0.098。B200 $0.106。B300 $0.132。想快可以快、想省可以省，TPU 的曲线包住了 GPU 的曲线。这就是 SemiAnalysis 的底气。敢说"50% better performance per dollar"。

实战调优细节（最值得看的部分）

1. DP attention（注意力数据并行）+ EP8（专家并行）

Qwen3.5 的 GQA 注意力层：32 个 query head。但只有 2 个共享 KV head。8 卡 TP 时，query head 很好分（每卡 4 个）。但 KV head 没法整除，4 张卡需要同一份 KV 数据。

做法是 KV head 复制。vLLM 本来就支持，TPU 后端补了个兼容 fix 把它激活。避免不必要的 All-to-All 通信。

更高并发时上了 DP8 attention + EP8。每张卡处理不同请求子集。各自保留完整的 KV head。KV cache 存的是不同请求的历史，不是重复拷贝。512 个路由专家则分散在各卡上，避免复制庞大的专家权重。这需要 serving 引擎协同调度三件事。请求分配、循环状态 slot、block table。这正是"prefill/decode 资源分离"思想。在 TPU 上的落地形态。

2. MoE 通信优化：把 80µs 抠出来

  • 把"专家 ID"和"路由权重"两次 all-gather 合并成一次。每层省约 80µs。DeepSeek-V3 有 58 层。一轮前向省 4.64ms，直接降低 TPOT。
  • ReduceScatter 搬家。从 TensorCore 搬到 SparseCore。后者擅长不规则数据搬运。die-to-die 链路先做片内合并，再跨片交换。还用 double buffering，让传输和计算重叠。8k1k 吞吐 +4.1%~14.2%。
  • 不是所有 collective 都值得搬。小 collective 在 TensorCore 上更快。阈值按 VMEM 容量定。调优是"看情况"，不是"一刀切"。

3. MoE kernel 优化：驯服"不规则"

MoE 的 token-专家分组是不规则的（ragged）。喂给 TPU 矩阵单元前要整理：

  • Grouped matmul v2。去掉冗余 tile 计算。按有效行数传数据。三重缓冲专家权重。元数据生成 fuse 进 kernel。
  • 把 token 重排搬到 SparseCore。TensorCore 专心做矩阵乘。吞吐 +12%，TTFT/TPOT 双降。
  • 小 batch 用专用置换路径（one-hot 矩阵 + 普通 matmul）。并发 64 时吞吐 +7.3%。
  • 排序键打包。expert ID + token index 合成一个 sort key。排序延迟从 106.6µs 降到 21.7µs。

4. 软件栈三代演进（vLLM/SGLang on TPU）

  1. PyTorch/XLA。lazy 执行，攒计算图再编译。原型阶段。
  2. TorchAX / tpu-inference。PyTorch 模型翻译成 JAX 执行。复用成熟的 TPU primitives。当前公开后端，但翻译层问题多。
  3. TorchTPU（10 月开源）。TPU 变成原生 PyTorch 设备（device="tpu"）。PyTorch dispatcher 直接路由 ATen 算子。编译走 StableHLO→XLA。用户面是 PyTorch-native。底层仍是 TPU-aware 的 Pallas kernel。

意义：vLLM/SGLang 能复用上游生态。模型代码、调度器、continuous batching、API 都不用重写。不用在 PyTorch↔JAX 边界上重造轮子，模型 bring-up 成本大降。

跟你研究方向的关联

  • 第一手的"别人是怎么调的"。DP attention 加 EP 的协同调度。KV head 复制。混合架构的前缀缓存，要同时保留 KV 和循环状态。这些都是实战案例。讲 prefill/decode 资源分离和 KV cache 优化。有具体数字，也有取舍逻辑。
  • 硬件格局。推理硬件从"NVIDIA 独大"走向"TPU/AMD 并存"。SGLang 的多后端架构会越来越值钱。RadixArk 正在做 SGL-torchtpu。选框架时"多硬件适配能力"是加分项。
  • P/D 解耦的参照。Google 内部 P/D 解耦已生产化多年，外部栈还没优化好。SemiAnalysis 明确说：几个月内补齐后会再测。对阵双方是 TPUv7 disagg 和 GB300 NVL72 disagg。这篇 follow-up 出来时值得再读。

术语表

  • TCO（total cost of ownership）。总拥有成本。这里指"每百万 token 实际花多少钱"。
  • Pareto 曲线。延迟-成本权衡曲线。曲线上的点都是"给定延迟下最便宜"的配置。
  • DP attention。注意力的数据并行。不同卡处理不同请求，而不是把一个请求的注意力切分到多卡。
  • EP（expert parallelism）。专家并行。MoE 的不同专家放在不同卡上。
  • Pallas。TPU 的 kernel 编程语言（对标 CUDA/Triton）。
  • SparseCore。TPU 上专门处理不规则/稀疏数据搬运的计算单元。TensorCore/MXU。干稠密矩阵乘的。
  • interactivity。每用户每秒 token 数。衡量"生成流畅度"的业务指标。
