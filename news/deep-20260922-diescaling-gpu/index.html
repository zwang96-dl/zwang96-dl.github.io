DieScaling：GPU 越做越大，调度开始"看人下菜碟"

原文：Dissecting How Die Scaling Breaks GPU Fine-grained Scheduling
arXiv:2609.24270v1，2026-09-21 提交。
作者：Xiaoze Fan、Jianhao Wang、Weihao Cui 等（上海交大、新加坡国立、NVIDIA）。

人话解读

  • 你以为 GPU 是"对称"的，其实不是。
  • 卡越做越大，代价是物理结构开始不对称。
  • 第一个不对称来自良率筛选（floorsweeping，坏的 SM 关掉保良率）。
  • 整颗 die 造出来，有问题的 SM 直接物理屏蔽。
  • 于是同样叫 H200 的卡，每张卡的 SM 分布都不一样。
  • 第二个不对称在内存：L2 缓存被切成两块 NUMA 分区。
  • NUMA 就是非统一内存访问：一块近、一块远。
  • 访问远端分区的 HBM，延迟贵 34% 到 67%。
  • L2 远端访问更惨，B200 上接近翻倍。
  • 以前的调度器只关心"分多少资源"，不关心"分到哪块物理位置"。
  • 这篇证明：不管位置，性能最多能差 1.33 倍。
  • 还给了一套轻量方法，把每张卡的真实拓扑测出来。
  • 再用测到的拓扑，让现有调度器学会"认路"。
  • 三个场景都吃到甜头：整卡 kernel、PD 复用、多租户混跑。
  • PD 就是 prefill/decode 解耦，你正在评估的那个方向。

核心方法

  • SM 是 GPU 的基本计算单元，先记住这个。
  • 算力侧：用两阶段探测，拼出逻辑 SM 到物理 GPC 的完整映射。
  • GPC 是计算簇，一组 SM 的上级单位。
  • 第一阶段用 Thread Block Cluster 探测。
  • Thread Block Cluster 就是线程块簇。它把一组 block 钉在同一个 GPC 的 SM 上。
  • 在同一个簇里共现的 SM，一定属于同一个 GPC。
  • 第二阶段测 L2 带宽：同一 GPC 内的 SM 会挤占 Xbar 带宽。
  • Xbar 是 SM 通往 L2 的交叉开关。
  • SM 加到 6 个（H200）带宽还不涨，就说明它们挤在同一个 GPC。
  • 两轮探测不到 1 分钟，用 nvdebug 校验 100% 一致。
  • 结论：逻辑 SM 分成两类，normal 和 random。
  • normal SM 走架构预定义的映射。random SM 的位置，随每张卡的良率结果漂。
  • 内存侧：先测 HBM 延迟分布，拉出本地和远端两个峰。
  • 再逐位翻转物理地址，看哪个 bit 决定分区归属。
  • 翻出一个 XOR 哈希：物理地址某些位做异或，奇偶定分区。
  • 三种卡上最低参与位都是 bit 12，也就是 4KB 粒度。
  • 整个哈希反推只要 10 秒左右。
  • 拿到拓扑后，调度策略就多了一个维度：不只看分多少，还看分哪块。

关键数据

  • 远端 HBM 延迟：H200 约 490→655 周期，贵 34%。
  • 同一项在 B200 上约 552→920 周期，贵 67%。
  • 远端 L2 延迟：H200 约 309→466 周期，贵 51%。
  • B200 上约 364→725 周期，接近翻倍。
  • 28 张 H200 里，23 张长一个样。都是 6 个 16-SM GPC 加 2 个 18-SM GPC。
  • 剩下的几张更不齐，最惨的一张有一个 10-SM 的 GPC。
  • 同 SKU 的卡拓扑各不相同，静态查表行不通。
  • 有效 L2 只有标称的 65.8%（H200）和 64.7%（B200）。
  • 原因是远端数据会被复制进本地 L2，白白挤掉本地数据。
  • 感知 NUMA 的 GroupGEMM，在 B200 上最高快 1.22 倍。
  • PD 复用里，感知 NUMA 的排布很管用。H200 上 decode 吞吐涨了 14.3%。
  • B200 上是 10.4%，prefill 基本没涨，因为它是计算密集型。
  • 拓扑无知的 SM 分配，最多造成 1.33 倍的性能落差。
  • MIG 为了让同 SKU 的 profile 长得一样，会关掉本来好好的 SM。
  • 测的那张 H200 上，4g profile 硬关了 4 个健康 SM。

跟你研究方向的关联

  • 你在 MI350 单卡上跑 vLLM 吞吐 benchmark，正在调调度层参数。
  • 这篇虽然测的是 NVIDIA 卡，但第 8 章专门讨论了 AMD。
  • MI300X 上每个 XCD 也有良率筛选。
  • XCD 是 AMD 的加速器计算 die，类似 NVIDIA 的 GPC。
  • 每个 XCD 40 个 CU，关掉 2 个，剩 38 个，各个 XCD 倒是整齐。
  • CU 是 AMD 的基本计算单元，类似 SM。
  • 但内存侧照样有 NUMA。Infinity Fabric 把每个 XCD 连到各个分区缓存。
  • MI350 也是 chiplet 堆叠，内存不对称大概率还在。
  • 你的 benchmark 里，decode 是访存密集型，最吃 NUMA 的亏。
  • 如果 vLLM 的调度器不管物理位置，KV 访问可能频繁跨分区。
  • 论文里有效 L2 只有标称 65%，这点对你算 batch 上限有参考。
  • KV cache 实际能蹭到的 L2，比规格书上写的少。
  • 你正在评估的 PD 解耦，正好撞上这篇的第二个场景。
  • 它的做法：task 私有状态放本地分区，共享的权重和 KV 跨分区共享。
  • 14.3% 的 decode 提升，逻辑就是"各扫门前雪，公用的再共享"。
  • 调参时多一个维度：不只分多少 SM，还要问分的是哪几块 SM。
  • MI350 上没有 Thread Block Cluster 这功能。但 NUMA 亲和性，依然值得你亲手测一测。
  • 建议：跑 benchmark 时顺手测一下跨分区延迟，当个基线。

术语表

  • SM：流式多处理器，GPU 的基本计算单元。
  • GPC：图形处理簇，一组 SM 的上级单位。
  • TPC：纹理处理簇，两个 SM 一组。
  • floorsweeping：良率筛选。坏的 SM 物理屏蔽，保证出货良率。
  • NUMA：非统一内存访问。离得近的内存快，远的慢。
  • normal/random SM：逻辑 SM 的两类。normal 位置固定，random 随良率漂。
  • Thread Block Cluster：线程块簇。把一组 block 钉在同 GPC 的 SM 上，Hopper 引入。
  • LTC fabric：连接两个 L2 分区的片上网络，远端带宽的瓶颈。
  • XOR hash：异或哈希。物理地址某些位异或定分区，粒度 4KB。
  • MIG：多实例 GPU。把一张卡硬切成几个隔离实例。
  • Green Context：轻量 SM 分区机制，给并发 kernel 分 SM。
  • PTB：持久线程块。一个 block 钉在一个 SM 上循环干活。
  • PD 解耦：prefill 和 decode 分开跑，互不拖后腿。
  • XCD：AMD 的加速器计算 die，类似 NVIDIA 的 GPC。
  • CU：计算单元，AMD 的基本计算单元，类似 SM。
