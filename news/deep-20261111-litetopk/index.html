LiteTopK：长上下文读题，挑名次那步不用再写整张表

  • 原文：Ziqi Yin、Jianyang Gao 等，arXiv:2607.11976（2026-07-13 提交）
  • 原文链接：https://arxiv.org/abs/2607.11976
  • 落地：SGLang #47469（2026-11-11 合入，11点版深读）
  • 落地链接：https://github.com/sgl-project/sglang/pull/47469
  • 说明：论文 7 月就出了，SGLang 的实现今天才合入主线

一句话

DSA 读题挑前 k 名。

老办法先把整张打分表写进显存。

再单独跑一遍挑名次。

1M 上下文光是这步就要 32GB。

LiteTopK 先采样估个阈值。

边算边筛，只留过线的候选。

打分表再也不用落地了。

人话解读

DSA 是 DeepSeek 用的稀疏注意力。

GLM-5.x 和 DeepSeek-V4.1 都在用它。

读题时，每行要从所有可见 key 里挑前 k 名。

挑之前先算一遍打分。

打分就是 query 和 key 的相似度。

老办法分两步走。

第一步，DeepGEMM 把整张打分表写进显存。

表是行乘列，行是 query，列是 key。

第二步，再单独跑一遍 top-k 挑名次。

上下文一长，这张表就大得吓人。

1M 上下文、8192 个词元一块读。

光是这步就要约 32GB 临时显存。

显存就这么多，表占了，KV 缓存就没地方住。

KV 缓存就是模型留的草稿纸。

vLLM 和 SGLang 只好把块切小。

8192 切成 512，拿吞吐换显存。

作者发现了一个可以利用的现象。

高维向量的内积分数，挤在很窄的区间里。

这叫分数集中，是维度灾难的另一面。

GLM-5.2 第一层，1M 上下文。

分数集中在 25 到 35 之间。

45 分以上极其罕见。

前 100 名的门槛是 51.37 分。

前 10000 名的门槛是 45.21 分。

前 100000 名的门槛是 41.45 分。

三个门槛隔得这么开。

抽一小撮分数，就能估出阈值在哪。

估准了，边算边筛就行。

过线的才留下来进终选。

不过线的，算完就扔。

类比：招 100 个人，先看一小摞简历定分数线。

分数线一定，后面边看边筛。

不用先把所有简历复印一份再挑。

核心方法

1. sample-filter-select：采样、过滤、再选

三步走，融进一个核里。

第一步是采样。

每行抽一小撮 key，算它们的分数。

用这些分数估出这行的阈值。

阈值就是过线才能进终选的分数线。

第二步是过滤。

算每个 key 的分数时，顺手跟阈值比。

过线的才写下来，不过线的直接扔。

第三步是选。

只在过线的候选里跑 top-k。

整张打分表从头到尾没落地。

显存只住候选，不住全表。

2. 两种阈值实现：保守估计和预测加回退

第一种是保守阈值估计。

采样估个偏低的阈值。

宁可多留几个候选，不漏掉真前 k。

代价是候选多一点，终选慢一点。

第二种是预测阈值加回退。

先预测一个更准的阈值。

候选留得更少，终选更快。

万一预测偏了，候选不够数。

就回退重算，保证结果不错。

3. LiteDSA：相邻 query 复用重叠的 KV

挑完名次，还要算稀疏注意力本身。

相邻的 query，选中的 key 大量重叠。

LiteDSA 让它们共享 KV 加载。

不重复从显存搬同一份数据。

每 query 的入选集合保持原样。

结果不变，只是少搬运。

4. SGLang 的落地：只给长上下文开绿灯

SGLang #47469 把这套办法接进来了。

FP8 索引器给 DSA 用，32 或 64 个索引头。

FP4 索引器给 DeepSeek-V4.1 用。

都是 SM100 上的单核。

SM100 是 Blackwell 架构的计算单元代号。

默认关闭，想试要开环境变量。

SGLANG_OPT_USE_PREFILL_LITE_TOPK=1

开也有门槛，不是所有请求都走新路。

DSA 读题，最长行看到的 key 至少是 8 倍 index_topk。

V4.1 那边，最长请求至少 24576 个压缩 key。

短了走老路，老路一样快。

关键数据

  • 动机：SGLang 上，1M 上下文读题，挑名次占 70.9%
  • 动机：vLLM 上，GLM-5.2 占 61.8%，V4-Flash 占 46.5%
  • 临时显存：1M 下基线约 32GB，LiteTopK 只要 2.84GB
  • 内核延迟：1M 上下文，8192 个 query，LiteTopK 37.78 毫秒
  • 内核延迟：同样配置，vLLM 51.25 毫秒，SGLang 64.85 毫秒
  • 内核加速：比 vLLM 快 1.36 倍，比 SGLang 快 1.72 倍
  • 内核加速：256K 上下文，比 vLLM 快 1.25 倍，比 SGLang 快 1.57 倍
  • 端到端读题：1M 上下文，GLM-5.2 快 1.21–1.37 倍
  • 端到端读题：1M 上下文，V4-Flash 快 1.10–1.38 倍
  • 端到端读题：1M 上下文，Hy-4-Preview 快 1.19–1.27 倍
  • 端到端读题：开上下文并行，Hy-4-Preview 到 1.49 倍
  • LiteDSA：每 8192 词元块，1.55 毫秒降到 0.91 毫秒
  • LiteDSA：256K 到 1M，四档都是 1.70–1.81 倍
  • 解码挑名次：比 SGLang 快 1.08–1.82 倍，比 vLLM 快 1.13–1.88 倍
  • 解码端到端：最多快 1.04 倍，解码本来就不吃这步
  • 精确性：挑名次的召回是 100%，一个没漏
  • 精确性：双针检索，最大绝对差 0.29 个百分点
  • SGLang B300：32K 上下文，内核快 2.45 倍
  • SGLang B300：128K 上下文，内核快 2.16 倍
  • SGLang B300：1M 上下文，内核快 1.58–1.68 倍
  • SGLang 端到端：GLM-5.3 FP8，128K 首字快 12.7%
  • SGLang 端到端：128K 乘 4 并发，输入吞吐涨 17.5%
  • SGLang 正确性：4100 万行对比，99.9% 完全一致
  • SGLang 正确性：平均召回 0.9999995，分歧全是并列换位

跟研究方向的关联

这篇直接撞上 P/D 解耦评估。

读题池子是解耦里最吃负载的环节。

DSA 模型的读题，挑名次占七成时间。

三招能直接进评估清单。

第一招：采样估阈值、边算边筛。

评估长上下文读题时，先问挑名次占多少。

再问临时显存占多少。

32GB 压到 2.84GB，省出来的显存能多住 KV。

第二招：短上下文走老路。

16K 个 key 以下，过滤留太多。

新路不比老路快。

评估时要按上下文长度分档。

别拿 1M 的加速比去套 8K 的请求。

第三招：LiteDSA 的 KV 复用。

相邻 query 共享加载，少搬运。

跟 ISER-MoE 是同一方向的不同环节。

那篇治 MoE 读题的负载不均。

这篇治稀疏注意力读题的挑名次。

两篇合起来，DSA 模型的读题账本才算全。

还有两个数字能当标尺。

挑名次召回 100%，算没牺牲精度。

4100 万行 99.9% 完全一致，算落地靠谱。

术语表

  • DSA：DeepSeek 稀疏注意力，每行只细看挑中的 key
  • Indexer-TopK：索引器挑前 k，先打分再挑名次
  • HBM：高带宽显存，GPU 里的高速内存
  • sample-filter-select：采样估阈值、边算边筛、再终选
  • LiteDSA：相邻 query 复用重叠 KV 的稀疏注意力
  • DeepGEMM：DeepSeek 的矩阵乘法库，写打分表用的
  • DeepSelect：DeepSeek 的 top-k 选择库
  • GDN：门控增量网络，一种循环线性注意力
  • SM100：Blackwell 架构的计算单元代号
  • TTFT：首字延迟，第一个词吐出来要多久
  • CP：上下文并行，长上下文切开分给多卡算
  • 维度灾难：高维下距离都差不多，分数挤在一起

注意事项

  • 数字全是作者自报，没有第三方复现
  • SGLang 的 B300 数字是 PR 作者自报
  • 只在 B200 和 B300 上测了核
  • 短上下文走老路，16K 个 key 以下没收益
  • V4.1 只有 3 层用全 top-k 索引器
  • V4.1 端到端基本没变化，别指望它提速
  • 默认关闭，要开环境变量才生效
  • 核要 nvcc 13.4 以上才能编译
