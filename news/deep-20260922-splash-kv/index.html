SPLASH：把 KV 缓存搬进高带宽闪存，长上下文 decode 快 3.5–11.4 倍

原文：SPLASH: Co-Designing Sparse Attention with High-Bandwidth Flash for Efficient Long-Context Inference
作者：Aditya Anirudh Jonnalagadda 等（新加坡国立大学）
arXiv:2609.23816v1，2026-09-20（cs.AR）
链接：https://arxiv.org/abs/2609.23816
PDF：https://arxiv.org/pdf/2609.23816v1.pdf

一句话人话版

HBM（GPU 自带的高速显存）装不下长上下文的 KV 缓存（模型的草稿纸）。

这篇论文把草稿纸分两层放：常用的放 HBM，旧的放 HBF。

HBF 是高带宽闪存，一种紧贴 GPU 的新型闪存，容量 TB 级，读带宽接近 HBM。

再配一个懂闪存脾气的稀疏注意力（只看部分历史的注意力机制）。

结果：decode（逐字生成阶段）每卡吞吐涨 3.5 到 11.4 倍，精度损失不到 4%。

它解决什么问题

长上下文推理的瓶颈在 decode。

每个新 token 都要把全部历史 KV 读一遍，基本是在纯搬数据。

64 个 100 万 token 的请求同时跑。Qwen3-235B 的 KV 缓存要 12.9 TB。

光放这批缓存，就要 68 张 B200 的 HBM，模型权重还没地方放。

加卡扩容量行不通。decode 时算力本来就吃不满，加卡等于花钱买闲置算力。

老的分层方案（CPU 内存、CXL、SSD）带宽比 HBM 低两个数量级。

预取、切块这些技巧都救不回来，decode 直接变成搬运工。

HBF 是条新路。它把闪存堆在 GPU 旁边，TB 级容量，读带宽接近 HBM。

但闪存有三处怪脾气，软件必须迁就它。

第一，读的最小单位是页（4KB），不能像 HBM 那样按字节抠。

第二，单次读要几微秒，比 HBM 慢得多，得靠几千个 plane 并行才追得上。

plane 是闪存内部的独立读写单元，可以同时干活。

第三，写多了会坏（擦写寿命有限），只适合"写一次、读很多"的数据。

好消息：KV 缓存天生就是这个脾气。写进去就不再改，请求结束才释放。

图 1 人话解读。左图是各种存储技术的"位置图"。横轴是单位面积能塞多少容量，纵轴是每块芯片的读带宽。HBF（黑点加星标）落在右上角：容量密度接近闪存，带宽追上 HBM。右图是 Qwen3-235B 跑 64 个请求、100ms 延迟目标下的每卡吞吐。SPLASH（黑线）从 4K 到 1M 上下文几乎不掉。H3（在 HBF 上做稠密注意力，橙线）到 1M 掉了十几倍。纯 HBM（蓝虚线）16K 之后开始崩。1M 处 SPLASH 是纯 HBM 方案的 11.4 倍。

核心方法：算法、软件、硬件三层一起改

整套设计分三层（见图 2）。算法层管"看什么"，软件层管"放哪儿"，硬件层管"怎么读"。

  • 第一层，KV 缓存分家。每个请求的历史切两段：最近的窗口 W 放 HBM，更早的历史 H 放 HBF。
  • 窗口里放 attention sink（开头必看的几个 token）和最近的 token。
  • 第二层，decode 时两路并行。HBM 窗口做稠密注意力，HBF 历史做稀疏注意力。
  • 两路结果按注意力权重合并，公式是加权平均。
  • 第三层，页是基本单位。一个 4KB 页（BF16 精度）装 16 个 token。
  • 键和值分开存，配成 key 页加 value 页的对子。
  • 第四层，每页只存一个"代表"。代表叫 centroid（质心），是这一页所有 key 向量的平均值。
  • query 跟 centroid 点乘一次，就知道整页值不值得读。
  • 一次点乘代替 16 次，选页开销直接除以 16。
  • 存这些代表只多占 3.125% 的空间。
  • 第五层，选页只看预算。每层每个 KV 头只选 Kp 个页对，Kp 是历史页数的固定比例。
  • 预算花完就停，每步读多少数据完全可控。
  • 第六层，选页开销藏起来。centroid 扫描跟 HBM 窗口的注意力同时跑。
  • 扫描比窗口算得快时，GPU 根本感觉不到这笔开销。
  • 第七层，同类 token 住同页。token 在 HBM 住着时，系统悄悄记录"哪些 query 爱看它"。
  • 被同一批 query 看中的 token，挪进 HBF 时分到同一页。
  • 这样一页读出来，里面大多是有用的，不浪费带宽。
  • 实测这种分法比按位置分、按向量相似分都准。
  • 第八层，读的时候雨露均沾。选中的页摊到尽量多的 plane 上并行读。
  • 最忙的那个 plane 决定整轮延迟，所以每 plane 的读取数要封顶。
  • 第九层，地址翻译跟着 query 走。query 先算 centroid 分数，硬件查表得到页的位置。
  • 查到"页在哪个 plane 的哪个槽"后，再下发读命令。
  • GPU 只看到一块统一内存，闪存的物理细节全藏在底层芯片里。
  • 第十层，闪存只写一次。页的内容写定后不再搬家。
  • HBM 负责吸收新 token，攒满一批再整页写入 HBF。
  • 写放大（实际写入量除以有用数据）只有 1.15。

图 2 人话解读。这是 SPLASH 的总装图，分四行读。第一行算法层：decode 拆成 HBM 窗口的稠密注意力和 HBF 历史的稀疏注意力。第二行软件层：一个分层 KV 缓存管理器，对上呈现"一块逻辑内存"。第三行硬件层：GPU 左边连 HBM（DRAM 颗粒），右边连 HBF（NAND 颗粒）。各自的底层芯片里塞了地址路由、选择引擎和闪存管理逻辑。第四行执行流：GPU 做窗口注意力的同时，选择引擎在后台打分。打完分，HBF 把选中的页读出来。注意最后一行小字：选页和读闪存的开销，藏在窗口注意力的时间里。

关键数据

评测配置：5 个模型，上下文三档：128K、512K、1M。

模型是 Llama-3-8B、Mixtral-8x22B、DeepSeek-67B。还有 Llama-3-70B、Qwen3-235B。

每卡 8 叠 HBM 加 8 叠 HBF，共 192GB HBM 和 3TB HBF。

对比基线有 5 个：纯 HBM、H3、FlashAccel-CSI。还有 FlashAccel-CLI、LongSight-HBF。

延迟目标是 100ms 生成一个 token。每卡 decode 吞吐是各基线的 3.5 到 11.4 倍（几何平均）。

拆开看：纯 HBM 的 11.4 倍，H3 的 9.3 倍。FlashAccel-CLI 的 6.4 倍。

FlashAccel-CSI 的 5.8 倍，LongSight-HBF 的 3.5 倍。

目标收紧到 50ms，提升变成 8.9、7.3、7.2 倍。后两档是 6.2、4.5 倍，顺序同上。

Llama-3-70B 跑 1M 上下文，SPLASH 的 p50 延迟 68.8ms。p99 是 74.8ms。

同等负载下，FlashAccel-CSI 要 369ms。LongSight-HBF 要 255ms。其余基线直接跑不动。

15 组评测里，基线的单步解码耗时是 SPLASH 的 2.0 到 7.5 倍。

单步拆解：70B、128K 上下文、128 个请求。SPLASH 一步 85ms，其中读 HBF 只花 32ms。

FlashAccel-CSI 一步 373ms，是 4.4 倍。LongSight-HBF 245ms，是 2.9 倍。

精度：长上下文榜单上，SPLASH 得分是稠密注意力的 96% 到 101%。

PG-19 困惑度最多涨 0.04，基本可以忽略。

预算给到 2% 就够：六个 LongBench 任务里五个在只读 2% 历史时就追平稠密分数。

能耗：每焦耳生成的 token 数，是 H3 的 5.27 倍。是 LongSight-HBF 的 4.15 倍。

闪存读取占 SPLASH 总能耗的 51%，单字节 64pJ，HBM 是 22.5pJ。

硬件代价：选择引擎加查表逻辑占 9.67 平方毫米，是 HBF 底层芯片面积的 9.7%。

寿命测算：写放大取 1.15，3TB 的 SLC 闪存约 5 年寿命。

请求结束后保留 30 分钟再回收，测算寿命超过 5 年。

生产环境里请求的中位数只有 1.5K token，根本到不了 HBF。

143 万个 ChatGPT 请求里，只有 0.0008% 超过 16K token。没有超过 64K 的。

诚实短板：多针检索任务上，SPLASH 只恢复 0.50 的注意力。

Quest 是 0.62，稠密是 0.86。一页一个代表，在"满地找针"时确实会漏。

图 3 人话解读。横轴是 5 个模型各跑 128K、512K、1M 上下文。纵轴是每卡吞吐，以 SPLASH 为 1 归一化。深蓝条是 SPLASH，永远顶着虚线（SLO=100ms）。其他基线的条越矮说明越拉胯。纯 HBM（灰条）在 1M 处几乎看不见：它要 68 张卡才装得下，摊到每卡就没剩多少。注意：这是各自在 100ms 前沿取最优点再归一化。比的是每卡效率，不是绝对吞吐。

跟你的研究方向怎么挂钩

先说 P/D 解耦（把 prefill 读题和 decode 生成拆到不同机器）。

SPLASH 是纯 decode 侧优化，prefill 还是 HBM 里做稠密。两者正交不打架。

你的 decode 池如果上了 HBF，单卡吞吐涨 3.5 倍起。decode 侧要的卡数直接砍半。

再说 KV cache 优化。它跟 KVTC（那篇 20 倍压缩）是叠加关系。

一个把草稿纸压小，一个把草稿纸搬出 HBM、还少读。两招能一起用。

跟 py-kvcache 的结论放一起看最有意思。那篇说 NVMe 读盘可能不如重算。

因为 NVMe 带宽比 HBM 低两个数量级，读盘本身就不划算。

SPLASH 换了个前提：HBF 带宽接近 HBM，读盘本身划算了。

问题变成"读多少"，答案就是稀疏读。两篇合起来看，存储分层的盈亏线完全取决于带宽。

跟 CXL 那篇对照：CXL 是跨节点共享一块内存，解决"请求被甩到别处要重算"。

SPLASH 是单节点内扩容量，解决"一台机器装不下"。一个管共享，一个管容量。

一句话定位：长上下文 serving 的显存墙有三堵。SPLASH 拆的是"单卡容量"那堵。

而且是连硬件一起重新设计的拆法，不是纯软件 trick。

落地提醒：这篇是仿真评测（OpenHBF 模型），不是真实芯片。

定制底层芯片意味着短期内用不上，但思路值得先记下来。

术语表

  • KV cache：键值缓存，模型的草稿纸
  • HBF：高带宽闪存，紧贴 GPU 的闪存
  • HBM：高带宽内存，GPU 自带显存
  • decode：解码，逐字生成阶段
  • prefill：预填充，读题阶段
  • 稀疏注意力：只看部分历史的注意力
  • plane：闪存内的独立读写单元
  • page：页，闪存读写最小单位
  • centroid：质心，一页的平均向量
  • top-k：只取分数最高的 k 个
  • TPOT：每输出一个 token 的时间
  • FTL：闪存翻译层，管地址映射
  • 写放大：实际写入除以有用数据
  • P/E 次数：擦写次数，闪存寿命单位
  • SLC：单层存储，最耐用的闪存模式
  • GQA：分组查询注意力，共享 KV 头
  • attention sink：注意力汇点，开头必看 token
