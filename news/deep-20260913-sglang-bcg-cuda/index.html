SGLang 官方：给 CUDA 图装上"断路器"，prefill 图构建快 5 倍

原文：Breakable CUDA Graph in SGLang: 5× faster graph builds
出处：SGLang 官方博客（SGLang Team × Meta 合作），约 2026-09-10 发布
链接：https://www.sglang.io/blog/breakable-cuda-graph

一句话人话版

  • CUDA 图好比把 GPU 操作录成"一键回放"。
  • 录一次，之后直接回放，省掉 CPU 逐个启动 kernel 的开销。
  • 但 forward 里总有些算子不兼容，录不进去。
  • 以前的解法是 torch.compile 切分：慢，还得伺候编译器。
  • BCG 换了思路：捕获时直接"掐断"，图段之间留 eager 区。
  • 结果：prefill 图构建快 3.8–5.2 倍，代码还少了七成。
  • prefill 路径已经默认用它。

背景：为什么 prefill 一直难上 CUDA 图

  • decode 是逐 token 跑：形状固定，好录。
  • prefill 两个维度都在变：prompt 长度、请求的 token 归属。
  • CUDA 图要求两个维度都固定，所以 prefill 难录。
  • 还有 attention 后端依赖运行时元数据，录不进图。
  • 这是 prefill 长期只能用"可断开"方案的原因。

核心方法

BCG：捕获时直接掐断

  • 开发者用 @eager_on_graph 装饰器标记不兼容的函数。
  • 捕获跑到标记处：当前图段收口，标记函数正常执行。
  • 执行完继续捕获，开启新的图段。
  • 标记函数在捕获时跑一次，返回值留成"边界缓冲"。
  • 边界缓冲的设备地址固定，后续图段对着它捕获。
  • 回放时：标记函数正常跑出新 tensor，BCG 拷贝进边界缓冲。
  • 直观效果：eager 要 12 次 launch。
  • BCG 只要 4 次。

图注：同一份 forward，eager 模式要 12 次 kernel launch，BCG 切成图段后只要 4 次，完整 capture 只要 1 次。BCG 的秘诀就是用 @eager_on_graph 在捕获时直接切开，图段之间保留 eager 区。

老路为什么慢：编译器占了 78–86% 的时间

  • 老方案 tc_piecewise 先 trace 整个 forward。
  • 再在 FX 图上切分，每个分段编译加捕获。
  • 实测：准备 prefill 图的时间里，编译占 78–86%。
  • 模型越复杂，编译越慢，跟复杂度一起涨。
  • SGLang 一堆自研 CUDA、Triton、JIT kernel。
  • 这些不是原生 PyTorch 算子，编译器根本不认识。
  • 想让编译器认识：包一层 torch.library，再写 fake 实现。
  • 断点位置也受限：跨边界的输入输出必须是编译器能表示的类型。
  • BCG 干脆踢掉编译器：捕获执行到哪，就在哪切。
  • 同样的分段执行，代码从 1771 行砍到 521 行。

图注：冷启动时构建 prefill CUDA 图的时间。Qwen3-235B-A22B 上 BCG 27.7 秒、编译器方案 106.6 秒；GLM-5.2 上 BCG 35.2 秒、编译器方案 183.1 秒。测试条件：TP4、4×GB300、每配置 42 个形状。

调试：黑盒开了个"逃生门"

  • CUDA 图回放时是黑盒：Python 的 print、断言都进不去。
  • BCG 的 eager 区每次回放都正常跑 Python。
  • print、断点都能用，排查方便多了。
  • 再加 --debug-cuda-graph 开关。
  • 整个 decode forward 一键包成 eager。
  • 二分法：问题还在，就是模型的锅；问题没了，先查捕获。

更进一步：prefill 完整 capture（实验性）

  • BCG 每个断点都留一小段 eager，还是不够极致。
  • 完整 capture 把整个 prefill forward 录成一张图。
  • token 维度：用"桶"解决，pad 到最近的已捕获长度。
  • 请求维度：每张图预留固定请求槽。
  • 活请求占前几个槽，其余填零长度的哨兵。
  • 请求数超了预留槽：回退到 eager。
  • 目前只支持 FlashAttention(FA4) 和 FlashInfer。
  • 还是实验开关，生产环境官方推荐用 BCG。

图注：prefill 单独测速，相对 eager 的加速比。gpt-oss-120b 上编译器方案 1.45×、BCG 1.70×、完整 capture 1.93×；GLM-5.2 的稀疏注意力只有 BCG 能 capture（1.60×）。完整 capture 目前只支持 FA4/FlashInfer 且是实验性开关。

显存：图段切多了，内存不能跟着涨

  • 图切成 N 段，每段的中间结果都常驻，内存会膨胀。
  • 解法：图段按顺序回放，同一时间只跑一段。
  • 后一段可以直接复用前一段的内存。
  • 三招：所有图段共享一个 CUDA 图内存池。
  • eager 断点处用弱引用，不让 Python 引用拖长寿命。
  • 所有捕获尺寸共享一个最大输出缓冲，各取所需。
  • 78 层 MoE 的 GLM-5.2：42 个形状只多占 2.4 GB。

捕获上限：把显存峰值"拍扁"

  • 捕获一个形状，等于把它的瞬时峰值换成常驻内存。
  • 只换小的形状不划算：关键看捕获上限。
  • 上限设到 chunked_prefill_size。
  • 最大的 prefill 也能回放。
  • gpt-oss-120b：峰值从 0.56 GB 压到 0.001 GB。
  • GLM-5.2：从 1.55 GB 压到 0.35 GB。
  • 总显存反而比不用图还低：0.51 GB / 1.10 GB。
  • 附带好处：显存占用变成捕获时就定死的数。
  • 引擎可以提前算账，不用给大 prefill 留余量。

图注：把捕获上限设到 chunked_prefill_size 后，prefill 的峰值激活显存变化。gpt-oss-120b 从 0.56 GB 压到 0.001 GB，GLM-5.2 从 1.55 GB 压到 0.35 GB。总显存反而比不用 CUDA 图的 baseline 还低（0.51 GB / 1.10 GB）。

术语表

  • CUDA Graph：把一连串 GPU 操作录下来、一键回放的技术。
  • eager：PyTorch 默认的逐算子执行模式。
  • BCG（Breakable CUDA Graph）：可断开的 CUDA 图。
  • tc_piecewise：老方案，靠 torch.compile 切分。
  • launch：CPU 向 GPU 提交一次 kernel 执行。
  • TP4：张量并行，模型切成 4 份跑。
  • FX 图：torch.compile 的中间计算图表示。
  • FA4：FlashAttention 第 4 代。
  • chunked_prefill_size：分块 prefill 单次处理上限。
  • 哨兵（sentinel）：占位的零长度请求。
