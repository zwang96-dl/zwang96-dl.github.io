PrefixBench-H100：前缀复用在 H100 上到底赢在哪——缓存打平，调度定胜负

原文：arXiv:2609.19657 ｜ 作者：Omkar Shewale、Deepak Kumar、Divakar Kumar Yadav ｜ 入库 2026-09-17

人话解读

这篇论文干了一件实在事：同一块 H100 NVL、同样的请求流。 vLLM 和 TensorRT-LLM 贴身实测前缀复用。 TensorRT-LLM 是 NVIDIA 的推理引擎。 前缀复用（prefix caching）：重复出现的前缀只算一遍。 KV 缓存就是草稿纸，存着已算好的注意力中间结果，跨请求复用。 核心结论很反直觉：两个引擎的缓存本身一样好，命中率都约 92%。 谁更快，取决于请求怎么来。 请求一拥而上时，TensorRT-LLM 的中位数首 token 时间反超 2.4 倍。 流量平稳时，vLLM 的 p95（95% 的请求都比它快）反杀 9.2 倍。 说白了：缓存是标配了，胜负手搬到了它上面的调度器。

核心方法

  • 同一个负载驱动两个引擎，保证公平。
  • 用 OpenAI 兼容接口发请求，同一份 JSONL 工作负载。
  • 五个维度独立扫描：前缀长度、后缀多样性、并发、输出长度、缓存配置。
  • 两种工作负载：合成固定前缀、RAG 风格模板 trace。
  • 模型固定 Qwen2-7B-Instruct，FP8 权重。
  • 单卡 H100 NVL 跑完全部实验。
  • 指标：TTFT（首 token 时间）p50/p95、token 间延迟、端到端延迟。
  • 还有吞吐、缓存命中率、显存占用。

关键数据

  • 8192 token 共享前缀、并发 1。
  • vLLM：345.1ms 降到 53.0ms，加速 6.51 倍。
  • TensorRT-LLM：306.1ms 降到 58.2ms。
  • 加速 5.26 倍。
  • 两家缓存命中率都约 92%，统计上没有差别。
  • 跨引擎的差距是每请求的固定开销：vLLM 整条曲线低约 8ms，跟缓存无关。
  • 突发到达、并发 32：vLLM 的 p50 从 42ms 膨胀到 759ms。
  • TensorRT-LLM 只涨到 319ms，反超 2.4 倍。
  • 但此时缓存命中率两家都没掉：翻转是调度层的功劳，不是缓存。
  • 固定速率 16 QPS 的 RAG 负载下。
  • vLLM 的 p95 只比 p50 高 2-3ms。
  • TensorRT-LLM 的 p95 是自己 p50 的 7.1 倍。
  • 是 vLLM p95 的 9.2 倍。
  • TensorRT-LLM 的延迟分布是双峰的。
  • 在 200ms 和 1s 处各有一个调度台阶。
  • 工作集超过 KV 容量后：缓存重新成为瓶颈，两家一起慢。

术语表

  • TTFT（Time To First Token）：首 token 时间。
  • 就是用户敲回车到看到第一个字的时间。
  • p50 / p95：中位数 / 95 分位延迟，p95 专治"偶尔卡一下"。
  • 前缀复用（prefix caching）：重复前缀的 KV 缓存跨请求复用。
  • RAG 和 agent 场景的标配。
  • 突发到达（burst arrival）：请求一拥而上；固定速率（fixed-rate）：请求匀速到来。
  • tokens_per_block：缓存块大小，是 TRT-LLM 的一个调参旋钮。
  • 这篇测下来：调它基本没用。
