为什么 temperature=0 的推理还是不可复现？——"What Makes Inference Nondeterministic?"

  • 原文：Paolo Perrone, The AI Engineer (Substack), 2026-09-09
  • 原文链接：https://theaiengineer.substack.com/p/what-makes-inference-nondeterministic
  • 阅读方式：全文已读；3 张原文图已下载配中文图注

一句话人话版

temperature 设成 0 也保证不了"同样的输入得到同样的输出"——因为你请求到来的那一刻，服务器上还有多少别人家的请求在排队，会悄悄改变 GPU 做加法的"分组方式"，加法顺序一变，结果的末尾小数就变了，模型选出的词就可能跟着变。

核心机制：为什么"温度 0 + 固定 seed"都不管用

  1. GPU 从来不是一个数一个数往下加的。 一层模型里最长的向量求和（比如 4096 个数），GPU 会把它切成若干块，每块丢给一组核心并行算，最后再把各块的总和加起来。"切几块"由当前有多少工作量决定——工作量多就多切几块，让每个核心都不闲着。
  2. 请求来了多少 = 工作量 = 切块方式。 你的请求和同机房别的请求会被拼成一个 batch（批处理，凑在一起读一次模型权重，省显存带宽）。batch 里有 10 个请求和 30 个请求，切块方式就不同。
  3. 切块方式不同 = 加法顺序不同 = 和数不同。 计算机的小数只有固定位数，就像"3 位数天平上加 2kg 面粉再放一撮盐，盐根本显示不出来"。1e20 + 0.1 再减去 1e20 得到的是 0.0，而不是 0.1——顺序决定了小数字"死"在哪一步。
  4. 误差会沿着网络层层放大。 Attention、归一化、矩阵乘法全是长加法，第 1 层末尾小数的差异传到第 2 层输入，越传越大；到最后两层时，排第一和第二的候选词分差经常比这个误差还小——于是"谁是第一名"翻转了。
  5. seed 和 PyTorch 确定性开关为什么救不了你：seed 只管 temperature>0 时"从 top-k 里抽哪一个"的随机数，温度 0 根本没有这一步抽签；PyTorch 的确定性 flag 只保证"同样的运行条件再跑一遍一样"，但你两个 run 的条件本来就不一样（一个是安静的服务器、一个是忙的服务器）。
  6. 修复办法是存在的：batch-invariant kernel（"批次无关"内核）。 让内核"无论 batch 里有几个请求都按固定方式切块"，但代价就是小 batch 时大部分核心空转——vLLM 和 SGLang 都内置了这个开关，默认都是关闭的。

关键数据

  • Thinking Machines Lab 实测：同一个 prompt、同一个模型、temperature 0、普通 serving 环境下发 1000 个请求，得到 80 种不同的回答；前 102 个词全部一字不差，第 103 个词开始分叉。
  • 数字游戏：8 个能精确抵消的数（1, 0.01, 0.00001, 1e-10 及其相反数），理论总和是 0；40320 种加法顺序算出了 102 种不同的和。
  • 4096 个数的向量（= 模型每层求和的典型长度），只改切块方式、数都不变，255 次算出了 17 个不同的总和。
  • 确定性开关的价格：Thinking Machines 开启后每小时少处理 38% 的请求；SGLang 官方测出来每个请求多 24%–55% 延迟（见下图 3）。
  • vLLM issue #9567：一句话总结——量化版 Llama 3，温度 0，手动固定 batch size、排除流量干扰，只改 batch 大小，输出就变。问题在 serving 栈里，不在你的代码里。
  • MoE（混合专家）模型目前无解：vLLM 和 SGLang 的确定性模式都不覆盖 MoE（每次走不同专家分片）；TensorRT-LLM 压根没有这个模式——在那上面只有 batch size=1 才可复现。

原文关键图

图 1 人话解读：8 个明明能精确抵消的数（真和 = 0），换 40320 种加法顺序，算出了 102 种不同的答案——这不是 bug，这是浮点数加法本身的特性。模型每一层都在做上千次这样的长加法。

图 2 人话解读：这是整篇文章最妙的一张图。同样的 4 个数：左边只有你一个请求（batch size 1），GPU 按相邻两两分组加，结果和 = 0.0，选出 "safe"；右边多了 29 个路人请求（batch size 30），GPU 换了分组方式，结果和 = 0.15，选出 "safely"。唯一变的，是那一刻有谁在跟你共享服务器。

图 3 人话解读：SGLang 开确定性模式（Qwen3-8B、单卡、1k–8k 输入输出）：FlashInfer 后端多 24.4%–46.0% 延迟，FA3 多 27.2%–35.7%，Triton 后端多 44.6%–55.1%。注意"开 CUDA graphs 能追回大部分"：带 graphs 的确定性模式比不带 graphs 的快 2.79–2.93 倍——所以"定价"不能说一个数，跟 attention 后端实现强相关。

跟你研究方向的关联

  • 你正在评估 SGLang P/D 解耦、做 vLLM vs SGLang 框架选型实测（刚出的 H100 实测笔记）：这篇文章直接解释了为什么你的 benchmark 每次跑结果都有漂移——TTFT/吞吐曲线的"误差棒"，一部分来自并发/batch 变化，而不是框架本身。做 A/B 对比时要么固定并发和 batch 配置，要么开确定性开关再测，否则差 10% 级别的结论可能只是在测噪声。
  • vLLM v0.29.0（9 月 9 日刚发布）正好在补这块拼图：release notes 里专门有一节 Determinism——trace_decode_token_ids 确定性 decode 回放、每架构调优的 batch-invariant matmul 配置（RTX 4090D/H20 上约 3 倍 decode kernel）、Blackwell 自动调优带来 33.6% 端到端延迟降低、DP+EP 下的确定性 MoE combine（原文说 MoE 无解的部分已经开始被追上了）。升级 0.29.0 后做可复现 eval 更有抓手。
  • 一条实操铁律（原文的"坑"）：确定性开关是整批生效的——一个调用方想要可复现，同 endpoint 上的所有人都要一起付延迟税。所以可复现流量（eval、回归测试、安全审计）单独给一个 endpoint，聊天/生产流量保持默认关闭。
  • 什么时候该开：eval 评测、RL 训练回放、安全审计、回归测试、复现 bug；什么时候不开：聊天流量、草稿、coding、一切"两个好答案都行"的场景。

术语表

  • temperature（温度）：控制采样随机性的参数。temperature=0 表示"永远取打分最高的词"，而不是"输出完全确定"。
  • seed（随机种子）：随机数生成器的起点，管的是"抽签"环节的随机数；温度 0 时没有抽签环节，seed 无能为力。
  • batch（批次）：serving 引擎把同一时刻到达的多个请求拼在一起，一次读权重、并行算，省显存带宽。batch size = 一批里几个请求。
  • batch-invariant kernel（批次无关内核）：不管 batch 里有几个请求都按固定切块方式做加法的 GPU 内核；固定了加法顺序 → 结果可复现。
  • continuous batching（连续批处理）：请求做完一个就出、新的立刻补进来，batch 大小动态变化——这也是"条件"永远不一样的原因。
  • eval / 回归测试：用固定测试集衡量模型表现的流程；不可复现的 serving 会让"case 41 挂了一次又过了"这种灵异事件成常态。
