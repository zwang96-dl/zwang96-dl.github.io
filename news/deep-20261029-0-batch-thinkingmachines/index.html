温度设 0 结果还飘？真凶是 batch 大小在变

原文：Thinking Machines Lab《Defeating Nondeterminism in LLM Inference》
作者：Horace He（PyTorch 核心开发者，2026 年 3 月从 Meta 加入 Thinking Machines）
原文链接：https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/
开源代码：https://github.com/thinking-machines-lab/batch-invariant-ops

一句话人话版

温度设成 0，vLLM 照样每次吐出不一样的答案。 大家都怪浮点数和 GPU 并发，这篇说都怪错了。 真凶是 batch 大小：你的请求每次跟不同数量的请求拼一批。 拼法一变，算子内部的切分策略就变，结果就飘了。

核心观点：四句话讲清确定性

下面四句话同时成立，听着绕，但理顺了就通了。

  1. GPU 上的 kernel 大多是 run-to-run 确定的。
  2. LLM 前向用的 kernel 全是确定的，没有 atomic add。
  3. 推理服务器的前向也是确定的：同样的请求集合，输出永远一样。
  4. 但对单个用户来说，服务器永远不确定。

为什么？因为你不知道这次跟谁拼了一批。 服务器忙时你的请求跟 100 个请求拼，闲时跟 10 个拼。 batch 大小一变，算子的切分策略就变，结果就飘了。

*图1：确定性系统的定义。同样的请求进来，永远得到同样的输出。这是数学上对确定性的要求，也是这篇要达成的目标。*

*图2：为什么推理服务会飘。你的请求没变，但同批的其他用户请求变了。batch 大小一变，你的结果就跟着飘。*

核心方法：batch-invariant kernel 三件套

只有归约（reduction）操作会破坏 batch 不变性。 Transformer 里就三个：RMSNorm、矩阵乘法、注意力。 pointwise 操作天生 batch 不变，不用管。

1. RMSNorm：一个 batch 元素只用一个核心

理想策略是 data-parallel：每个 batch 元素分给一个核心。 归约全在一个核心内部做完，batch 大小不影响归约顺序。 batch 变大没关系，核心排队处理多行就行。 batch 变小会出事：核心比行多，有人没活干。 工程师本能会拆分归约（split reduction）来喂饱核心。 但一切分，归约顺序就变了，batch 不变性就丢了。

*图3：小 batch 时的 split-reduction RMSNorm。把一行的归约拆给多个核心并行，核心喂饱了，但归约顺序变了，batch 不变性就丢了。*

2. 矩阵乘法：一个配置打天下

思路一样：把输出切成 2D tile，每块分给一个核心。 归约（K 维度）全在核心内部，不跨核心通信。 M、N 太小喂不饱 GPU 时，常规做法是 split-K。 split-K 把归约拆到多个核心，batch 一变切分就变。 stream-k 更极端，连 batch 内的位置都不保。 解法很直接：编译一个 kernel 配置，所有形状都用它。 代价是性能掉约 20%（相对 cuBLAS），作者认为可以接受。

3. 注意力：固定切块大小，先排好 KV

注意力有两个 matmul，难点多两个。 一是归约维度多了序列维度。 二是 chunked prefill、prefix caching 会把序列切成几段。 vLLM 的 Triton attention 把 KV cache 和当前 token 分开算。 KV 里 80 个、当前 48 个，块边界对不上，归约顺序就变了。 解法：进 attention kernel 之前，先更新 KV cache 和 page table。 让 key/value 的排布跟处理多少 token 无关。 decode 阶段 query 很短，喂不饱 GPU，得用 split-KV。 常规 split-KV 按块数均分，batch 一变切分就变。 FlashInfer 的 balanced 调度更糟：按能喂饱核心的最大块切。 解法是固定切块大小：KV 长 1000，就切三块 256 加一块 232。 块数随 batch 变，但每块内部的归约顺序永远不变。

*图4：固定切块大小的 split-KV 策略。KV 按固定 256 切块，块数随 batch 变，但每块内部的归约顺序永远不变，batch 不变性就保住了。*

关键数据

  • Qwen3-235B-A22B，温度 0，同一 prompt 跑 1000 次。
  • 蹦出 80 种不同的 completion，最常见的只出现 78 次。
  • 前 102 个 token 全一样，第 103 个开始分叉。
  • 992 个生成"Queens, New York"，8 个生成"New York City"。
  • 开 batch-invariant kernel 后，1000 次结果完全一致。
  • 性能：Qwen3-8B 单卡，vLLM 默认 26 秒，确定性版 55 秒。
  • 优化 attention kernel 后降到 42 秒，作者说还能接受。
  • RL 实验：确定性采样让训练和采样数值完全一致。
  • KL 散度恒为 0，真 on-policy，不用 importance weighting 救场。

跟你的研究方向的关联

你在评估 PD 解耦，精度门是硬指标。 这篇给你加了一条：batch 大小本身就是精度变量。 PD 下 prefill 和 decode 的 batch 形状天天变。 chunked prefill 一开，序列切几段也是变量。 锁精度口径时，batch 档位要写进测试矩阵。 不然今天过的精度门，明天换个并发就飘了。 反过来想：这也是"静默算飘"，跟静默算错清单是姊妹篇。 一个是算错了不报错，一个是算飘了不报错。

术语表

  • batch invariance（批不变性）：batch 大小变化时，单个请求的结果不变。
  • run-to-run determinism：同一份输入跑两次，结果 bitwise 一致。
  • atomic add（原子加）：多核心同时往同一地址加，顺序看谁先跑完。
  • split-K：矩阵乘法把归约维度 K 拆给多个核心并行。
  • split-KV / FlashDecoding：注意力把 KV 维度拆给多个核心并行。
  • data-parallel 策略：按 batch 维度切分，每个核心算完整的一行或一块。
  • FlexAttention：PyTorch 的可编程注意力接口，这篇用它替换算子。
  • on-policy RL：训练用的数据分布和当前策略完全一致。
