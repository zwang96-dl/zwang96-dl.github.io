Dynamo：把显存跟引擎进程解耦，故障恢复压到 7 秒内

原文：Fast Recovery for LLM Serving via Decoupled Device Memory Lifetime in Dynamo（arXiv:2609.25451，2026-09-21，16 页 12 图）
开源：ai-dynamo/dynamo 和 ai-dynamo/snapshot
一句话版本：服务进程挂了，GPU 和显存其实没坏。这篇把显存所有权从进程里抽出来，恢复时直接"复用"，不用重装整个引擎。

人话解读

在线推理服务最怕的是什么。 引擎进程崩了，整个副本要重新初始化。

模型权重重新加载、CUDA 上下文重建、通信组重建。 8 卡 B200 上跑 vLLM 0.27.1，这一套要几分钟。

NVIDIA Research 团队看了一眼生产数据，发现一个事实。 18 周的 Dynamo 集群故障里，大多数是"设备保留型"的。 翻译一下：进程死了，GPU 本体和显存里的分配完好无损。

类比一下：厨师晕倒了，厨房和食材都在。 你不需要重盖一间厨房，只需要换个厨师进来。

所以这篇的核心思路就一句话。 把显存的"房本"从引擎进程手里拿出来，放到独立服务里。 进程崩了，显存还在；新引擎直接接管，不用重装。

对你意味着什么：你在 SGLang 上做 P/D 解耦评估。 解耦部署的组件越多，故障域越多。 这篇就是解耦部署的"可靠性拼图"。 恢复时间跟模型大小无关，只跟固定开销有关。

核心方法

  • GMS（GPU Memory Service）：显存管家。
  • 独立进程管每卡显存。
  • 引擎只映射使用，不拥有。进程崩了，物理分配还在。
  • 权重只读共享：加载器把权重写进 GMS 页，提交后锁成只读。替换引擎和 Shadow Engine 都只读映射同一份，不复制。
  • Snapshot（快照，拍好的系统照片）：捕获已初始化好的引擎。
  • host 进程用 CRIU（Linux 进程快照工具）拍。
  • CUDA 状态用 cuda-checkpoint 拍。
  • 这是 NVIDIA 的快照工具。
  • 恢复就是"复用"，不用重装。
  • 新引擎进口旧的 GMS 分配。
  • 只读映射到原来的虚拟地址。
  • 权重完全不用重载，跳过最慢的一步。
  • Shadow Engine（影子引擎）：替补队员。
  • 同一 GPU 上再跑一个初始化好的引擎。
  • 平时停车不干活，只占一点点显存。
  • 影子不占 KV 显存：它只保留虚拟地址占位，不占物理 KV 页。主引擎挂了，影子装上新的 KV 页就上岗。
  • 恢复等于"晋升"：影子转正，主引擎的请求重新回放一遍。被打断的请求会重放，调度器需要重建。
  • 三层恢复路径：先试影子晋升，再试快照恢复，最后才走慢速重启。一层比一层慢，一层比一层兜底。
  • 还有个 FSM（状态机，带锁的借还规则）。
  • 模型页有"已提交"和"只读"两种状态。
  • 谁在读谁在写，规矩写死。

关键数据

  • 恢复压到 7 秒内。
  • 4 个模型 × vLLM/SGLang，全部 4.6–6.2 秒。
  • 比 warm restart 快 13–29 倍。
  • 最惨的对比：DSV4-Pro（DeepSeek-V4-Pro）。
  • vLLM 上 warm restart 要 156.5 秒。
  • GMS 加影子引擎后只要 5.4 秒，快 29 倍。
  • SGLang 上也一样。
  • Qwen3.8-27B 从 79.6 秒压到 6.2 秒。
  • GLM-5.2 从 144.6 秒压到 5.7 秒。
  • 代价是固定的：每卡多占 4–8 GiB 显存。跟模型大小无关，小模型也一样交这个"停车费"。
  • Figure 9 的分解：4.3 GiB 到 8.1 GiB。
  • 大头是引擎私有的运行时状态。
  • 权重反而没占多少，不用复制。
  • 18 周生产 trace 回放。
  • 5,762 次原地恢复，丢了 2,967 个 GPU 小时。
  • 这套方案能抢回其中 79%。
  • 集群规模：783 张 B200。
  • 再加 135 张 RTX PRO 6000。
  • 每副本 8 卡，约 150 个并发副本。
  • 快照单独用不够。
  • 只用快照不用 GMS，大模型恢复反而更慢。
  • DSV4-Pro 快照要 189.7 秒。
  • warm restart 只要 156.5 秒。
  • 瓶颈在 CUDA 恢复。
  • cuda-checkpoint 是串行拷贝。
  • 它吃不满 PCIe 带宽。
  • 权重常驻 GMS 后，这部分开销直接消失。
  • 影子补给不打扰服务。
  • 用快照给新影子"补位"。
  • 服务中 TTFT/ITL 几乎无感。
  • 比 warm restart 补位快得多。

跟你研究方向的关联

P/D 解耦评估里，故障恢复是必答题。 prefill 池、decode 池、KV 传输链路。 任何一个环节挂了，都要能快速回来。 这篇给的是现成答案：7 秒内恢复，跟模型大小无关。

GMS 的显存解耦思路跟 KV 搬运直接相关。 P/D 解耦要在 prefill 和 decode 之间搬 KV。 GMS 这种"跨进程共享显存页"的机制，就是搬运的底层拼图。 NIXL 搬的是网络，这篇搬的是同一卡上的所有权。

你在 MI350 单卡上跑 vLLM 吞吐基准，也可以借鉴。 单卡没有多副本容错，进程一崩就是全停。 Shadow Engine 的思路在单卡上同样成立。 4–8 GiB 固定开销，换 7 秒恢复。 MI350 显存大，这个"保险费"交得起。

跟 9/20 的 SPLASH 笔记对照看。 SPLASH 把 KV 缓存往闪存分层，这篇把显存所有权从进程解耦。 两篇都在回答同一个问题：显存到底该归谁管。

术语表

  • GMS（GPU Memory Service）：独立管显存的服务进程。显存的"房本"归它，引擎只是租户。
  • device-preserving（设备保留型）：进程死了，GPU 没坏。
  • 这种故障最常见。
  • 显存分配也完好无损。
  • 这种故障占生产故障的大多数。
  • Snapshot（快照）：拍好的系统照片。初始化完的引擎整体打包，恢复时直接"还原"。
  • CRIU：Linux 进程快照工具。把运行中的进程冻结打包。
  • cuda-checkpoint：NVIDIA 的 CUDA 快照工具。
  • 备份 GPU 上的分配和内容。
  • Shadow Engine（影子引擎）：提前初始化好的替补引擎。平时停车，主挂了立刻转正。
  • warm restart（热重启）：缓存是热的重启。
  • 但引擎要完整重初始化。
  • 比冷启动快，仍要几分钟。
  • TTFT：从请求到达，到第一个 token 出来的时间。
  • ITL：相邻两个 token 之间的间隔。决定"吐字"流畅度。
  • KV cache（键值缓存）：解码时存的"草稿纸"。避免每个 token 都重算注意力。
  • FSM：有限状态机。这里指 GMS 模型页"谁可读谁可写"的借还规则。
  • XID：NVIDIA 驱动报的 GPU 错误码。用来判断故障是保留型还是损毁型。
