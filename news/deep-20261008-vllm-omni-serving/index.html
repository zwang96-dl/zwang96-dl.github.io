vLLM-Omni：vLLM 官方给多模态 serving 造了个"统一调度器"

原文：https://arxiv.org/abs/2610.09307 vLLM-Omni Team，2026-10-07 提交，技术报告，34 页。

人话解读

  • 以前 vLLM 只干一件事：文字接龙。
  • 现在语音助手、画图、机器人全来了，每种活节奏都不一样。
  • 有的要一句话一句话往外蹦（自回归），有的要反复打磨几十步（扩散）。
  • 以前各搭各的，部署全靠手搓胶水代码。
  • vLLM-Omni 就是官方出的统一版：一个总调度，什么模态都接。

核心方法

  • 一切皆流水线：每个 workload 拆成多阶段 pipeline。
  • stage（阶段）= 一个模型组件 + 一个执行引擎 + 一份资源预算。
  • 语音助手拆成三段：thinker（想词）→talker（发音）→声码器（出波形）。
  • 总调度叫 orchestrator（编排器），只干四件事：接单、推进、流式输出、收尾。
  • 它不管 stage 内部怎么算 token，也不管 paged KV 和扩散去噪。
  • 好比项目经理只排工期，不管工人怎么砌砖。
  • 控制面和数据面分开走。
  • 轻信令（调度指令、元数据）走 orchestrator。
  • 重数据（hidden states、KV 块、latents）走 OmniConnector 专线。
  • 控制环不会被大 tensor 堵死。
  • KV 交接是"特种货物"，有专门通道。
  • P/D 解耦时，前后 stage 标成生产者/消费者。
  • KV 走 Mooncake 这类专线搬家。
  • 文生图时，AR 阶段的 KV 取出来，扩散模型当 past_key_values 接着用。
  • Session（会话）是一等公民。
  • 长对话、世界模型、机器人这种"不断线"的活，有专门状态机管生命周期。
  • 请求完成的定义是"所有模态都吐完了"，不是"到最后一个 stage"。

关键数据

  • 评测跑在 H100 上（TTS 和 MiniCPM-o 在 H200），主力是 Qwen3-Omni。
  • 异步分块（async-chunk）是最大单项优化，并发 32 时：

- 首字延迟 3420ms → 508ms，约 6.7 倍。 - 端到端 136.6s → 72.6s。

  • TTS 优化配置：CosyVoice3 并发 8 时，实时率 RTF 1.657 → 0.129。
  • RTF 小于 1 表示生成比播放快，越小越好。
  • 画图：Qwen-Image 512²/20 步，单流约 2.4 秒。
  • Cache-DiT 复用去噪中间结果，延迟和并发双收。

术语表

  • orchestrator：总调度，只管"下一个 stage 跑谁"，不管 stage 里怎么算。
  • stage：流水线上的一个工位，模型组件+引擎+资源预算三件套。
  • OmniConnector：传重数据（tensor）的专线，类比工厂传送带。
  • Mooncake：跨节点传 KV 的高速方案，P/D 解耦搬 KV 的"货车"。
  • async-chunk：异步分块，上游没算完就先把算好的块往下游送。
  • past_key_values：attention 算过的 KV 缓存，接着用不用重算。
  • DiT：Diffusion Transformer，画图和视频的主力结构。
  • VLA：视觉-语言-动作模型，机器人用的那种。
  • OpenPI：机器人 serving 的开放接口标准。
  • RTF：实时率，小于 1 表示生成比播放快。
