Agent 会话的草稿纸，留在显存里才划算

一句话

Agent 每轮都把整段历史重发一遍。

工具一跑，历史就被缓存踢出显存。

回来又得全重算，一半的活都在白干。

留着会话的草稿纸，回来得快就赚大了。

人话解读

Coding agent 的工作方式很固定。

先把整段对话发给模型。

模型回一个工具调用，比如跑命令、改文件。

Agent 跑完工具，把结果贴回对话。

再把整段对话重新发一遍。

中位数 60 轮，历史能长到几万个词。

每一轮，引擎都要拿到整段历史的 KV 缓存。

KV 缓存就是算过的历史草稿纸。

如果上轮的缓存还在显存里。

这一轮只算新增的几个词就行。

如果缓存被踢出去了。

整段历史得从头再算一遍。

vLLM 和 SGLang 都有前缀缓存。

前缀缓存就是把算过的开头先存着。

但它们不知道这个请求还会回来。

Agent 等工具的那半秒，在缓存眼里就是闲置。

内存一紧，历史就是最先被踢的那个。

踢掉容易，回来重算的代价却很大。

作者自己写了个 Rust 引擎，约 1700 行。

会话是一等公民，KV 缓存按会话留着。

跨会话还能共享公共前缀。

新会话进来之前，先看显存还装不装得下。

装不下就先不接，这叫会话级准入。

核心方法

  • 工作负载是真实轨迹，不是合成数据。
  • 24 个 coding agent 会话，共 791 轮。
  • 来源是 SWE-rebench-OpenHands 数据集。
  • 每轮生成 256 个词，忽略结束符。
  • 三个引擎做同样的活，方便横向比。
  • 模型是 Qwen3-8B，BF16 精度。
  • 一张英伟达 L40S，KV 缓存统一 173200 个词。
  • vLLM 是 0.33.0，SGLang 是 0.5.23。
  • 工具等待固定三档：0.5 秒、5 秒、60 秒。
  • 0.5 秒接近实测的工具调用中位数。
  • 每种配置跑两遍，波动看得见。
  • 每个策略改动前，先写下通过标准。
  • 看到结果再改标准，这事作者明令禁止。

关键数据

表 1：24 个会话全跑完的总时间，单位秒，越小越好。

SGLang 0.5.23 LRU2013 / 20482179 / 21544069 / 4154
SGLang 0.5.23 TLRU2067 / 20242121 / 21524078 / 4093
Rust 会话引擎1506 / 15861868 / 19084083 / 4011

0.5 秒档，Rust 引擎比最强基线快 1.31 倍。

比 vLLM 快 1.45 倍，两次运行都赢了全部基线。

5 秒档，优势缩到 1.13 倍，比 vLLM 快 1.24 倍。

60 秒档，全部引擎差距在 2% 以内，基本打平。

表 2：首字延迟中位数，和重算历史的占比。

0.5 秒档，vLLM 首字中位数 28.6 秒。

SGLang LRU 是 35.0 秒，TLRU 是 36.3 秒。

Rust 引擎只有 4.5 秒，快约 5 倍。

重算历史占比上，vLLM 是 55%，SGLang 约 51%。

Rust 引擎只有 7.5% 到 15.6%。

5 秒档，Rust 引擎首字 5.1 秒，重算 19% 到 23%。

基线首字 25 到 29 秒，重算还是过半。

60 秒档，Rust 引擎首字 11.5 到 13.8 秒。

反而比 vLLM 的 3.5 秒慢，重算占比也回到 55%。

作者的解释是准入规则在排队。

基线先到先得，Rust 引擎让新会话等。

等工具的会话少了，队列本来就短。

留缓存的收益没了，排队的代价还在。

三条固定策略，全都没跑赢基线。

固定钉 30 秒：60 秒档重算 85%，比 vLLM 慢 1.3 倍。

按工具自适应钉：60 秒档比 vLLM 慢 1.6 倍。

首字 P90 超过 4 分钟，闲置会话堵住了新请求。

加了上限的钉：60 秒档只比 vLLM 慢 3% 到 4%。

还是没过作者自己定的通过线。

最后是跨会话共享前缀，起了关键作用。

60 秒档从慢 3% 到 4%，扳回平手。

5 秒档从 2097 秒降到 1888 秒。

还有一个诚实数字：Rust 引擎本身并不快。

纯解码比 vLLM 慢 15% 到 21%。

赢全靠少干活，不是核跑得快。

跟研究方向的关联

这篇跟前缀缓存评估直接对口。

Agent 场景下，缓存的命题变了。

不再是命中率越高越好。

而是会话回来之前，缓存能不能活着。

三个数字可以直接进评估清单。

第一是重算历史占比，超过一半就是报警线。

第二是工具等待时间，0.5 秒和 60 秒是两个世界。

第三是首字延迟中位数，agent 场景下它比总时间更敏感。

两个检查手段也可以直接抄。

vLLM 开 --enable-prompt-tokens-details。

SGLang 开 --enable-cache-report。

都能看到每个请求复用了多少词。

复用率过半，说明一半的钱花在重算上。

PD 解耦评估也能借这篇的思路。

读题卡和解码卡分开之后。

会话的草稿纸该放哪边，值得单列一项。

解码卡上留着会话，读题卡只算增量。

这正是 P/D 解耦想省的那部分。

还有一个提醒：TLRU 只比 LRU 好约 1%。

TLRU 是一种优化的淘汰策略。

在真实 agent 轨迹上，它几乎没拉开差距。

换淘汰策略之前，先看重算占比。

占比没下来，换策略也是白换。

局限与提醒

  • 只测了一个模型：Qwen3-8B。
  • 只测了一张卡：英伟达 L40S。
  • 只测了一种负载：24 个会话同时跑。
  • 工具等待是固定的三档，没测混合分布。
  • 真实工具调用有长尾，短和长的一起来。
  • 没测 CPU 卸载：LMCache 和 HiCache 都没上。
  • 没测 SGLang 的流式会话，可能缩小差距。
  • TLRU 的配置没按作者推荐的方法调。
  • vLLM 和 SGLang 拒绝超过 32768 词的提示词。
  • Rust 引擎不拒绝，多跑了两三轮。
  • 两次运行的波动最高 7.7%，方差没刻画全。
  • 数字全是作者自报，单机实测非线上服务。

术语表

  • KV 缓存：算过的历史草稿纸，存着下轮复用。
  • 前缀缓存：把算过的开头存着，相同开头直接复用。
  • LRU：最久没用的先踢掉，一种淘汰策略。
  • TLRU：按尾巴优化的淘汰策略，先踢会话尾部。
  • 首字延迟：从发请求到收到第一个词的时间。
  • P90：90% 的请求都比这个数快。
  • 会话级准入：新会话进来前，先看显存装不装得下。
  • 固定钉：会话缓存强制留在显存一段固定时间。
  • 跨会话共享：不同会话共用相同的公共前缀。
  • BF16：16 位浮点格式，省显存、精度略低。
  • L40S：英伟达一张数据中心显卡。
