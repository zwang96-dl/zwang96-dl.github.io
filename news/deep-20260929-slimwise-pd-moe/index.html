SlimWise：prefill 用完整模型，decode 用"瘦身版"——MoE 推理的 P/D 分工新思路

原文：SlimWise: Decoupling Expert Pruning Across Prefill and Decode for Efficient MoE Serving（arXiv:2609.34117，2026-09-28；作者 Gunho Park 等，KAIST；基于 vLLM 实现，支持 P/D 解耦与同机部署两种模式）

一句话人话

MoE 是混合专家模型：一群"专家"分工，每次只叫醒几个。

推理时 decode 阶段要反复搬运专家权重，带宽先顶不住。

SlimWise 的点子很直白：分阶段用不同大小的模型。

prefill（读提示词、一次性算完的阶段）用完整模型保质量。

decode（逐 token 往外吐的阶段）用剪枝后的"瘦身版"提速。

KV 缓存就是模型的"草稿纸"，存着已算好的注意力状态。

它直接交接，不用转换，免训练。

核心问题：剪枝剪错了地方

MoE 每个 token 只激活少数专家。

但 decode 时 batch 一大，几乎所有专家都会被摸到一遍。

专家权重反复从显存搬运，成了 decode 的头号瓶颈。

专家剪枝就是砍掉不常用的专家，能降搬运量。

但传统做法 prefill 和 decode 一起剪，等于一刀切。

问题是 prefill 是计算密集型，剪它省不了多少时间，白白丢精度。

说白了：以前是"一刀切"，该瘦的地方没瘦，不该瘦的瘦了。

核心方法：三件套

1. 分阶段配专家容量：prefill 全量，decode 瘦身

prefill 保留全部专家，保证提示词表示的质量。

decode 只留子集，专家权重搬运量直线下降。

论文测了 25%、50%、75% 三档剪枝。

每个 token 激活的专家数 k 不变。

路由（决定每个 token 找哪个专家的"调度员"）逻辑不用改。

2. KV 缓存免转换交接：剪枝不改变"草稿纸"格式

关键洞察：专家剪枝只动 MoE 的专家池，不动 attention 结构。

所以 prefill 生成的 KV 缓存，decode 端拿来就能用。

一个字节都不用转。

作者管这叫 KV cache handoff。

全程 training-free，不用重新训练。

类比一下：完整版厨师备好菜，瘦身版厨师接着炒。

备菜单不用重写，直接沿用。

3. 两套部署形态都支持

P/D 解耦模式：prefill 和 decode 拆到不同机器上跑。

decode 机器只加载剪枝后的 checkpoint。

省下权重显存，KV 缓存容量更大，batch 能开更大。

同机模式：全量专家常驻显存，专供 prefill 用。

decode 时用"阶段感知路由掩码"，只走保留的专家。

代价是掩码操作每步多约 0.5ms，占 decode 单步 2.5%–5%。

4. 低成本蒸馏：修"答对了但话变多/变少"的毛病

论文发现一个坑：只看 benchmark 分数，剪枝好像没掉点。

但生成行为变了：有的任务推理链变短（答得敷衍），有的变长（啰嗦）。

解法是轻量蒸馏（distillation：让小模型模仿大模型的输出分布）：

  • 训 decode 端从"完整模型的 KV 缓存"接着生成
  • 只更新极小一部分参数。
  • Qwen3.6 上动 0.4%，Gemma-4 上动 2.1%。
  • 每个模型约 8000 步，B200 上约 6 小时

蒸馏后生成长度回到完整模型的水平，精度再往上补一截。

关键数据

实验模型：Qwen3.6-35B-A3B、Gemma-4-26B-A4B。

基于 vLLM 实现。

  • 50% 剪枝：decode 吞吐最高 1.81 倍（P/D 解耦）。
  • 同机部署是 1.36–1.72 倍。
  • 75% 剪枝：1.65–2.39 倍（P/D 解耦）。
  • 同机部署是 1.57–2.28 倍。
  • 精度：五个 benchmark 平均分基本持平。
  • 覆盖 HE+、MBPP+、GSM8K、MATH-500、BFCL。
  • SLO（服务等级目标：每用户每秒 token 数）越严格，相对收益越大
  • 蒸馏成本：只动 0.4%–2.1% 参数，6 小时 B200

一句话：decode 提速近一倍，精度几乎不掉，代价是一次 6 小时的轻量蒸馏。

跟你的研究方向的关联

你正在评估 SGLang 的 P/D 解耦。

这篇是"解耦之后还能怎么玩"的直接答案。

P/D 解耦把两个阶段拆到不同机器。

SlimWise 证明：decode 端完全可以用更小的专家子集。

换句话说：解耦不只是"分开部署"，还可以"分开配模型容量"。

思路可以平移到你的 MI350 评估。

prefill 侧保质量，decode 侧砍专家权重搬运。

注意：论文基于 vLLM 实现，SGLang 上复现要自己动手。

局限与提醒

作者自己列了两条：

  • prefill 还是得用完整模型跑，prefill 本身的成本一分没省
  • 同机部署时全量专家常驻显存，模型权重占的显存没省下来

另外 75% 剪枝档的精度在部分任务上有可见下滑，50% 档是最稳的甜点。

术语表

  • MoE：混合专家模型，很多专家分工，每次只激活几个
  • prefill：读提示词、一次性算完的阶段，计算密集
  • decode：逐 token 生成的阶段，访存密集，瓶颈在搬数据
  • KV cache：模型的"草稿纸"，存已算好的注意力键值
  • P/D 解耦：prefill 与 decode 拆到不同实例/机器上跑
  • 专家剪枝：砍掉不常用的专家，降权重搬运量
  • router：路由器，决定每个 token 分给哪个专家
  • training-free：免训练，不用重新训练模型
  • 蒸馏：让小模型学习大模型的输出分布
  • SLO：服务等级目标，如每用户每秒 50 token
  • TPOT：每个输出 token 的耗时
