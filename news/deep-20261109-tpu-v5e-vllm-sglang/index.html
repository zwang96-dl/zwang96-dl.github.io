六引擎同台：一块 TPU v5e 上 vLLM 与 SGLang 谁更快

原文：xbill《Six Serving Engines on One Cloud TPU v5e Chip: Gemma 4 E2B》，2026-11-09 发布

原文链接：https://xbill999.medium.com/six-serving-engines-on-one-cloud-tpu-v5e-chip-gemma-4-e2b-7d767dd0c521

一句话：同一块小芯片上，SGLang 高并发赢 2.5 倍。

vLLM 稳得多。

人话解读

一个人把六个推理引擎，放在同一块谷歌 TPU v5e 芯片上跑。

模型是 Gemma 4 E2B，只有 20 亿参数。

芯片也小，一张卡只有 15.75 GB 显存。

结果很有意思。

一个请求时，大家差不多。

SGLang-JAX 最快，每秒 159.9 个词。

vLLM 是 143.9 个词，Rust 写的模型是 145.2 个词。

差距不到 12%。

请求一多，差距就拉开了。

64 个请求一起上，长回复那档。

SGLang-JAX 每秒 4249 个词。

vLLM 是 1689 个词。

SGLang 快了 2.52 倍。

但别急着下结论。

SGLang 这次赢，是打了补丁的。

它本来跑不了 E2B 这个模型。

作者给它写了 190 行补丁才跑起来。

而且它跑五次，结果能差两倍。

vLLM 五次跑下来，波动不到 5%。

说白了，SGLang 是上限高、下限也低。

vLLM 是上限低一点，但每次都一样稳。

还有一个冷知识。

vLLM 是唯一能返回工具调用的引擎。

函数调用测试 BFCL 上，vLLM 拿了 0.920 分。

其他引擎直接交白卷。

核心方法

作者的思路很干净：只换引擎，其他全锁死。

每台引擎独占一块 v5e 芯片。

同一机房、同一型号、同一批任务。

六个引擎分别是 vLLM、SGLang-JAX、纯 JAX 引擎。

还有 Rust 模型和 TorchTPU。

TorchTPU 分 Python 版和 Rust 版。

模型全是 Gemma 4 E2B。

vLLM 跑的是 4 位量化版。

SGLang-JAX 和 JAX 系跑半精度版。

权重不一样，这是这篇最大的口径缺口。

解码方式全是贪心，思考模式关掉。

每台引擎跑三组任务。

第一组是六个聊天问题，测单请求速度。

第二组是 1 到 64 个请求的压测，两种形状：短进长出、长进短出。

第三组是 GSM8K 的 1319 道数学题，测答题准不准。

每台机器跑完就自毁，数据先上传再删卡。

这套流程的好处是：没人能挑硬件不公平。

关键数据

单请求速度，四个引擎咬得很紧。

SGLang-JAX 每秒 159.9 个词，排第一。

Rust 模型 145.2 个词，vLLM 143.9 个词。

JAX 引擎 134.3 个词。

TorchTPU 完全掉队。

Python 版 6.6 个词，Rust 版 13.4 个词。

首字延迟最短的是 Rust 模型，只有 9.4 毫秒。

SGLang-JAX 反而最慢，20.2 毫秒。

高并发是 SGLang-JAX 的主场。

128 词进、512 词出，64 请求时它每秒 4249 个词。

vLLM 是 1689 个词，差距 2.52 倍。

512 词进、128 词出，64 请求时它是 2758.9 个词。

vLLM 是 1288.4 个词，差距 2.14 倍。

但低并发时它反而落后。

2 个请求、长进短出那档，它只有 117.4 个词每秒。

vLLM 是 257.4 个词，反超它一倍多。

波动是 SGLang-JAX 的软肋。

同样一档跑五次，它最慢和最快能差 49% 到 205%。

vLLM 的波动最多 5%。

答题准确率上，SGLang-JAX 也领先一点。

GSM8K 它拿了 0.9143 分，vLLM 是 0.9007 分。

差距 0.0136 分，95% 置信区间在零以上。

半精度引擎普遍比 4 位量化引擎高约 1 个点。

启动时间差了一个数量级。

vLLM 要 31 到 34 分钟，编译每个请求形状。

SGLang-JAX 有缓存时 270 秒。

全新机器上每个读题形状约 5 分钟。

Rust 模型只要 22 秒。

还有一个坑：vLLM 加投机解码的草稿模型后。

单芯片上预热就显存爆炸，直接跑不起来。

最后是跨硬件对照。

同一套测试在英伟达 L4 卡上也跑过。

单请求时 v5e 是 L4 的 1.06 倍。

64 请求时只剩 0.81 倍和 0.46 倍。

小芯片扛高并发，先天吃亏。

跟研究方向的关联

这篇跟你的引擎选型直接对口。

你正在 H100 和 MI350X 上评估 vLLM 和 SGLang。

这篇的结论别直接搬。

它跑的是 TPU v5e 单芯片、20 亿小模型。

你的卡和模型都比这大得多。

但方法论可以直接抄。

第一，同卡同权重同 prompt 再比。

这篇最大的口径缺口就是权重不一致。

vLLM 跑 4 位量化，SGLang-JAX 跑半精度。

你的评估清单里，权重版本必须先锁死。

第二，压测要报重复波动。

SGLang-JAX 中位数好看，单次能差两倍。

只报中位数，会把不稳定的引擎报成赢家。

你的评测要像这篇一样，报五次的散布。

第三，别只看峰值倍数。

SGLang-JAX 在 64 请求时赢 2.52 倍。

2 个请求时反而输给 vLLM。

你的 PD 解耦评估要按并发分档。

低并发和高并发各一张表。

第四，启动成本要进账。

vLLM 编译要 34 分钟。

你调参时一天重启几十次，这个时间全是成本。

第五，工具调用是 vLLM 的独家优势。

你的 agent 类负载要走函数调用。

SGLang-JAX 这次直接交白卷。

术语表

  • TPU v5e：谷歌第五代推理芯片的节能版，单芯片 15.75 GB 显存。
  • Gemma 4 E2B：谷歌 20 亿参数的开源小模型，带多模态能力。
  • SGLang-JAX：SGLang 跑在 JAX 上的版本，专为 TPU 优化。
  • GSM8K：1319 道小学数学题，常用来测模型答题准不准。
  • BFCL：伯克利函数调用排行榜，测模型会不会调工具。
  • 贪心解码：每步只取概率最高的词，不随机采样。
  • 首字延迟：从发请求到第一个词出来，要等多久。
  • 4 位量化：把模型权重压到 4 位存，省显存、掉一点精度。
  • 草稿模型：投机解码里先写草稿的小模型，大模型只负责改。
  • 压测波动：同一档跑多次，结果最慢和最快差多少。
