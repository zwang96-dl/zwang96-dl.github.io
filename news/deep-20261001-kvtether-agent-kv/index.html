KVTether：Agent 的 KV 缓存，不该只懂 LRU 该懂"谁死了"

原文：https://arxiv.org/abs/2609.39819 作者：Kaihua Fu、Yukun Zhou（共同一作，HKUST） 单位：HKUST、阿里巴巴、上海交大 日期：2026-09-30

人话解读

Agent（ReAct，边想边调工具那种）跑起来，KV 缓存是最贵的账单之一。 一个 Codex 请求能攒到 258K token 上下文。光 KV 就要 93GB。 留着费钱，扔了又得重算 prefill，所以缓存管理很关键。

但有个结构性问题。Agent 框架管的是"消息"：append、替换、删、fork。 serving 层只看到一串 token 和 KV 页。根本不知道哪段 KV 已经"死了"。 结果两种浪费一起出现。

浪费一：僵尸 KV（zombie KV）。 消息逻辑上已经死了，KV 还占着显存。 比如压缩子 agent 把长历史换成摘要，旧历史和一次性压缩上下文都死了。 它们的 KV 却要等 LRU 被动淘汰。 实测：僵尸 KV 最高占掉 LMCache 36.3% 的容量。 LMCache 是一个开源 KV 缓存方案。

浪费二：淘汰方向搞反了。 LRU 按"最近用过"排序，以为新产生的 KV 最近会被复用。 但 Agent 里新产生的 KV 往往在等工具执行，离复用还远。 老 KV 反而更快被下一次 LLM 调用命中。 实测三条生产 trace 上，LRU 71.0%–95.0% 的淘汰都杀错了对象。 实际 KV 命中率：LMCache 只有 28.1%。MORI 也只有 39.8%。 MORI 是一个 agent 感知的缓存方案。

一句话：缓存层看不懂应用层的"生死簿"，LRU 只能瞎忙。

核心方法

三层设计（对应原文 Figure 7，从上到下）：

第一层：语义原语模型。 不给每个 Agent 框架打补丁，而是抽出统一的消息操作原语。 六个原语：Append、Delete、Pin、Spawn、Truncate、One-off。 Codex、SWE-agent、OpenCode，加上 Hermes、Agent-G、OpenClaw，都对得上。 每家接入要改 26–216 行代码。

第二层：事件驱动的生命周期管理器。 把消息级事件翻译成 KV 级的生命周期状态。 比如 fork 子 agent，父子上下文各记各的寿命，共享 KV 两边都保留。 消息一改，后面 KV 全得重算。这叫 prefix dependency（前缀依赖）。 这里统一处理。

第三层：状态优先的 KV 淘汰引擎。 淘汰顺序按状态排优先级，不再只看"最近用没用过"。 死掉的 KV 主动删，不用等 LRU 慢慢挤。 活着但暂时闲置的 KV 优先保住。 非得在活 KV 里杀一个时，用 MRU（最近挂起的最先杀），跟 LRU 反着来。 道理：刚挂起的 KV 大概率在等工具，老 KV 反而先被复用。

开销很小：原语记录每次不到 100 微秒。 每次 LLM 调用前通知缓存引擎不到 50 毫秒。 256K token 输入的解析约 350 毫秒。单次 LLM 调用 19.96 秒，只占 2.0%。

关键数据

对比 LMCache 和 MORI。 三条 trace：Agent-X、Agent-G、Codex。用了 12 张 GB200。

  • KV 命中率：比 LMCache 高 33.3 个百分点。比 MORI 高 24.5 个百分点。
  • 累计 prefill 时间：比 LMCache 降 29.2%，比 MORI 降 23.3%。最高 41.2% / 33.2%。
  • 端到端延迟：比 LMCache 降 16.5%，比 MORI 降 12.4%。最高 26.3% / 17.4%。
  • 单任务价格：按 DeepSeek-V4-Pro 费率估算。平均降 40.0% / 33.2%。最高 53.6% / 44.1%。
  • 杀错方向比例：三条 trace 上从 65.6% / 75.0% / 92.3%。降到 38.7% / 25.7% / 38.6%。

高负载下差距拉大。Agent-X 最高请求率时，LMCache 命中率掉到 10.2%。 KVTether 还能保住 49.5%。

原文关键图表

图注：compaction（把长历史压缩成摘要）、message append（追加消息）、subagent call（fork 子 agent）三种典型操作下，消息分长期、短期、临时三类。长期消息跨调用一直复用。短期消息被替换或删除前复用。临时消息本次调用完就过期。应用层看得清清楚楚，但传到 KV 层只剩一堆 token，"谁死了"没人知道。

图注：最上层从各家 Agent 框架（Codex、Claude Code）抽出统一语义原语（Append、Delete、Pin、Spawn、Truncate、One-off）。中间事件驱动的生命周期管理器做语义事件追踪，把消息级事件翻译成 KV 级生命周期状态（Active、One-off、Pin、Discarded）。最下层淘汰引擎按状态优先级管理 KV 页，死 KV 主动删（Proactive Delete），活 KV 按状态保。

图注：Agent-X、Agent-G、Codex 三条生产 trace，四个指标：KV 命中率、累计 prefill 时间、端到端延迟、单任务价格。蓝色 KVTether 在三条线里几乎全线最优。注意 Agent-X 那行：负载一高，LMCache（橙色）的命中率直接塌掉，KVTether 还稳得住。

跟你的研究方向的关联

跟 P/D 解耦是互补关系。 解耦是把 prefill 和 decode 物理分开，各干各的。 KVTether 解决的是另一头。Agent serving 下，KV 缓存"认错人、杀错人"。 两边都落地，serving 链路才完整。

你评估 SGLang 的 prefix caching 时可以直接借鉴两点。 第一，淘汰策略别只看 LRU，Agent 场景下 MRU 反而更准。 第二，zombie KV 主动回收的思路，可以做进缓存容量规划里。

做 AI 自动调参系统的话，lifecycle 状态是个现成的信号。 它比"最近访问时间"更能预测 KV 的真实复用价值。

术语表

  • ReAct：推理+行动循环的 Agent 范式，LLM 和工具调用交替进行。
  • Zombie KV：逻辑上已死、物理上还占着缓存的 KV。
  • Wrong-direction eviction：杀错方向的淘汰。被杀的 KV 比新进来的更早被复用。
  • Semantic primitive：语义原语。Agent 框架对上下文的操作抽象。
  • MRU：最近最少优先淘汰的反面，最近用过的先杀。
  • Prefix dependency：前缀依赖，中间的消息一改，后面所有 KV 都得重算。
  • LMCache：开源的 KV 缓存共享方案，用 LRU 淘汰。
  • MORI：一个 agent 感知的 KV 缓存方案，按工具调用时间排优先级。

一句话总结

KV 缓存管理缺的不是更聪明的淘汰算法，是应用层的"生死簿"。 把消息生命周期传进来，LRU 杀错 9 成的问题直接少一半。
