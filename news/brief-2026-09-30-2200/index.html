  • DLFP：prefill 和 decode 抢资源的"软件解法"。
  • 场景你很熟：正在吐字的请求，被新来的长 prompt 一卡，全机顿一下。
  • 业界通用做法是 prefill 切块。
  • 但块大小得人肉调，模型一换就得重调。
  • DLFP 不建模，直接看延迟：实测延迟超标，下一块就切小一点。
  • 富余了就放大一点。像开车只看油表，不预测油耗。
  • 只在"有 decode 在跑"时生效。
  • 没 decode 就随便跑，保住吞吐。
  • 实测：Qwen3-0.6B，单张 A100。
  • 最卡的 1% token 间隔降了 27.7%。
  • 三轮降幅：24.8%、30.1%、28.2%。
  • SLO（服务等级目标）300 个请求全过。
  • 代价：首字延迟涨 34.8%，但还在 SLO 线内。顺滑了，第一个字慢一点。
  • 翻车也写得很诚实：8B、32B 和双卡上全不灵。
  • 根因：反馈信号拿"调度器调用间隔"冒充 GPU 真实耗时。
  • 大模型上这个信号失真了。
  • 「值得深读」：中文精读笔记已生成。
  • 含控制律公式、Table 1 和 Figure 1。
  • 跟你研究的 P/D 解耦是同一道题：解耦是物理分开，这篇是软件限流。
  • 论文：https://arxiv.org/abs/2609.38386
  • 共享 KV 缓存有个"认错人"的坑。
  • 很多生产部署把 KV 缓存做成机群共享层。
  • key 只按 token 内容算。
  • 但同一个 token 串，adapter（微调适配器）不同。
  • 算出的 KV 完全不一样。
  • 共享层只看 token 不看"出身"，就会张冠李戴。
  • 实测很吓人：跨 adapter 撞 key。
  • 准确率从 0.94 掉到 0.64。
  • KV 表示不兼容时，推理准确率直接归零。
  • 更狠的是计时攻击。
  • 93% 的 prompt 能从访问时间被反推出来。
  • 作者在 vLLM 和两版 SGLang 上都复现了。
  • 覆盖 12 个模型、160 多种配置。
  • 解法是给每个缓存条目打"出身标签"，key 里带上计算和共享上下文。
  • 一句话：上了共享 KV 缓存的，key 设计要回炉检查了。
  • 论文：https://arxiv.org/abs/2609.38706
  • KV 缓存往闪存下沉那派，又添一篇系统级实测。
  • 思路是分层：HBM 放热数据，高带宽闪存（HBF）放冷数据。
  • 还给了个"带缓冲的缓存感知调度"，专门伺候闪存的写入寿命。
  • 实测：加了闪存的系统，完成时间比纯 HBM 快 36.1%–87.0%。
  • 建模的能耗最多省 55.8%，但轻负载下闪存反而更费电。
  • 调度优化后，闪存写入寿命从 4.77 年延长到 14.82 年。
  • 一句话：跟 20 点版忆联/英特尔白皮书同路，这篇是学术版的量化对照。
  • 论文：https://arxiv.org/abs/2609.39131
  • PatchKV：KV 压缩的新思路，把信息"藏"进权重里找补。
  • 现有压缩法（丢 token、近似）一到激进压缩比就掉精度。
  • PatchKV 免训练：上下文加载时算一个"权重补丁"。
  • 岭回归闭式解，一次搞定。
  • 补丁合进模型后，每次推理的计算图不变，单上下文多查询零额外开销。
  • 在 170K token 上下文、四个基准上都测了。
  • SCBench、SQuAD、NIAH、GSM8K 全覆盖。
  • 覆盖三个模型架构。
  • 结论：各种压缩法配上它，在激进压缩下都更稳。
  • 一句话：KV 压不住了别只盯缓存，权重里也能"藏"上下文。
  • 论文：https://arxiv.org/abs/2609.39329
  • UBTree：投机解码的草稿环节，出了个并行新打法。
  • 背景：小模型先打草稿，大模型批量验证，草稿对了就加速。
  • 但目标分布越"发散"，草稿越难中，并行草稿器的效果就掉。
  • UBTree 两步走：unigram（一元模型）提候选。
  • bigram（二元模型）负责选搭配。
  • 搭出一棵草稿树。
  • 训练时不只盯贪心路径，分支也给监督信号。
  • 验证时更容易多收几个 token。
  • 实测：Qwen3-4B/8B，7 个基准。
  • 相对自回归解码平均加速 5.84–6.94 倍。
  • 28 组对比全胜 DARTree，生产级评测也赢了 DSpark。
  • 一句话：草稿质量看"树"不看"链"，想上投机解码的可以看一眼。
  • 论文：https://arxiv.org/abs/2609.39972
  • 消费级多卡跑 MoE（混合专家模型），通信是个大头。
  • MoE 每个 token 激活多个专家，专家分散在多卡上，每层都要通信。
  • 消费级 GPU 没有 NVLink，卡间通信都得经过 CPU 内存中转。
  • 现有库都假设 GPU 能直连。
  • NCCL 在这种机器上有多余的 PCIe 搬运。
  • 还跟专家计算抢资源，越跑越亏。
  • ThunderEP 专为 PCIe 消费级卡设计。
  • 去掉 ring 算法的中转跳数。
  • 用 DMA 引擎搬数据，不跟计算抢资源，同步轮询的开销也压低了。
  • 接进 vLLM，在 4090/5090 系统上测了三个 MoE 模型。
  • 分发和合并通信，比 NCCL 快 2.00 倍和 1.53 倍。
  • 端到端最高 1.66 倍。
  • 一句话：家用多卡玩 MoE 的，通信库换这个思路能榨出不少。
  • 论文：https://arxiv.org/abs/2609.40093
