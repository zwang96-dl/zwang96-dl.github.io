SGLang 的 PD 排队坑：等太久，前缀被淘汰，吞吐雪崩

原文链接：https://github.com/sgl-project/sglang/pull/46812 合并时间：2026-10-28 01:22 UTC（20点版窗口内） 硬件口径：GB300，PR 作者实测

人话解读

  • 这条讲 PD 解耦的一个雪崩坑。
  • PD 解耦就是读题吐字分工。
  • prefill 负责读题算草稿。
  • decode 负责一个字一个字吐。
  • 草稿纸就是 KV cache。
  • 它记着算过的中间结果。
  • 坑出在两队人中间的等候区。
  • 请求要先在等候区排队。
  • 等 decode 那边腾出空位。
  • 排队时没人管它的前缀。
  • 前缀就是能复用的老草稿。
  • 等太久，前缀就被淘汰了。
  • 轮到它时只能重算或外搬。
  • 越重算越慢，队排得越长。
  • 队越长，淘汰得越多。
  • 这是一个自己喂自己的死循环。
  • 修法就是排队时也续命。
  • 定期碰一下它的前缀。
  • 告诉缓存：这个还有人等。
  • 崩塌工况下吞吐涨了 59%。
  • 健康工况下基本没变化。

核心方法

背景：等候区叫 bootstrap 队列

  • PD 里请求分两步入场。
  • 先去 prefill 那边报到。
  • 再等 decode 预留出槽位。
  • 槽位就是 decode 的座位。
  • 等座位的队列叫 bootstrap 队列。
  • 英文全名是解耦启动队列。
  • decode 满员时它最长。
  • 作者实测每队排约 300 个。
  • 每个请求要等约 100 秒。

坑在哪：续命名单漏了等候区

  • SGLang 本来有个续命机制。
  • 它定期碰一下排队请求的前缀。
  • 碰一下就是刷新时间戳。
  • 缓存按最久没碰的先淘汰。
  • 这套机制英文叫 LRU。
  • 说白了就是先扔最旧的。
  • 但老机制只碰正式队列。
  • 等候区里的请求没人碰。
  • 它们的前缀就默默变旧。
  • 然后被当成垃圾淘汰掉。
  • 轮到执行时扑了个空。
  • 只能去外层缓存重新搬。
  • 外层是 Mooncake 的 L3。
  • L3 是更远的一层草稿仓库。
  • 搬不到就只能从头重算。

修法：等候区也进续命名单

  • 调度算优先级时多带一个队列。
  • 把等候区也交给续命那一步。
  • 先碰等候区，再碰正式队列。
  • 等候区一次最多碰 512 个。
  • 正式队列的顺序没有变。
  • 它们的时间戳仍然最新。
  • 碰前缀这个动作很便宜。
  • 它不分配新缓存。
  • 它也不去外层仓库查。
  • 只改淘汰顺序，不改结果。
  • 作者明确说精度不受影响。
  • 关续命的总开关仍然有效。
  • 非 PD 的服务完全不受影响。
  • decode 那边也完全没动。

跟你的研究有什么关系

  • 你正在评估 SGLang 的 PD。
  • 这坑只在 PD 形态下出现。
  • 触发条件有三个。
  • decode 先成为瓶颈。
  • 请求要在等候区久等。
  • 前缀总量撑满本机缓存池。
  • 三个凑齐才会雪崩。
  • 常规压测很难凑齐。
  • 会话数不够就复现不出来。
  • 作者用了 7480 个并发会话。
  • 还是多轮智能体的轨迹。
  • 你的负载是短请求高并发。
  • 约 250 词元，多请求共享前缀。
  • 共享前缀正是 radix 的菜。
  • radix 是前缀复用的缓存树。
  • 你评估时要专门造一档。
  • 让 decode 先满员堵住。
  • 再看前缀命中率掉不掉。
  • 命中率从 65% 掉到 22%。
  • 这就是雪崩的报警信号。
  • 只看总吞吐会发现得太晚。
  • 建议把命中来源拆开看。
  • 本机命中和 L3 搬运分开记。
  • 这条跟你那份 PD 清单互补。
  • 清单里可以加一项。
  • 等候区请求的前缀谁续命。

术语表

  • PD 解耦：prefill 和 decode 分开部署。
  • bootstrap 队列：等 decode 槽位的队列。
  • KV cache：草稿纸，存中间结果。
  • 前缀：多请求能复用的老草稿。
  • radix cache：按前缀组织的缓存树。
  • LRU：先淘汰最久没用过的。
  • L3：Mooncake 的外层缓存层。
  • TTFT：等到第一个字的时间。
  • DEP：数据并行加专家并行的组合。
