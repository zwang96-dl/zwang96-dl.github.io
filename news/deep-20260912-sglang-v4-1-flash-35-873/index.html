SGLang 官方实战：DeepSeek-V4.1-Flash 从 35 干到 873 tokens/s

原文：DeepSeek-V4.1 Flash on SGLang: from 35 to 873 tokens/s
出处：SGLang 官方博客（SGLang Team），2026-09-10 发布
链接：https://sglang.io/blog/deepseek-v4.1-flash-kernel-optimization

一句话人话版

新模型刚在 SGLang 上跑起来，只有 35 tokens/s。

SGLang 团队一轮轮抠 kernel，16 步干到 873.6。这篇是官方的"调优实录"：每步改了什么、涨了多少，全写明白了。

想给 SGLang 接新模型的人，直接照抄作业。测试条件：BS=1，4 张 GB300，attention 走 TP4。

背景：V4.1-Flash 长啥样

  • 它是"因果编码器-解码器"结构（encoder 先啃 prompt，decoder 再生成）。
  • 主干 552B 参数，另加 196B 的 Engram 记忆参数。
  • 每 token 只激活约 8B（输入侧）/16B（输出侧）。
  • 20 层编码器 + 20 层解码器。长 prompt 主要过前 20 层。
  • 所以 prefill 计算量直接砍半。生成时每个 token 还是要过全部 40 层。
  • 全局 KV cache 只有 890 字节/token，是 V4-Flash（3514 字节）的约四分之一。
  • 40 层里只有第 2/8/14/20 层产出全局 KV，其余层复用。
  • 前三层把 2 个 token 压成 1 条 KV（pooling，池化压缩）。
  • KV 条目存成 FP4（4 位浮点，极致省显存）。
  • CSA2（稀疏注意力 v2）：分层过滤候选，最后只让 top-512 个全局位置参与 attention。

核心方法

第一阶段：朴素 decode，35.2 → 203.3

第 1 步：FP8 GEMM 走快速通道（单步涨幅最大）

  • 部分稠密权重是 FP8 格式（8 位浮点）。
  • 但它的量化块和 scale 排布跟后端对不上，GEMM（矩阵乘法）走了慢速 fallback。
  • 改法：权重加载时一次性重排 scale，直接进 Blackwell 的 MXFP8 GEMM。
  • 效果：35.2 → 117.8 tokens/s。
  • 教训：新模型上线，先查每个 GEMM 实际 dispatch（派发）到哪个 kernel。
  • 这比调 tile 尺寸管用得多。

第 2 步：小算子融合（把短 kernel 焊在一起）

  • decode 逐 token 跑，一长串短 kernel：RoPE、FP4 量化、池化、RMSNorm、写 cache。
  • 相邻的 fuse（融合）成一个，省一次启动 + 一次显存往返。
  • RoPE + FP4：旋转、量化、反量化合一，117.8 → 133.5。
  • C2 压缩器：归一化、池化、写状态合一，148.4 → 152.1。
  • WO-A + norm + Engram 门：GEMV（矩阵乘向量）+ 小 norm/门控合一，186.6 → 203.3。
  • 每层重复建的请求索引和 scratch buffer 改成跨层共享，146.5 → 148.4。

第 3 步：mHC 的重叠执行

  • mHC（多残差流混合机制）：每层维护 4 条残差流。
  • 每个 attention/MoE 子层都要算混合系数，再做 Sinkhorn 归一化。
  • 单看都不贵，但每层跑两次，小 batch 下积少成多。
  • 统计量 reduction（归约）和 Sinkhorn 融合：133.5 → 141.1 → 146.5。
  • 更大的一招：单遍 mHC 里，pre-mix 用的是上一子层的系数。
  • 所以本子层的 attention/MoE 可以和本子层的统计量计算并行跑。
  • 两个 CUDA stream 分开跑，post-mix 处汇合：152 → 186。

第二阶段：DSpark 投机解码，558.24 → 873.63

  • DSpark：DeepSeek 官方的投机解码方案，draft 权重随 checkpoint 一起发布。
  • 3 个轻量 draft 块（草稿模型），从主模型最后几层的 hidden state 取输入。
  • 一次产出多个位置的 logits，Markov head（马尔可夫头）解决 draft 间的依赖。
  • 主模型批量验证（verify），接受的前缀直接提交。
  • 配置：block size 5，模拟接受长度 5.5（accept length，平均每步接受几个 token）。
优化步骤tokens/s
DSpark 未优化558.24
+ verify/MoE 融合与重叠718.75
+ 小 batch 投影 / mHC 融合761.71
+ indexer 后处理 / Q RoPE / WO-A 量化融合802.38
+ C2 verify 压缩融合853.49
+ MoE 从 EP4 切 TP4 + padding873.63
  • 关键细节：

- M=1 的快速路径要为 verify 的小 batch 重写（单请求 6 行）。 - router（MoE 路由器）直接吐出 expert 需要的排布。 - 输入量化与路由重叠执行。 - expert 加权归约 + shared expert 相加 + all-reduce 三步并一步。 - WO-A 用 split-K（拆 K 维），让更多 thread block 同时干活。 - indexer 后处理（Top-K 后检查、非法位置过滤、KV 页地址翻译）合成一步。

  • 最后一哆嗦：MoE 从 EP4（专家并行）切到 TP4（张量并行）+ padding。

- expert 中间维度每卡 576，padding 到 640 对齐 kernel。 - 同轮对比：EP4 854.64 → TP4 873.63，提升 2.22%。 - 各 rank 到达 finalize 的中位时间差从 11.14μs 降到 3.40μs。

两个诚实声明

  • 以上数字都没用 DeepSeek 随 V4.1 新发的 kernel，还有上探空间。
  • 接受长度是模拟的，生成文本不评质量。测的是 BS=1 decode 速度，不含完整 prefill。

术语表

  • GEMM：通用矩阵乘法，decode 里最吃算力的部分。
  • dispatch：实际调用了哪个 kernel 实现。
  • fusion（融合）：把相邻小算子合成一个 kernel。
  • GEMV：矩阵乘向量，batch=1 时投影层的形态。
  • mHC：V4.1 的多残差流混合机制，每子层维护 4 条残差流（原文未展开全称）。
  • Sinkhorn：一种归一化算法，这里用来归一化混合系数。
  • DSpark：DeepSeek 官方投机解码方案，draft 权重随 checkpoint 发布。
  • accept length：投机解码每步平均接受的 token 数。
  • split-K：把 K 维度拆开，让更多 thread block 并行。
  • EP / TP：专家并行 / 张量并行，MoE 的两种切分方式。
  • padding：把维度补齐到 kernel 喜欢的对齐数。
  • pooling（池化）：多个 token 的 KV 压成一条。

复现信息

  • 代码：BBuf/sglang@835c3909（dsv4.1 相关分支），checkpoint 用 revision dba1be0a。
  • 环境：4×GB300，PyTorch 2.13.0+cu130，FlashInfer 0.6.18，Triton 3.7.1。
  • 启动：--tp 4 --ep-size 1，--speculative-algorithm DSPARK --speculative-dspark-block-size 5。
  • 输入：固定种子 42 的 4096 随机 token，输出 1024 token，temperature=0。
  • 每个配置测 6 轮，关键配置独立起两次、12 轮取中位数，测吞吐时关掉 profiler。
