ServeTwin：分布式 serving 架构先"沙盘推演"，不用真机

  • 原文：ServeTwin: A Benchmark-Validated Simulator for Distributed LLM Architecture Exploration
  • 作者：Sungjoon Park、Changue Jung、Kyungno Joo、Mincheol Kang、Jaehyung Ahn、Sehwan Lee、Sangjoon Kim（三星 SAIT，三星综合技术院）
  • 链接：https://arxiv.org/abs/2610.02732v1
  • 发布：2026-10-02（arXiv），cs.PF

一句话人话

想知道某种 P/D 解耦配置跑起来多快，不用先买卡。

ServeTwin 是个"沙盘"：输入模型+引擎+硬件规格，直接算出吞吐和延迟前沿。

跟实测只差 3.6%，准到可以当决策依据。

解决什么问题

评估分布式 serving 架构，真机实测贵得离谱。

现有仿真器只有"半套功夫"，三缺一。

  • 解析式模型（GenZ、LLMCompass）：只看静态工作负载，不懂排队和反馈。
  • 事件仿真器（LLMServingSim、Vidur）：调度做得像，但死活要先在目标硬件上实测 profiling 数据。
  • 更糟的：P/D 解耦这类新架构，老仿真器干脆当"一段直管道"处理。

这篇举了个翻车例子（Figure 1）。

LLMServingSim 在 33 GiB KV 预算下跑多轮任务，45 秒就直接 abort。

原因很蠢：它没给"等着的 KV"留状态，多轮请求进不了 decode 就崩了。

ServeTwin 跑完 141 秒，还把容量演变全过程复现了。

说白了：老工具连"排队等位"都不会，仿真结果没法信。

核心方法

1. 闭环状态仿真：请求完成反过来改调度

  • 核心洞察：serving 是个"反馈环"。
  • 本轮迭代的硬件耗时，决定下一轮的批次组成。
  • 批次变了，队列深度和 KV 占用又变了，下一轮耗时跟着变。
  • 固定 batch 的开环模型，这个环直接断了。
  • ServeTwin 每轮都推进：仿真时钟 + 系统状态一起更新。
  • 类比：像玩回合制游戏，每回合的战果决定下回合的布阵。

2. iSTAGE：不用目标硬件的"算时"引擎

  • iSTAGE（解析式 trace 生成器）是第二个主角。
  • 输入只有三样：模型规格、引擎规格、硬件规格。
  • 从这三样直接算出每步耗时，不需要去目标卡上实测。
  • 闭环里的三大坑，它逐个填：
  • 坑一：serving 的 batch 天生"参差不齐"，硬垫成矩形会把耗时高估 146 倍。
  • 解法：统计保持的 batch 绑定，矩形近似但保住分布形状。
  • 坑二：理论 FLOPS 和带宽算不出真实耗时，CUDA graph padding、KV 翻页、kernel 发射这些离散机制才是大头。
  • 解法：把引擎的离散机制显式建模进去。
  • 坑三：每轮都算一遍 trace 太慢，端到端仿真跑不动。
  • 解法：trace 大量复用，轻到能塞进仿真循环里跑。

3. 成本归属账本：耗时拆三类，各归各的"主人"

  • 总耗时拆成三类成本，每类只归一个组件。
  • T（吞吐成本）：GPU 计算、访存、网络搬运，归"硬件+模型"。
  • S（调度成本）：CPU 调度开销、CUDA graph padding，归"引擎调度器"。
  • R（运行时成本）：KV 遍历、kernel 发射间隙、集体通信同步残余、P→D 交接，归"运行时机制"。
  • 归属不清的参数，一律不许靠曲线拟合。
  • 好处：换硬件只重校准 T 相关的，调度参数原封不动搬过去。
  • 类比：修车时分清"发动机问题"还是"变速箱问题"，不用整车重拆。

4. P/D 解耦的显式建模：KV 交接是"容量驱动"的

  • Figure 3 是这篇跟你关系最深的一张图。
  • prefill worker 算完 KV，先"暂存"（staged KV）。
  • decode worker 显存有空位时，主动 pull（拉取）过来。
  • decode 侧满了怎么办？背压（backpressure）自然压回 prefill。
  • 请求不准进，乖乖在队列里等。
  • 交接不是"算完就推"，而是"有空才拉"，这是 Dynamo/NIXL 一派的做法。
  • KV 在系统里有显式生命周期状态机：分配→暂存→常驻→淘汰/降级。
  • 跟简单"管道切一刀"的模型比，这套能仿出真实的排队和反压动态。

关键数据

  • InferenceX 吞吐-交互性前沿：DeepSeek-R1 FP8（671B MoE），8×H200。
  • 27 个工作点，平均误差 3.6%，全部落在 10% 以内。
  • H200、H200/B200 解耦、GB200 NVL72 三种部署，仿真线和实测线几乎重合。
  • LMBenchmark 多轮 agent 任务：Qwen3-32B，2×H100（1 prefill + 1 decode worker），vLLM。
  • 多轮动态的平均误差 9.9%，在 10% 误差带内。
  • 参数迁移实测：H200→B200 只更新硬件规格，holdout 预测照样准。
  • B200→H200 解耦：复用冻结的 B200 参数，只重测 host 控制，平均误差 3.1%。
  • pre-silicon 探索的两个反直觉发现：
  • 带宽和容量的权衡随工作负载反转，没有一招鲜。
  • 并发一高，瓶颈从显存带宽滑向调度器和运行时开销。
  • 独立单轮任务（W1）：HBM 带宽拉到 1.4 倍，吞吐 +24%。
  • 多轮任务（W2）：HBM 容量拉到 1.4 倍，吞吐 +22%，中位首字延迟从 12.55 秒降到 0.068 秒。

跟你的研究方向关联

  • 你正在评估 SGLang 的 P/D 解耦，ServeTwin 原生支持 P/D 解耦架构探索。
  • 你在设计 AI 自动调参系统（autotuner），最缺的就是"便宜又准的代价模型"。
  • ServeTwin 不需要目标硬件 profiling，换配置只改规格参数。
  • 这正好是 autotuner 搜索 P/D 比例、并行策略时的理想评估器。
  • Figure 3 的 KV 交接背压模型，可以直接借鉴进你评估报告的调度分析。
  • Figure 6 的前沿曲线，是你做"SLA 内吞吐最优"时的参照系：交互性和吞吐的 tradeoff 长什么样，论文里画好了。
  • pre-silicon 发现"并发一高瓶颈转调度器"，跟你的 MI350 实测（660 QPS 下 GPU 远未饱和、瓶颈在 vLLM CPU 调度）互相印证。

术语表

  • 闭环仿真（closed-loop simulation）：仿真结果反过来影响下一步仿真输入，有反馈。
  • iSTAGE：这篇的解析式耗时估算器，从规格算时间，不实测。
  • 背压（backpressure）：下游满了，向上游发"慢点"的信号。
  • 交互性（interactivity）：每个用户每秒拿到的 token 数，体验指标。
  • pre-silicon：芯片还没流片，先用仿真做设计决策。
  • holdout：留出一部分数据不参与校准，专门验证泛化。
