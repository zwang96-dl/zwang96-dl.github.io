BalanceRoute：DP 解码的负载均衡，路由做对能多出 15% 吞吐

  • 原文：https://arxiv.org/abs/2605.06113
  • 标题：Tackling the Data-Parallel Load Balancing Bottleneck in LLM Serving: Practical Online Routing at Scale
  • 作者：Tianci Bu、Yuan Lyu、Zixi Chen 等（港科大工业工程与决策分析系、华为 2012 实验室理论部、北大）
  • 提交：2026-05-07（v1），2026-09-27 修订（v3），NeurIPS 2026 接收
  • 深读：07点版（2026-11-07，中文媒体当日再报）
  • 含原文 Figure 1/2/3/4

人话解读

一句话：解码那拨卡，分活不均就全员等最慢的那个。 DP 是数据并行。 模型复制多份，每份各接一部分请求。 每吐一个词，所有 worker 要对齐一次。 这叫 barrier 同步。 像接力队等最后一个人到终点。 一个 worker 背的请求太重，全队都得等它。 生产部署里，这种空等能吃掉 40% 以上的加速器时间。 BalanceRoute 就是个分活的路由器。 它在请求进 decode 池之前，先算该去哪组。 BR-0 不用预测，现算现分。 BR-H 往前看 80 步，顺带猜每个请求还能吐多长。 144 张昇腾 910C 上跑 DeepSeek-V3 671B。 相对最强的老办法，吞吐涨了 15.4%。 卡越多，赚得越多。 16 组 decode 时涨到 34.5%。 这篇的价值不在 15% 这个数。 它把“分活”这件事第一次算明白了。

核心方法

1. 问题长什么样：四件事一起为难路由器

第一，分配是粘性的。 请求一旦落到某个 worker，就待到结束。 中途搬家要搬整个 KV 缓存，太贵了。 第二，每个请求的负担未知，还会变。 输出多长，路由时根本不知道。 KV 缓存越长，每步注意力越贵。 第三，到达不平稳。 请求从 prefill 那边一阵一阵涌过来。 第四，决策预算只有毫秒级。 生产上每步解码不到 100 毫秒。 路由器必须在这个时间里拍板。 经典的排队论办法不管用。 它们只看当前队列长度。 但解码的负担是 KV 占用的总量。 不是排队的人数。

2. F-score：一把量“分过去能省多少”的尺子

核心是一个分段线性打分，叫 F-score。 它衡量把请求 Q 分给 worker g。 能把不均衡减少多少。 打分是不对称的。 填进安全余量，便宜。 溢出到危险区，贵得多。 这符合直觉。 超载的 worker 会拖慢全队。 路由器每步挑总分最高的分配。 求解用两阶段分解。 毫秒级就能算完。 BR-0 只用这把尺子。 不需要任何预测基础设施。

3. BR-H：往前看 80 步，再加个终止预测器

BR-H 在 F-score 上加了前视。 往前看 H 步，H 取 80。 未来的不均衡按折扣算进当前分数。 前视需要猜每个请求还能活多久。 论文给了两个预测器。 ExactMatch 按 prompt 哈希查历史分布。 同样 prompt 以前吐多长，这次大概率也差不多。 Survival 用经验生存函数估计剩余长度。 没有 prompt 复现时也能用。 实测里 ExactMatch 找回了大部分前视收益。 Survival 也差不多。 这说明前视的收益不挑预测器。

4. 落地：一个有状态代理，嵌进 vLLM-Ascend

部署形态是一个有状态 Python 代理。 它夹在客户端和 vLLM-Ascend 之间。 分三步走。 Payload Mutator 先改写请求。 把 OpenAI 兼容请求改成单步模式。 Prompt Pool 缓冲已经读完题的请求。 BR-H Dispatcher 按 F-score 批量分发。 Cluster Snapshot 维护全集群快照。 每步的 SSE 遥测会纠正预测偏差。 KV 跨层搬运用 MooncakeConnectorV1。 实验拓扑默认 4P1D。 4 个 prefill 节点，各 16 张卡。 1 个 decode 节点，32 张卡。 DP 等于 8，TP 等于 4。 一共 8 个 decode worker。

关键数据

  • 主实验：G 等于 8，重载。
  • BR-H 已部署版，ExactMatch 预测。
  • 自有生产 trace：977 词每秒。
  • Azure-2024 trace：909 词每秒。
  • 相对最强基线 JSQ，涨 15.4% 和 14.5%。
  • 不均衡从 215,110 词元压到 36,277。
  • Azure 那边从 104,737 压到 38,496。
  • 尾部延迟也没牺牲。
  • TPOT P95 是所有办法里最低的。
  • BR-0 不用预测，也能涨 11.8% 和 8.8%。
  • 不均衡降 4.1 倍和 1.94 倍。
  • Oracle 版 BR-H 能到 1,029 和 957 词每秒。
  • 这是预测完美时的天花板。
  • 扩展性上，BR-H 的优势随 G 变大。
  • G 等于 4 时涨 13.4%。
  • G 等于 8 时涨 21.5%。
  • G 等于 16 时涨 34.5%。
  • 拟合下来，优势大约按 G 的 0.69 次方涨。
  • BR-0 是 0.44 次方，轨迹更平。
  • 调度开销很小。
  • 每轮中位数 1.20 毫秒。
  • 99 分位 2.77 毫秒。
  • 远低于 60 毫秒的解码预算。
  • 两条 trace 差别很大。
  • 自有 trace 平均输出 1,185 词元。
  • Azure-2024 平均输出 1,052 词元。
  • 结论在两边一致。
  • 数字均为作者自报。
  • 自有生产 trace 没有公开。

原文关键图表

图 1：DP 解码的 barrier 同步，不均就空等

图里分左右两半。 左边是均衡分配。 四个 worker 各背两个请求。 每步算力 88% 到 94%，一起到终点。 右边是不均衡分配。 两个 worker 背了四个请求。 另外两个只背两个。 快的那个每步只算 32% 的时间。 剩下的全在空等最慢的。 SYNC 那条黑竖线就是 barrier。 所有人必须同时到。 这张图就是整篇论文的动机。 一句话：不均的代价是每步都付。

图 2：系统长什么样，有状态代理居中调度

图分上下两层。 上层是控制面，一个有状态代理。 Payload Mutator 改写请求。 Prompt Pool 缓冲读完题的请求。 BR-H Dispatcher 按 F-score 分发。 Cluster Snapshot 存全集群快照。 下层是数据面，vLLM-Ascend 的 worker。 左边 prefill 层，右边 decode 层。 KV 缓存走 Mooncake 从左搬到右。 紫色虚线是 in-band 遥测回流。 用来纠正负载预测。 注意 prefill 节点每节点 16 张卡。 decode 节点 32 张卡，DP 等于 8。 这就是 4P1D 的拓扑。

图 3：八个 worker 的 KV 负担曲线，BR-H 收得最紧

四个小图，各画八条线。 每条线是一个 worker 的 KV 负担。 横轴是 1500 步解码。 纵轴是 KV 占用的词元数。 左上 Random：八条线上下散开。 差距最大，跨度约 10 万词元。 右上 JSQ：还是散，只是收了一点。 左下 BR-0：八条线基本缠在一起。 右下 BR-H：缠得更紧。 线越缠得紧，不均衡越小。 表 1 的数字跟这张图对得上。 BR-H 的不均衡只有 JSQ 的六分之一。

图 4：卡越多，路由的收益越大

左图是不均衡随 G 变化。 纵轴是对数刻度。 灰色是四个基线，越往上越差。 蓝色 BR-0 和红色 BR-H 在下面。 G 越大，差距拉得越开。 右图是吞吐优势随 G 变化。 G 等于 4 时，BR-H 领先 13.4%。 G 等于 8 时，领先 21.5%。 G 等于 16 时，领先 34.5%。 红色拟合线是 G 的 0.69 次方。 这张图的关键结论是超线性。 规模越大，路由越值钱。

跟研究方向的关联

  • PD 解耦评估里，decode 侧的 DP 路由是一块短板。
  • 只调 prefill 和 decode 的配比，不够。
  • decode 池子内部怎么分活，同样决定吞吐。
  • F-score 的思路可以直接抄。
  • 把“分过去能省多少不均衡”算成分数。
  • 放进 autotuner 的打分里。
  • 评估要按 G 分档。
  • G 等于 4 和 16 时，收益差两倍多。
  • 小规模测出的结论，别直接外推到大集群。
  • 注意这篇的实验环境。
  • 昇腾 910C 加 vLLM-Ascend。
  • KV 搬运用 Mooncake。
  • 换到 H100 加 NIXL，不均衡的形态可能不同。
  • 但 barrier 同步的机制是一样的。
  • ExactMatch 预测器依赖 prompt 复现。
  • 智能体多轮对话里，prompt 复现很常见。
  • 这正是 HiCache 和前缀缓存友好的负载。
  • 评估时可以顺带测 ExactMatch 的命中率。
  • 这篇跟 FluidPD、AMPD 是互补关系。
  • 它们管 worker 演什么角色。
  • 这篇管请求去哪个 worker。
  • 三个机制可以叠加。
  • 数字全是作者自报。

术语表

  • DP：数据并行，模型复制多份，各接一部分请求。
  • Barrier 同步：每步所有 worker 对齐一次，等最慢的那个。
  • Sticky assignment：粘性分配，请求落定后不再搬家。
  • F-score：分段线性打分，量分过去能省多少不均衡。
  • JSQ：Join-Shortest-Queue，接最短队列，最强基线。
  • P2C：Power-of-Two-Choices，随机挑两个取负担小的。
  • TPOT：每输出一个词元的时间，越小越快。
  • ExactMatch：按 prompt 哈希查历史输出长度的预测器。
  • Survival：用经验生存函数估计剩余长度的预测器。
  • SSE 遥测：每步从解码器回流的负载信号。
  • 4P1D：4 个 prefill 节点加 1 个 decode 节点。
  • G：decode worker 的个数。
  • TP：张量并行，把一层切开分给多卡算。
