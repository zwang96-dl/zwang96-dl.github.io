H200 单卡 vLLM 实战：3.69 倍效率分，KV 缓存是第一性原理

原文：3.69× the Baseline Score on a Single H200: Our AI Race 2026 LLM Inference Solution

链接：https://www.linkedin.com/pulse/369-baseline-score-single-h200-our-ai-race-2026-llm-inference-nam-gxwwc
背景：Viettel AI Race 2026 Round 3（LLM 推理优化），获奖队伍 MOE（Tran Thanh Nhan、Dam Anh Duc、Le Thanh Nam）的复盘
配图说明：原文无配图，关键数据已转录为下面的代码块和表格

一句话人话版

  • 在一块 H200 上用 vLLM 跑 agent 长上下文，效率分刷到官方基线的 3.69 倍。
  • 没有单点银弹，是内核重写 + 算法剪枝 + 服务工程三路叠出来的。
  • 整篇文章只讲一个道理：长上下文场景下，优化的账要按"占了多少 KV 缓存"算，不按"省了多少算力"算。

背景：这是什么比赛，负载长什么样

  • 模型：Qwen3.8-27B-FP8，固定死在一块 H200（143GB）上跑。
  • 负载：回放真实的 agent 编程会话 trace，不是合成 prompt。
  • 评分：ERS（Efficiency-Realism Score，官方定的延迟饱和分）。
  • ERS 同时看首 token 延迟和逐 token 延迟，两边权重一样。
  • prompt 平均 110,906 token，峰值 996,579 token。
  • 输出又短又碎：中位数只有 335 token。
  • agent 每轮几乎原样重发上下文，86–89% 的 prompt token 直接命中前缀缓存。
  • 最终配置下，每条 prompt 只有约 5.8% 是真正重新算的。
  • 结论：这不是 prefill 瓶颈，也不是 decode 瓶颈，是 KV 缓存容量瓶颈。
  • 每个吃显存的优化都要付两次代价：直接代价 + 挤掉前缀缓存的代价。

核心方法

整体架构：两容器流水线，一个 OpenAI 兼容入口

  • 基于 vLLM v0.28，不换引擎，只换"跑偏的零件"。
  • 复用：PagedAttention、前缀缓存、FP8 分页 KV 缓存、chunked prefill、Rust 前端、投机解码框架。
  • 前面挂一个投机预填充代理（speculative-prefill proxy），专管 prompt 剪枝。

投机预填充：用小模型先给 prompt"划重点"

  • 对每条首次出现、≥4096 token 的用户/工具消息做剪枝。
  • 用 16 层截断版 Qwen2.5-0.5B，在 8192 token 滑窗上做一次前向。
  • 取第 6、9、12、15 层、query 位置的注意力聚合成每 token 重要性分。
  • 保留 HEAD 256 + TAIL 512 token，再按自然语义单元补高分 token，总量上限 20%。
  • 低分但"看着像关键词"的锚点，用 BM25 再捞回来一遍。
  • 关键工程细节：剪完的文本按 sha256（消息内容）冻结。
  • 下一轮 agent 原样重发同一条消息时，字节级完全一致，前缀缓存照样命中。
  • 没有这一步，剪枝在多轮场景下是负优化：省的算力抵不过丢掉的缓存命中。

内核线：两个实打实的改动

  • 改动一：FlashAttention-3 的 FP8"两级累积"开关。
  • vLLM 的 FA3 分支默认开着两级累积：定期把 tensor core 累加器刷到 FP32 寄存器副本。
  • 上游说关掉它只快 5–13%，但精度会崩，所以"不值得"。
  • 在这套配置（head_dim=256，上游只测了 128）下，关掉它快 2.0–2.5 倍。
  • 原因是寄存器溢出：累加器翻倍后寄存器流量翻倍，spill 从 432 字节/线程降到 48 字节。
  • 而且 head_dim=256 时，单 warp 组的 decode 快路径被关掉，prefill 和 decode 跑同一个内核。
  • 所以这是唯一一个同时改善首 token 延迟和逐 token 延迟的改动。
  • 改动二：W4A16 GEMM 内核按 M=8–64 调优。
  • 已发表的 W4 内核都按 M≤8 调，生产构建在 M>32 时回退到 FP8，正好错过最贵的步。
  • 在 gate_up 34816×5120、M=40 时：41.1µs，对比 50.7µs（启发式分块）和 51.5µs（FP8 DeepGEMM），快 19%。
  • 这是标准的"访存瓶颈"修复：decode 每步读 21GB 权重吐约 10 个 token，唯一杠杆是每权重字节数。

一个诚实的负结果

  • prefill 的 GEMM 已经没油可榨：DeepGEMM 跑到 1357–1473 TFLOPS。
  • 基本吃满 H200 的 FP8 tensor core，测完确认没有更快的 prefill GEMM。
  • 负结果也写进复盘，这种诚实很难得。

关键数据

消融阶梯（分数 = 100 × ERS，官方命令实测）

`` baseline 23.27 + FA3 attention kernel 40.96 +17.69 + Humming W4A16 GEMM 41.35 +0.39 （噪声线以下） + DFlash2 speculative decoding 32.96 -8.39 <- 反而丢分 + scheduler fixes+offload 40.28 +7.32 + speculative prefill 56.28 +23.32 + speculative prefill+all 65.11 +32.15 ``

端到端（900 秒，同机同命令）

  • ERS：0.2327 → 0.86（3.69×）。
  • 900 秒服务请求数：138 → 491。
  • TTFT p50：927ms → 204ms；p90：4637ms → 542ms。
  • TPOT p50：31.01ms → 3.56ms（每步 1.00 → 4.83 token）。
  • 零分请求：TTFT 35 → 4，TPOT 24 → 0。零错误，零抢占。

发现 2：最快的内核在静默丢精度

  • 关掉两级累积后，累加和一直待在 FP8 tensor core 累加器里。
  • 只有约 10–14 位尾数，还向零舍入，串行链长达 4096–8192 步。
  • 实测相对 FP32 参考的平均偏差：

- 8k 上下文：−15.5% - 32k 上下文：−53.4% - 131k 上下文：−82.0% - 262k 上下文：−90.6%

  • ERS 看不出来：它只打分延迟，越快分越高，错得快也是快。
  • GPQA 看不出来：198 道题 token 化后中位数 201 token，最长 2763，上限 8k 才开始崩。
  • 随机输入的 attention 基准结构性失明：得用对抗输入（一个强 sink key + 长尾）才抓得到。
  • 正确修法是把整个加速全还回去：上游正确内核慢 2.52 倍。
  • 他们的折中：定期把累积链刷到全局内存的暂存区。
  • 代价从寄存器压力（head_dim=256 下是灾难）转成合并的全局内存流量（便宜）。
  • 262k 上下文：误差 −90.6% → −3.4%，速度只慢 11.6%。
  • 结论：96% 的误差用 8% 的代价修掉，ERS 零加分，但他们认为这是全篇最有价值的活。

发现 3：投机解码单独用是负收益（因果链）

`` drafter 权重占显存 → KV cache 容量 2,700,325 → 1,924,636 token（−28.7%） → 前缀缓存命中 82.8% → 43.3% → 重算 prompt 占比 17.4% → 56.3% → prefill 1683 → 5905 ms/请求 → 首 token 延迟崩盘，出现首次抢占 ``

  • decode 侧确实达标：TPOT p50 20.39 → 14.58ms，每步 2.72 token。
  • 但 ERS 掉了 8.39 分。所有已发表的投机解码加速数都是在"KV 容量固定"下测的。
  • 在 KV 容量瓶颈的负载上，这个假设不成立。
  • 先上 prompt 剪枝再叠投机解码：同一招值 +23.76 分。

核心原则（原文原话转述）

  • 长上下文 + 高前缀复用场景下，按"优化挤占了多少 KV 缓存"评估，不按"省了多少 FLOPs"评估。
  • 减少对缓存的需求，胜过给缓存加容量。
  • 这句话预测了整个消融：prompt 剪枝（降需求，+23.32）打赢了 120GB CPU KV offload（加容量，+3.35）。

跟你的研究方向的关联

  • 你正在 MI350 上用 vLLM 做吞吐基准，也在评估 SGLang 的 P/D 解耦。
  • P/D 解耦的核心代价就是 KV 在 prefill/decode 节点之间搬运，这篇把 KV 当第一性原理。
  • "看挤占不看节省"的评估框架，可以直接套用到你的 P/D 解耦评估里。
  • 投机预填充的"hash 冻结保缓存命中"是个可复用的工程模式：任何改 prompt 的预处理都要过这一关。
  • FP8 两级累积的坑跟 head_dim 强相关：你在 MI350 上跑 FP8/量化路线时，精度验证要用长上下文对抗输入，短题基准测不出来。
  • 投机解码的负收益案例是现成的反例：drafter 显存占用 vs KV 容量的 trade-off，在你的 MI350 单卡上同样存在。
  • 团队联系方式在原文末尾：作者明确想知道有没有人在生产环境撞见过 head_dim=256 的 FP8 累积问题。

术语表

  • ERS（Efficiency-Realism Score）：比赛官方的效率分，首 token 延迟和逐 token 延迟各占一半的饱和打分。
  • speculative prefill（投机预填充）：用小模型先给长 prompt 划重点、剪枝，再送进大模型。
  • speculative decoding（投机解码）：小模型先打草稿、大模型批量批改的加速法。
  • prefix cache（前缀缓存）：之前算过的 prompt 片段直接复用，不再重算。
  • TTFT（time to first token）：首 token 延迟，用户敲回车到看到第一个字的时间。
  • TPOT（time per output token）：逐 token 延迟，平均每个 token 的生成间隔。
  • two-level accumulation（两级累积）：FA3 的 FP8 模式下，定期把累加器刷到 FP32 副本保精度的机制。
  • head_dim：注意力头的维度，这篇里是 256（上游只在 128 上测过）。
  • BM25：经典的关键词检索打分，这里用来捞回低分但词面重要的锚点。
  • DeepGEMM：DeepSeek 开源的 FP8 GEMM 库，这篇里 prefill 已经吃满算力。
  • W4A16：权重 4bit、激活 16bit 的量化格式，decode 访存瓶颈的标准解法。
