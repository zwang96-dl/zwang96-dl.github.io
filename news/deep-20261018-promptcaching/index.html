Prompt Caching：逐词元讲清前缀复用

原文：A Token-by-Token Guide to Prompt Caching 作者：Sithan Kanna（个人技术博客） 发布：2026-10-18 链接：https://www.sithankanna.com/posts/prompt-caching-vs-kv-caching.html

人话解读

  • 这篇把两个词彻底分清了。
  • KV 缓存是单次回答内的复用。
  • Prompt 缓存是跨轮次的复用。
  • KV 缓存就是模型的草稿纸。
  • 草稿纸留下来，下轮接着用。
  • 省的是开头那段重算。
  • 它不直接返回旧答案。
  • 新词元还要照常生成。
  • 只是不用再算一遍前缀。
  • 对多轮对话，这省得很实在。
  • 对 Agent 工具调用也一样。
  • 工具结果一回来，前缀全在。

图注：图 1 是原文的第一张图。 第一轮输入是 A、B、C 三个词元。 模型答出 D、E 两个词元。 第二轮输入就变成了七个词元。 老输入、老回答、新消息全拼一起。 前缀越拼越长，重算越亏。

核心方法

  • 先证一件事：前缀不会变。
  • 因果掩码挡住了后面的词元。
  • 后面的词看不见前面的计算。
  • 所以前面每层的 K、V 不变。
  • K、V 就是每层存的草稿。
  • 每层各存各的，互不混用。
  • 第二步，看 vLLM 怎么找缓存。
  • vLLM 把词元切成定长小块。
  • 例子里每块只放两个词元。
  • 只有装满的块才能被复用。
  • 半块不算数，只能重算。
  • 第三步，看块怎么编号。
  • 每块算一个哈希当身份证。
  • 哈希就是内容的短指纹。
  • 后块哈希要带上前块哈希。
  • 这样才认得出完整前缀。
  • 查找从第一个块开始扫。
  • 第一个没命中就直接停。
  • 中间对上号也不算命中。
  • 因为前文不同，草稿就不同。

图注：图 2 是原文的复用示意图。 左边是第一轮存下的 A 到 D。 右边是第二轮要算的 E 到 Z。 虚线箭头连的是同一层的草稿。 只有 E 往后需要重新计算。 A 到 D 直接拿来用就行。

关键数据

  • 原文用三轮对话算命中率。
  • 第一轮输入 3 个词元。
  • 命中 0 个，命中率是 0%。
  • 第二轮输入 8 个词元。
  • 命中 4 个，命中率 50%。
  • 第三轮输入 12 个词元。
  • 命中 8 个，命中率约 66.7%。
  • 三轮合计算是约 52.2%。
  • 注意，这不是三个数的平均。
  • 这是玩具例子，不是实测。
  • 更不是厂商的计费预测。
  • 它只说明一个趋势。
  • 对话越长，复用比例越高。
  • 前缀越稳，省得越多。

图注：图 3 是原文的共享示意图。 两个会话都以 A、B 开头。 这个满块就能只存一份。 后面各自岔开就各存各的。 共享只到共同前缀为止。

一个大坑

  • 系统提示开头别放时间戳。
  • 时间戳每轮都会变。
  • 第一个词元一变就全变。
  • 第一块哈希跟着全变。
  • 后面没变的块也认不出来。
  • 结果是零个词元被复用。
  • 正确做法是稳定内容放前面。
  • 变化内容尽量往后放。
  • 工具定义改动也有同样问题。
  • 改早年消息也会打破前缀。
  • 看着一样不等于算着一样。
  • 模型实际吃到的词元说了算。

跟你研究的关系

  • 你的负载正好是前缀型。
  • 每请求约 250 个输入词元。
  • 前约 200 个是共享的。
  • 这篇讲清了块粒度的代价。
  • 共享段没凑满整块就浪费。
  • 块大小直接影响命中上限。
  • 它还讲清了隔离怎么做。
  • vLLM 可以加缓存盐隔离用户。
  • 缓存盐就是给哈希加标记。
  • 同提示加不同盐就互不共享。
  • 云 API 的边界也对上了。
  • OpenAI 按组织隔离缓存。
  • Claude 按工作区隔离缓存。
  • 自建服务选隔离粒度时可参考。

术语表

  • KV 缓存：单次生成内留的草稿纸。
  • Prompt 缓存：跨请求复用前缀草稿。
  • Prefill：读题阶段，批量算输入。
  • Decode：续写阶段，一个个吐词。
  • 块哈希：给一小块词元的指纹。
  • 缓存盐：隔离不同用户的哈希标记。
  • 命中率：复用词元占输入的比例。
