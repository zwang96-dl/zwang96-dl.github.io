P/D 解耦的功率账：电有限时，prefill 和 decode 各配几张卡

原文：Analytical Power-Aware Provisioning for Prefill–Decode Disaggregated AI Inference
作者：Mingyuan Yan, Haiyu Wang, Linxuan Biao, H. Jonathan Chao, Sai Qian Zhang, Wenqi Cui（NYU）
链接：https://arxiv.org/abs/2609.24639

人话解读

机房批的电不够，推理服务也得省着用。 P/D 解耦把 prefill 和 decode 拆成两个池，各配多少卡直接决定电费和吞吐。 之前配卡靠 profiling 瞎试，请求分布一变就得重跑。 这篇给了纯解析模型：不跑 benchmark，直接算出"电有限时怎么配卡最划算"。 说白了：给 P/D 解耦配了个"电费-吞吐"菜单，点菜不用再试吃。 Qwen3-32B + H100、4 卡配、SGLang 0.5.9 实测校准。 功率模型误差只有 2.3–2.7%。 模型选出的最低功耗部署，跟实测选出的一致率 85–90%。

核心方法

两个解析模型拼出一条前沿：

  • 供给能力模型。

prefill 是计算 bound，一次把输入全算完，按 FLOPs 算。 decode 是访存 bound，一次吐一个 token，按内存带宽算。

  • KV 缓存耦合。

P/D 之间的 KV 搬运和预留让两池互相牵制。 decode 侧的 KV 预留用排队论建模，Little 定律那一套。

  • 功率模型。

单卡功率随归一化吞吐先升后饱和，不是线性关系。

  • 拼出"供给能力–功率"帕累托前沿（图 1）。

横轴吞吐，纵轴功率，曲线上每个点是一个 (np, nd) 部署。 运营商给定目标吞吐，直接在前沿上找最低功耗点。

两个配卡场景验证：

  • 请求率下降 → 砍掉一个 decode 实例，省约 270W，TTFT/TPOT 几乎不动。
  • 固定请求率下临时降功率 → TTFT 从 0.7 涨到 8.5 秒。

请求在队列里等，降电费的代价是尾延迟。

关键数据

  • 固定长度负载（4096 输入 / 256 输出）：功率模型平均误差 2.3%。

Mooncake trace 2.7%，Azure trace 2.6%。

  • 帕累托前沿选出的最低功耗部署，跟实测选出的一致率。

固定长度 90%，Mooncake 85%，Azure 86%。 分歧都出现在可行性边界（±4% 以内），无伤大雅。

  • 降载场景：3p2d 配 60% 负载，砍一个 decode 实例省约 270W。

中位 TTFT 还是 0.55 秒，基本没感觉。

  • 限电场景：固定 5.3 req/s 砍一个 decode 实例。

TTFT p50 从 0.7 秒涨到 8.5 秒，TPOT 中位涨 39 毫秒。

  • 实验硬件：Qwen3-32B，H100，4 GPU 一实例，SGLang 0.5.9。

Trace：Mooncake（Kimi 真实请求）、Azure（微软生产 trace）。

跟你研究方向的关联

你正在评估 SGLang 的 P/D 解耦，这篇直接回答"解耦之后各配几张卡"。 之前的 PD 笔记（报价器路由、FPT 实战）讲的都是"请求分给谁"，这篇补上"池子配多大"。 功率约束是你没碰过的维度，数据中心电批不下来时这就是硬约束。 模型只用固定长度负载校准一次，trace 负载免校准复用，方法论可抄。 SGLang 0.5.9 的实测数据，跟你评估的版本线也对得上。

术语表

  • P/D 解耦（PD disaggregation）：prefill 和 decode 跑在不同的 GPU 池里，各自独立扩缩容。
  • 供给能力（serving capacity）：系统能扛住的最大请求速率。
  • 帕累托前沿（Pareto front）："电费–吞吐"菜单上最划算的那条曲线，曲线外的点都被支配。
  • TTFT：从请求到来到第一个 token 的时间。
  • TPOT：每吐一个 token 的平均时间。
  • Mooncake trace：月之暗面 Kimi 服务的真实请求 trace。
  • MFU/MBU：算力/带宽利用率，衡量硬件吃满程度。
