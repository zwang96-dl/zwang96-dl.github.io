一句话人话版

这是一张"推理平台全栈地图"。核心就一句话。别再盯 GPU 利用率，看 goodput。瓶颈永远在显存和状态搬运，不在算力。

这是什么、有什么用

从你按下发送键，到第一个字蹦出来，中间隔着五层系统。网关、路由、K8s、推理引擎、GPU。这篇文章把每一层串成一条线。讲它是干嘛的、怎么 sizing、怎么看监控、怎么半夜排障、怎么算账。

对你最直接的用处跟 MI350 评估有关。你在用 vLLM 做 P/D 评估。文章讲了 prefill/decode 的硬件胃口。还讲了 prefix caching、batch 拐点、goodput。正好是评估时要盯的指标框架。

核心观点

五层栈，每层回答同一个问题：请求的状态住哪、要花多少钱。模型权重是只读的全局状态。KV cache 是每个请求的动态状态，也是显存里最大的变量。

prefill 和 decode 是两种动物。prefill 一次处理整个 prompt，高度并行，吃算力。decode 一次吐一个 token。每吐一个要把全部权重从显存读一遍。吃带宽，算力大半在空转。这就是 P/D 解耦的物理动机。

并发上限是显存定的，不是算力。KV cache 大小 = 每 token 大小 × 上下文长度 × 并发数。100 个用户各聊 8000 token，cache 可能比模型权重本身还大。"这张卡能带多少用户"不带上下文长度就是伪命题。

GPU 利用率是骗人的指标。decode 时 GPU 被内存读取卡住，算力空转，利用率照样报 100%。正确指标是 goodput：在延迟目标内完成的请求数。吞吐高但用户等 8 秒才看到第一个字，goodput 就是零。

容量有两个天花板，取小的那个。显存天花板：算一下 KV 池能装多少并发。延迟天花板：batch 太大 TPOT 就超标，这个只能实测。内存不够就量化、砍上下文。延迟超标就加副本，加显存没用。

prefix caching 的命门在 prompt 开头。引擎按"块哈希 + 之前所有块的哈希"找可复用的 cache。prompt 开头放个动态时间戳，第一个块的哈希就变了，后面全军覆没。稳定内容放前面，动态内容放后面。

成本公式：百万 token 成本 = GPU 小时价 / 每小时产出。分子基本固定，优化全在分母。影响从大到小排序。并发最大。其次是前缀缓存命中率。然后是模型大小和精度。最后是空闲预留和上下文长度。注意没有"换更快的卡"这一项。

跟你研究方向的关联

你在 MI350 上测 Llama 3.2 3B 的 660 QPS。这篇文章给了评估框架。

第一，你的 workload 是 250 in / 200 共享 / 1 out。前缀缓存命中时，prefill 只算 50 个新 token。这正是文章说的场景：prefix caching 把重复 prefill 干掉。测的时候要同时记录命中率。不然 QPS 数字没法复现。

第二，文章强调 benchmark 要扫 arrival rate。找到 knee 点，而不是固定并发。你之前只给了 660 QPS 一个点。建议补一条 goodput-负载曲线。拐点才是真实容量。

第三，单卡 660 QPS 时 GPU 利用率可能已经很高。但按文章的说法，那可能是"带宽饿死"的假象。要区分瓶颈，得看 token 吞吐和 TPOT。而不是 nvidia-smi 式的利用率数字。

第四，P/D 解耦的动机在 decode 的带宽瓶颈里写得最清楚。decode 每 token 读一遍全部权重。batch 是唯一的摊薄手段。这也是 SGLang/llm-d 做 E/P/D 解耦的出发点。

术语表

  • goodput：在延迟目标内完成的请求数。吞吐看机器干了多少，goodput 看用户拿到了多少。
  • TTFT：time to first token，第一个字蹦出来要多久。决定界面"活不活"。
  • TPOT：time per output token，每个字平均多久。决定读起来顺不顺。
  • ITL：inter-token latency，字与字之间的间隔。暴露卡顿，平均数藏不住它。
  • prefill：处理整个 prompt 的阶段，吃算力。
  • decode：一个一个吐 token 的阶段，吃显存带宽。
  • KV cache：存着前面所有 token 的 key/value。避免重复计算。显存里最大的动态开销。
  • PagedAttention：vLLM 的显存管理技术。把 KV cache 按小块分配，不浪费。
  • prefix caching：相同前缀的请求复用 KV cache。跳过重复 prefill。
  • continuous batching：动态重组 batch 进出。做完的走、排队的进。
  • chunked prefill：把大 prefill 切成小块。插到 decode 中间。避免一次大 prefill 卡住所有输出。
  • P/D 解耦：prefill 和 decode 放不同的 GPU 池。各用最合适的并行策略。
  • llm-d：Kubernetes 原生的推理平台项目。支持 P/D 解耦和缓存感知的调度。
  • 抢占（preemption）：显存池满了，把正在跑的请求踢掉。非零就说明超容量了。
