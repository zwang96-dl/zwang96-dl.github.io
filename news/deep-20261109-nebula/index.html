Nebula：分布式位置无关缓存，首字延迟降六成

原文：Yifei Liu 等《Nebula: Distributed Position-Independent Caching for LLM Serving》
原文链接：https://arxiv.org/abs/2611.09474
发布：2026-11-06，23点版深读（11 月 6 日那批，之前几期漏报的补读）
作者单位：小红书、上交、北大；arXiv:2611.09474v1 [cs.DC]

一句话人话版

RAG 和 agent 的长 prompt 里。 检索文档、工具返回到处换位置。 前缀缓存认不出来，全得重算。 Nebula 让这些段落跨节点也能复用。 首字延迟平均降六成。

先说问题：前缀缓存只认开头，RAG 的段落到处跑

prefill 是读题，一次性处理全部输入。 decode 是一词一词往外吐。 RAG 的 prompt 由多段独立文本拼成。 系统提示、检索到的文档、用户问题各一段。 agent 更甚，工具输出、记忆、技能文件不断往后贴。 前缀缓存只认严格相同的前缀。 前缀就是从头开始一字不差的那段。 文档换个位置、换个顺序，缓存就认不出来。 全得重算，首字延迟就上去了。

论文先算了这笔账有多大。 ChatRAG 两套对话数据，前缀命中率只有 3% 左右。 位置无关复用能再捞回 97% 和 84% 的词。 RAGPulse 那条公开 trace，前缀命中 31.5%。 位置无关还能再找回 59.1% 的漏网词。 agent 的 workload 前缀命中本来就高。 τ-bench 92.6%，SWE-agent 95.3%。 但剩下的漏网词里，位置无关还能捞回一半左右。 多智能体协作的 ChatDev，漏网词能捞回 84.7%。 机会是真实存在的，问题出在系统层面。

*图1：同一个请求，分布式位置无关缓存怎么分工。请求由系统提示 P、PIC 段 A、B、C、D 和问题 q 组成。(a) 老做法：只认前缀，A 在 W1 上复用，B 在 W2 上够不着，W3 空着。(b) Nebula：B 的 KV 从 W2 搬过来复用，D 在 W3 上并行算，C 在 W1 上算，最后在 W1 汇总。*

现有的两类系统各缺一半。 Mooncake、LMCache、MemServe 能跨节点存 KV。 但只认前缀，段落换位置就复用不了。 CacheBlend、A3、EPIC、HYPIC 会位置无关复用。 但只在单机内玩，不做集群级管理。 直接把单机 PIC 挂到 Dynamo 后面也不行。 调度器找不到别的节点上的段。 算活也分不到空闲节点上。 P99 首字延迟能到 2.1 倍中位数。 等于一半请求快，一半请求拖后腿。

核心方法：三招，复用、视图、自调

1. 把 PIC 段当一等公民：跨节点复用加并行读题

应用用 <pic>...</pic> 标签标出哪些段能换位置复用。 RAG 标检索到的文档。 agent 标工具输出、环境观测、跨智能体消息。 没标的段走老路：前缀缓存或重算。 标了的段可以独立读题、缓存、搬运、复用。

请求进来后，控制面先做三件事。 第一，全请求做一次前缀匹配。 第二，没盖住的 PIC 段做位置无关匹配。 第三，调度器按匹配结果和各节点负载出执行计划。 计划给每个 PIC 段指定一个节点。 要么提供缓存的 KV，要么现算。 再指定一个汇总点，叫 combine home。 所有 KV 在那里汇合，完成读题。

执行分三种操作，可以重叠跑。 Scatter prefill：冷段分到各节点上并行算。 算完把 KV 发到汇总点。 Cache reuse：命中的段把 KV 搬到汇总点。 远的也搬，不只认本机。 Combine prefill：在汇总点拼起来。 算剩下的内容，做必要的重算。 PIC 段直接拼起来会有数值偏差。 偏差是因为 KV 依赖原来的位置和上下文。 所以要重算一小部分词来修正。 CacheBlend 按 KV 偏差挑词重算。 A3 看注意力分布挑关键 token。 EPIC 按注意力汇点静态选每段前几个词。 HYPIC 用转移矩阵处理线性注意力。 Nebula 不绑死某一种，后端接口是统一的。

2. 集群视图要又快又真：乐观记账加事件驱动更新

PIC 的状态变化又细又快。 一个请求能拆出几百个调度单元。 缓存位置、节点负载随时在变。 视图不准就会出两种错。 一是无效命中：以为有缓存，其实已被驱逐。 二是重复计算：以为没缓存，其实已经算好了。 论文测过，单用乐观记账或单用事件驱动都不行。 乐观记账是先假设写成功，后面再对账。 事件驱动是等 worker 上报了才更新。 前者在高并发下无效命中多。 后者在高并发下重复计算多。

Nebula 把两者拼起来。 写操作先乐观记账，立刻可用。 同时发事件，worker 回来再确认。 没确认的条目给 5 秒存活期。 过期还没确认就作废。 40 QPS 下，无效命中的词比纯乐观记账少 98.4%。 重复计算的词比纯事件驱动少 96.1%。 视图终于又快又真。

*图2：Nebula 系统架构，控制面加数据面。控制面在 Nebula Router 里：Cluster View 管全集群缓存和负载视图，Cache Manager 管 PC 和 PIC 的容量分配，Prefill Scheduler 出执行计划。数据面在各 Worker 上：推理引擎加 PIC 后端，PC 和 PIC 两块缓存并存。命令、KV 搬运、视图更新三条线分开走。*

3. 缓存配比自己调：幽灵命中反馈加统一时间模型

PC 和 PIC 共用一块缓存，配比是个难题。 RAG 要 PIC 多一点，agent 要 PC 多一点。 写死一半一半，两边都吃亏。 Nebula 用幽灵命中反馈自己调。 幽灵命中就是假如多给点容量能多命中的次数。 路由器按反馈动态调两边的配比。 RAGPulse 在 48 QPS 下。 比统一 LRU 命中率高 4.32 个点。 比固定对半分高 4.88 个点。 中位数首字延迟低 11.5% 和 14.7%。

调度还要算一笔总账。 排队、计算、KV 搬运三项成本进同一个模型。 算出每种分法的预计完成时间。 再决定并行度弹多大、活分到哪台机器。 亲缓存的节点可能负载高。 空闲节点可能搬运贵。 模型把这两头一起算，不拍脑袋。

关键数据

实验跑在两台一样的机器上。 每台 4 张 NVLink 直连的 H20。 两颗 48 核至强铂金 8575C。 1TB 内存，4 条 200Gbps RDMA 网。 7 个 prefill 节点加 1 个 decode 节点。 每节点 1 张卡，TP1。 4 个模型，4 套真实 workload。 DeepSeek-V2-Lite、Qwen3.5-35B-A3B。 Mistral-7B、Qwen3-30B-A3B。 ChatRAG、RAGPulse、τ-bench、ChatDev。 实现基于 SGLang 加 Dynamo。 约 1.9 万行代码，KV 搬运走 NIXL。

跟你的研究方向的关联

这篇正撞你的 PD 评估线。 第一，它就建在 SGLang 加 Dynamo 上。 不是另起炉灶，是在你评估的栈上加能力。 第二，它把分布式 KV 复用做成了账本。 哪些段能复用、复用率多少、漏网词找回多少。 这套度量能直接进你的评估矩阵。 第三，PIC 的重算策略值得单列。 CacheBlend、A3、EPIC、HYPIC 四种挑词法。 精度和成本各不相同，选型要按 workload 测。 第四，视图同步那节是 PD 的通用教训。 乐观记账加事件驱动，5 秒存活期。 无效命中和重复计算两个指标能直接抄。 第五，缓存配比自调的思路能进自动调参。 幽灵命中反馈是个现成的信号。 不用暴力扫配比，看反馈调就行。

注意三点边界。 第一，实验只生成 1 个词。 decode 侧的压力没测，PD 的 decode 池子还得你自己测。 第二，H20 的卡，200Gbps RDMA。 搬到 H100 或 MI350X 上，搬运和计算的配比会变。 第三，PIC 的数值偏差靠重算修正。 重算比例没给死数，不同模型要自己标定。 精度门里要加一项：PIC 开关前后的分数对比。

术语表

  • prefill（读题）：一次性处理全部输入，算出 KV 缓存。
  • decode（吐词）：一个词一个词生成，严重依赖显存带宽。
  • TTFT（首字延迟）：从发请求到第一个词出来的时间。
  • KV 缓存：读题后留下的键值草稿，decode 靠它接着写。
  • 前缀缓存：只复用从头开始一字不差的那段。
  • PIC（位置无关缓存）：一段话换个位置也能复用。
  • NPHR（非前缀命中率）：前缀认不出来、PIC 能捞回的词占比。
  • PMRR（前缀漏网找回率）：漏网词里 PIC 能捞回的比例。
  • RAG（检索增强生成）：先查文档再回答，prompt 里贴检索结果。
  • agent（智能体）：多轮调用工具、自己推进任务的模型用法。
  • combine home（汇总点）：各段 KV 汇合、完成读题的那台机器。
  • scatter prefill（分散读题）：冷段分到各节点上并行算。
  • 幽灵命中：假如多给点容量，本能命中的次数。
  • 乐观记账：先假设写成功，后面再对账。
  • 事件驱动更新：等 worker 上报了才更新视图。
  • 7P1D：7 个 prefill 节点加 1 个 decode 节点。
  • NIXL：英伟达的 KV 搬运库，管跨节点传 KV。
  • Dynamo：英伟达的推理编排框架，管多节点 KV 路由。
  • H20：英伟达面向中国市场的 GPU，Hopper 架构。
  • QPS：每秒请求数，压测里的负载档位。
  • SLO：服务等级目标，这里指首字延迟 1 秒。
  • 好吞吐：在 SLO 内完成的请求数除以总时间。
