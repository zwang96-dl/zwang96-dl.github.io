NVIDIA Snapshot：推理服务冷启动，几分钟压到几十秒

原文：NVIDIA 官方技术博客，2026-11-10 发布（KubeCon 同步宣布） 原文链接：https://developer.nvidia.com/blog/start-and-restore-gpu-workloads-in-seconds-with-nvidia-snapshot/ 开源仓库：https://github.com/NVIDIA/snapshot（Apache 2.0）

一句话

推理服务扩容或故障恢复时，冷启动要几分钟。

Snapshot 把初始化好的 worker 整个拍下来。

下次直接还原，几十秒就能接请求。

人话解读

先说冷启动为什么慢。

一台空闲 GPU 不能马上干活。

模型权重得读进显存。

推理引擎得启动、建通信、分配草稿纸。

内核要编译调优，还要抓 CUDA 图。

CUDA 图是把一串操作预先排好，快进键。

这一套走下来，小模型一两分钟。

8 卡大模型要 6 到 19 分钟。

流量一涨、副本一挂，扩容就卡在这几分钟上。

Snapshot 的思路很直白：别每次都重做。

第一次把 worker 初始化好，整个进程连 CPU 带 GPU 内存拍成快照。

以后要新副本，直接把快照还原到新节点上。

权重加载、内核编译、抓图全跳过。

还原完握个手就能接请求。

这就像游戏存档：通关前的准备工作做一次。

读档直接从存档点开始，不用重打前面的关。

它最初是给 Dynamo 的推理 worker 做的。

Dynamo 是英伟达的推理服务框架。

现在拆成通用组件，vLLM、SGLang、TRT-LLM 都能用。

仓库里三家引擎的现成例子都有。

核心方法

1. 两个操作：拍快照、还原

拍快照只在 worker 完全初始化好之后做。

CPU 内存和 GPU 内存一起存成一个可移植的产物。

还原时在新 Pod 上从这个产物恢复。

要求新节点 GPU 型号和驱动跟原来一样。

恢复完进程从断点继续跑。

2. Kubernetes 里的用法：两个自定义资源加一个注解

想给正在跑的 Pod 拍照，建一个 PodSnapshot 指着它。

想让 Pod 一就绪就自动拍照，建一个 SnapshotJob。

想从快照起新 Pod，给 Pod 加个注解。

注解的键是 nvidia.com/restore-from。

注解里写要恢复的那个 PodSnapshot 名字。

节点上有个特权代理负责干活。

共享存储放快照产物。

3. 恢复分四步：哪一步花时间，表里拆得清清楚楚

第一步是代理准备：找到快照产物，备好目标 Pod 和 GPU。

第二步是 CRIU 还原：把 CPU 进程镜像从存储读进主机内存。

CRIU 是 Linux 上给进程拍照的标准工具。

这步快慢主要看存储后端。

第三步是 CUDA 还原：把 GPU 状态拷回显存。

第四步是唤醒重映射：让进程适应新节点，再把引擎叫醒。

大模型上第三步最贵。

8 卡 MoE 配置里，GPU 状态还原要 18 到 29 秒。

CRIU 还原只要 4.2 到 10.8 秒。

4. 快照里不含 KV 缓存

恢复前会先触发 KV 缓存释放。

KV 缓存就是推理时的草稿纸。

它不进快照产物。

这点很关键：还原回来的是干净的引擎。

不是带着旧会话的半成品。

5. 兼容范围：单节点多卡一把梭

快照能覆盖单节点上跨多卡的 workload。

一个快照产物管所有 rank。

张量并行、数据加专家并行、解码上下文并行都支持。

张量并行是把一层切到多卡上。

专家并行是把 MoE 的专家分到多卡上。

解码上下文并行是解码时分上下文。

多机跨节点不在这篇的范围里。

关键数据

测试环境要先说清：B200 显卡，驱动 615.71.09。

存储是 VAST 的 NFS。

三家引擎版本先说清。

vLLM 0.31.0，SGLang 0.5.21，TRT-LLM 1.3.0。

数字全是英伟达自报，没有独立复核。

  • 恢复时间全线压在 43 秒以内：所有配置 3.6 到 42.7 秒。
  • 比冷启动快 8 到 36 倍：最大的 MoE 模型冷启动 6 到 19 分钟。
  • DeepSeek-V4.1-Flash，vLLM，8 卡：冷启动 1110.65 秒，恢复 30.96 秒，快 35.87 倍。
  • DeepSeek-V4-Pro-NVFP4，vLLM，8 卡：冷启动 908.48 秒，恢复 39.56 秒，快 22.96 倍。
  • GLM-5.3-NVFP4，vLLM，8 卡：冷启动 393.65 秒，恢复 28.64 秒，快 13.74 倍。
  • 小模型更快：Qwen3-0.6B，SGLang，单卡：冷启动 87.08 秒，恢复 3.59 秒，快 24.26 倍。
  • 拍快照一次的代价：15 秒到 5.5 分钟，看模型大小。
  • 快照产物大小：8 卡大模型 600GB 到 1TB，小模型只要 8GB 左右。
  • 关键结论：每个配置上，拍快照加恢复一次，比单次冷启动还短。
  • 第三方实测也对得上：Crusoe 的 GLM-5.3 从 8 分钟压到 31 秒。
  • Saturn Cloud 的 vLLM 从 2 到 8.5 分钟压到 6 到 34 秒。

冷启动的时间都花在哪了，表 2 拆得很细。

看 DeepSeek-V4.1-Flash 那组。

vLLM 上编译加抓图占了 784.54 秒。

占冷启动总时间的七成。

这正是快照能省掉的大头。

TRT-LLM 有个特点：初始化那步特别贵。

Qwen3-14B 单卡上初始化要 40.64 秒。

vLLM 只要 14.58 秒，SGLang 只要 8.41 秒。

跟研究方向的关联

这篇跟 PD 解耦评估直接对口，理由有三条。

第一，扩容成本要重算。

PD 解耦把读题池和解码池分开，弹性伸缩是卖点之一。

但解码池冷启动几分钟，伸缩就不及时。

Snapshot 把这个暗成本压到几十秒。

评估清单里可以加一条：解码池扩容的恢复时间。

第二，故障恢复的账变了。

副本挂了要补，冷启动那几分钟是服务缺口。

快照恢复把缺口压到半分钟。

评估时可以把恢复时间当成一个指标。

跟首字延迟、吞吐放同一张表里。

第三，口径要盯紧。

恢复计时不含拉镜像和配机器。

这两步在真实扩容里也要花时间。

拿数字做决策时，记得把这两步加回去。

另外快照产物要 600GB 到 1TB 存储。

8 卡大模型每配一个快照就是这个量。

存储成本和快照更新频率也要进账本。

术语表

  • 冷启动：从零启动推理服务，权重加载、编译、抓图全走一遍。
  • Snapshot：英伟达的新开源组件，给 GPU workload 拍照和还原。
  • DSX：英伟达的 AI 工厂平台，Snapshot 是它的组件之一。
  • CRIU：Linux 上给运行中进程拍照和还原的标准工具。
  • CUDA 图：把一串 GPU 操作预先排好，执行时一键放行。
  • KV 缓存：推理时的草稿纸，存已经算好的键值。
  • PodSnapshot / SnapshotJob：Snapshot 在 Kubernetes 里的两个自定义资源。
  • 张量并行：把模型一层切到多张卡上一起算。
  • 专家并行：把 MoE 模型的专家分到多张卡上。
  • 解码上下文并行：解码时把上下文分到多张卡上。
  • VAST：测试里用的 NFS 存储后端品牌。

局限与提醒

  • 数字全是英伟达自报，B200 加 VAST NFS 的环境，没有独立复核。
  • 恢复计时不含拉镜像和配机器，真实扩容要把这两步加回去。
  • 快照产物很大，8 卡大模型 600GB 到 1TB，存储成本要算进去。
  • 恢复要求同型号 GPU 和同版本驱动，异构集群用不上。
  • KV 缓存不在快照里，还原回来是干净引擎，不是热副本。
  • 引擎版本是 vLLM 0.31.0、SGLang 0.5.21、TRT-LLM 1.3.0，都是 11 月初的版本。
  • 前置要求不低：Linux 内核 5.13 以上，GPU Operator 26.3 以上。
  • MIG 分区要关掉，MIG 是把一张卡切成小卡的功能。
