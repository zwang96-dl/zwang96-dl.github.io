SpecStream：长上下文投机解码，KV 不用搬完就开工

  • 原文：https://arxiv.org/abs/2609.33184
  • 作者：Fei Li、Song Liu、Shiqiang Nie、Jinyu Wang、Weiguo Wu（西安交通大学）
  • 提交：2026-09-27，14 页 10 图，CC BY 4.0
  • 一句话：长上下文 serving 里 KV 太大放不下，它让"搬运"和"计算"重叠起来干

人话版：这篇在解决什么

  • 长上下文推理时，KV 缓存（注意力算过的草稿纸）越长越大，显存放不下。
  • 老办法是"以存代算"：把旧 KV 搬到 CPU 内存，不够了再搬回来。
  • 但老办法有个笨规矩：必须等整份 KV 全搬回来，大模型才开工验证。
  • 更亏的是：等货的这段时间，GPU 算力在那儿闲着发呆。
  • SpecStream 做了三件事，每件都冲着"别让 GPU 闲着"去。
  • 第一，只搬"板上钉钉"的旧 KV，待验的候选一律不搬。
  • 第二，搬一块算一块，不用等全部到齐。
  • 第三，等货的空档，让小模型在同一张卡上先打草稿。
  • 结果：同样两张卡，能接更多并发请求，输出质量基本不掉。

核心方法：三件套

1. 按"提交线"分三层，搬错了不返工

  • 投机解码（小模型先猜几个 token，大模型一次验完）里，KV 有两种命。
  • 一种是已提交的：大模型验过了，板上钉钉，后面不会变。
  • 一种是候选的：还在排队等验，随时可能被退货。
  • 老办法不分青红皂白一起搬，退货的 KV 等于白搬。
  • 白搬还不算完，CPU 那边还要清理被退货的 KV，多一道活。
  • SpecStream 只搬已提交的旧 KV，候选的全留显存。
  • 具体分成三层，各有去处。
  • Sealed History：老的已提交 KV，放 CPU 内存。
  • Active Tail：最近的 512 个 token，放显存，随用随取。
  • Speculative Frontier：待验的候选 KV，放显存。
  • 搬运不搞碎片化：攒够一批（g 个 token）再整块搬。
  • 退货只发生在显存里，CPU 那边永远干净，这就是"免返工"。

2. 流式验证：来一块算一块

  • 验证一轮有 q 个待验位置，它们要看的是同一份旧 KV。
  • 老办法：等当前层的全部历史搬回来，才开始算注意力。
  • SpecStream：历史切成小块，来一块就算一块。
  • 难点在于 softmax（注意力归一化）：本来要看完全部 KV 才归一化。
  • 解法是 online softmax（在线归一化）：每块只记三个数。
  • m 是当前见过的最大分数，ℓ 是指数和，a 是 value 的加权和。
  • 新块来了，把三组数按最大值 rescale 一下合并，继续往下走。
  • 数学上跟一次算完完全等价，只是换了个到达顺序。
  • 工程上再加三招藏延迟：双缓冲轮流接货、跨层预取、请求分组批量算。
  • 验证宽度 q（一轮验几个）不写死，从 {2,4,6,8} 里动态选。
  • 选择标准很实在：哪个 q 让"每提交一个 token 耗时"最低，就用哪个。
  • q 太小，搬运成本摊不薄；q 太大，废算力太多，实时反馈找平衡点。

3. 等货别闲着：小模型同卡打草稿，但大模型优先

  • 大模型等 KV 搬运时，GPU 上是有空闲算力的，这就是"气泡"。
  • SpecStream 让小模型（Draft）在同一张卡上，用气泡接着打草稿。
  • 但分寸很重要：小模型拿多了，会拖慢大模型的搬运和验证。
  • 论文实测了这个 trade-off。
  • 给小模型 34 个 TPC（计算单元分组）时，总吞吐最高。
  • 完全不限制小模型，反而比不搞并行还慢，得不偿失。
  • 所以调度器定了一条铁律：大模型优先，小模型只能捡漏。
  • 每次只推进一个 token，打完就问大模型：还让继续吗。

关键数据

  • 实现基于 SGLang 0.5.17。
  • 硬件是 2 张 A800 80GB，主机内存 240GB。
  • 模型有两组。
  • Qwen3-32B 配 0.6B 小模型。
  • InternLM2.5-20B 配 1.8B。
  • 打的是 TriForce（同类 offload 基线）。
  • 三数据集平均吞吐 1.41 倍、1.32 倍。
  • 对 SGLang 自带投机解码加 offload：1.44 倍 / 1.62 倍。
  • 看短输入（GSM8K）。
  • 比纯显存的 SGLang 投机解码快 16.9%、10.6%。
  • 快的原因：动态 q 让每轮多提交 16% / 28% 的 token。
  • 输出质量：跟 SGLang 投机解码比，最大差距 0.2 个百分点，可忽略。
  • 省卡效果：原来要 3 张卡（大模型 2 张，小模型 1 张），现在 2 张搞定。
  • 换算下来，每张卡的输出吞吐涨 55.4%。
  • 看高并发（32 路）：CPU 里最多压 45–50 GiB 的 KV。
  • 显存腾出来接新请求。
  • 同样并发下，纯显存方案已经开始排队了。
  • 代价也要说清楚：长上下文且显存够用时，不如全放显存的方案快。
  • PCIe 搬运 31.5 GB/s，HBM 是 1935 GB/s。
  • 两者差 60 倍，流式只能藏住一部分。
  • 结论：它是"显存不够时"的解法，不是"显存管够时"的更快解法。

跟你的研究方向的关联

  • 你正在评估 SGLang 的 P/D 解耦。
  • 这篇是"解耦"思想在投机解码维度的版本。
  • P/D 解耦把 prefill 和 decode 拆到不同卡上跑。
  • SpecStream 把"搬 KV"和"算注意力"在时间上拆开。
  • 又把大小模型在空间上合到同一张卡。
  • 它的动态 q 选择器值得借鉴：按"每提交 token 耗时"实时选宽度。
  • 你的 AI 自动调参系统里，这就是现成的调参目标函数。
  • "提交线"思想可以直接用在 P/D 解耦的 KV 交接上：只传已提交的。
  • 候选的不传，省下的就是跨节点的传输量。
  • 注意硬件差异：论文在 A800 + PCIe Gen4 上测的，搬运带宽是瓶颈。
  • 你的 H100 / MI350X 上带宽配比不同，藏得住多少要重测，别直接套数字。

术语表

  • 投机解码：小模型先猜几个 token，大模型一次验完，猜对的直接采用。
  • Target / Draft：拍板的大模型 / 打草稿的小模型。
  • KV 缓存：注意力算过的中间结果，像草稿纸，越长越占显存。
  • online softmax：分块做归一化，每块记三个数。
  • 合并时 rescale，结果等价。
  • 验证宽度 q：一轮验证里放几个候选 token，越大并行度越高、废算力也越多。
  • TPC：GPU 上的计算单元分组，论文用它限制小模型能用的算力份额。
  • TriForce：同类 KV offload 基线方法，论文主要拿它当靶子打。
  • 以存代算：显存放不下就把 KV 搬到 CPU 内存，用搬运换容量。
