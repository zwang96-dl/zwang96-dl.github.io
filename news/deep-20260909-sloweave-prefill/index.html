SLOWeave：给 chunked prefill 装上"自适应油门"

论文：Deadline-Aware Adaptive Prefill Chunking for Efficient Large Language Model Serving
作者：Siyu Song, Qi Bai, Jinbo Hao 等（2026-09-07，arXiv:2609.07883）
原文：http://arxiv.org/abs/2609.07883v1

一句话人话版

chunked prefill 就是把长输入切成小块喂模型。"块切多大"一直是个玄学参数。这篇论文给出了一个数学上最优的在线控制器。每次自动选"最大的、能在 decode 截止时间前跑完的块"。不用人工调参。

它解决什么问题

先说背景。现代推理服务都用 continuous batching。也就是连续批处理：请求随到随加进正在跑的 batch。不用等整批凑齐。但有个经典矛盾：

  • prefill（"读题"阶段）。处理长输入，一次算很久。会堵住正在 decode 的请求。也就是正在"答题"、逐字生成的请求。它们的 token 延迟会超标。
  • chunked prefill 是标准解法。把长 prefill 切成小块。每轮 iteration 只跑一块，给 decode 留出呼吸空间。

但块大小（chunk size）是个两难：

块太小块太大
保护 decode 延迟，但每次启动的固定开销（launch overhead）被反复支付，prefill 总效率低prefill 跑得快，但一轮 iteration 时间太长，decode 请求的"下个 token 截止时间"被违反

以前的做法是固定一个 chunk size。靠经验调参，不同负载下顾此失彼。

核心方法：SLOWeave

打个比方：你管着一条流水线。既要保证"老客户的订单按时出货"。这是 decode 的 TPOT 目标。又想"新订单的备料越快越好"。这是 prefill 进度。SLOWeave 就是那个每轮动态决定"这次备多少料"的调度员。

具体做法：

  1. 定 deadline。维护每个 decode 请求的"下个 token 截止时间"。取其中最早的那个。
  2. 用一个单调的 iteration 成本模型预测。"如果这轮塞进大小为 C 的 prefill 块，这一轮要跑多久？"
  3. 选最大的 C，让预测的本轮耗时仍在最早 deadline 之前。
  4. 这个搜索是对数时间的，开销可以忽略。

论文还给了理论保证。前提是"纯 decode 的一轮"本身可行，成本预测也准确。所有"保住 decode deadline"的决策里。SLOWeave 选 prefill 进度最大的那个。也就是说，它不是拍脑袋的 heuristic（启发式），而是有最优性证明的控制器。

关键特性：不需要按工作负载调参。chunk size 从超参数变成了在线决策。

原文关键图

图 1 人话解读。请求流进来，调度器看一眼当前 prefill/decode 状态。红色框里的 SLOWeave 控制器，算出本轮最多能塞多少 prefill。这个值记作 c*。GPU 跑一轮混合迭代，结果进持久状态。下面那条"代价分析器加遥测"回路是保险丝：实时对比"预测耗时 vs 实际耗时"。预测不准就自动收紧。注意整个系统只有"本轮塞多少 prefill"这一个旋钮被接管。模型、attention kernel、KV 布局一行不改。这就是它能直接塞进 vLLM/SGLang 的原因。

图 2 人话解读。这是整篇论文最直观的一张图。橙色块是 prefill，蓝色块是 decode。红色虚线是 decode 的"下个 token 截止线"。

  • 整块 prefill。一口气把长输入全算完，直接撞线，deadline miss（违约）。
  • 固定小块。每轮都留白，安全但浪费。那些虚线框就是白白空转的 GPU 时间。
  • SLOWeave。橙色块的宽度跟着 decode 负载"涨潮退潮"。每个 deadline 窗口都被 prefill 填得满满当当，一个违约也没有。

关键实验数据

  • 测试环境：可复现的事件驱动模拟器。加上 iteration 级别的 GPU 真实运行时。覆盖聊天、混合上下文、长上下文、突发流量四种负载。
  • TPOT 目标 25ms。混合请求 goodput（有效吞吐。满足 SLO 的请求吞吐）比最强固定分块基线 +39%。长上下文请求 +38%。
  • TPOT 目标收紧到 10ms。提升放大到 3.3× 和 2.4×。SLO 越严格，自适应的价值越大。
  • 结论：自适应 chunk sizing 值得加入 serving runtime。它是一个基础原语。论文给的是可直接集成的控制器实现。

图 5 人话解读。横轴是 TPOT 目标（10ms → 25ms → 50ms，越往左越严格）。纵轴是 goodput。红线 SLOWeave 全程在最上面。注意最左边 10ms 那一档。固定策略（灰/蓝线）几乎趴到 0。红线还坚挺在 35+。SLO 越严格，自适应的价值越大。这张图就是"为什么值得做"的最有力证据。

跟你研究方向的关联

  • 直接相关。你正在评估 SGLang 的 prefill/decode 解耦。英文叫 P/D disaggregation。SLOWeave 解决的是聚合部署的一个干扰问题。prefill 和 decode 会互相影响。这是理解"为什么要做 P/D 解耦"的另一面。读懂它，你对"解耦 vs 不解耦"的取舍会有量化直觉。
  • 工程落地。chunked prefill 调度器，都能塞进这个控制器。SGLang、vLLM 都适用。如果你以后做调度实验，这是现成的 baseline。
  • 方法论。把"调参问题"转化成"带 deadline 约束的在线优化问题"。这个思路可以迁移到 KV cache 管理、batch 组装等其他调度决策上。

术语表

  • chunked prefill。分块预填充。把长输入切成小块，每轮只处理一块。避免长 prefill 独占 GPU 太久。
  • TPOT（time per output token）。每输出一个 token 的平均延迟。衡量"生成流畅度"的核心 SLO 指标。
  • goodput。有效吞吐。只统计满足延迟目标的那部分请求吞吐，比 raw throughput 更诚实。
  • continuous batching。连续批处理。vLLM 带火的机制，请求可以随时加入正在执行的 batch。
  • launch overhead。kernel 启动开销。每次 GPU kernel 启动有固定成本，块切太小会被它吃掉效率。
