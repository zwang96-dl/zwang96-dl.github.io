VibeSys：AI agent 从零造了个 serving 引擎，MI300A 上跑赢调优 SGLang 2.33 倍

  • 原文：华盛顿大学 SYFI 实验室博客《VibeSys Builds a Qwen3.5-397B Engine on MI300A, 2.3× Tuned SGLang》（2026-10-08）

https://syfi.cs.washington.edu/blog/2026-10-08-qwen35-mi300a/

  • HN 帖：https://news.ycombinator.com/item?id=50030387
  • VibeSys 开源：https://github.com/uw-syfi/vibesys
  • 18点版收录。深读理由：你手里有 MI300X/MI350X，正在评估 SGLang。

一句话人话

一群 AI agent 当了 105 小时的"性能工程师"。 从零写出一个 serving 引擎，没用人写一行代码。 在 4 张 AMD MI300A 上跑 397B 大模型。 最终好吞吐是调优版 SGLang 的 2.33 倍。

目标是啥

  • 模型：Qwen3.5-397B-A17B。397B 参数、每次只激活 17B。

混合 MoE：60 层里 15 层全注意力、45 层是 Gated DeltaNet。 Gated DeltaNet 是一种线性注意力，状态固定大小、原地更新。

  • 硬件：4 张 AMD MI300A。每张是 CPU+GPU 一体封装。

128GB HBM3 显存和内存共用，权重、KV、系统全抢同一块内存。

  • 负载：确定性多轮聊天，从 1 并发 ramp 到 192 会话。

每轮重发完整对话历史。SLO：p95 TPOT≤250ms，p95 TTFT≤10s。 TPOT=每输出一个 token 的耗时，TTFT=首字耗时。

agent 是怎么干活的

  • VibeSys 是多 agent 系统， orchestration 这套来自 VibeServe 原型。
  • agent 拿到权重、HF 参考实现、benchmark 和硬件描述。
  • 只许用 PyTorch、Triton 和 AMD AITER 的单个内核。
  • 不许用 SGLang、vLLM、TensorRT-LLM 的 serving 代码。
  • 评审 agent 检查每条改动是否违规。
  • 调度 agent 提优化假设，实现 agent 写代码，评测 agent 跑分。
  • 每次结果都挂到 commit 上，调度 agent 能看到完整轨迹。
  • 假设被接受要过双重门：held-out 集上好吞吐提升+正确性检查。
  • 节点间有 ±10% 噪声，所以要求同节点前后脚跑两次对照。
  • 105 小时用了 392.8 小时 agent 工时，全是 Claude Code + Opus 5。

先把 SGLang 移植过去（基线怎么来的）

原生 SGLang v0.5.18 在这卡上根本跑不起来。 三个拦路虎：

  • 没 MoE 内核：SGLang 锁的 AITER 版本里，MXFP4 内核只支持 gfx950。

MI300A 是 gfx942，warmup 直接 abort。 Triton 通用版没有 512 专家的调优配置，只能跑出 1-3% 的 HBM 带宽。

  • 内存估算翻车：SGLang 按"加载权重后剩余内存"定 KV 池大小。

共享内存下，page cache 让四张卡看到的剩余内存不均。 启动就 OOM、负预算或卡死。

  • 启动太慢：权重加载约 60 分钟，AITER 现场编译 attention 内核约 105 秒。

SGLang 20 秒的健康检查直接把 server 杀了。

agent 的解法：手写 fused HIP MoE 内核（MXFP4 寄存器内反量化）。 固定 KV 池大小。换成预分片权重的有界读取（加载压到约 1 分钟）。 预编译 AITER 内核缓存。调优后好吞吐 961 tok/s（48 并发）。 调优大头：MTP 投机解码（TPOT 中位数 70.9→38.3ms）。 每个 decode 形状的 GEMM 调优表（38.1→22.9ms）。 agent 给 SGLang 加了约 3,500 行代码。

结果：12.8 → 2,242 tok/s

agent 自研引擎在 96 并发达到 2,242 tok/s。 是调优 SGLang 峰值的 2.33 倍。两边都用了 MTP。 调优 SGLang 峰值在 48 并发，96 并发时 p95 TTFT 飙到 15.5s。 自研引擎约 19,400 行代码，其中 520 行 HIP。

注意短板：agent 只优化了峰值好吞吐。 低并发下调优 SGLang 还是更快。 16 并发时 MTP 让后期轮次 p95 TTFT 涨了 11-15%。

加速从哪来的（四段轨迹）

1. 前缀缓存：12.8 → 55.6 tok/s（4.3 倍）

  • 最初的引擎每轮都重 prefill 完整对话。
  • 串行 prefill 饿死 decode。
  • DeltaNet 层只能从存下的 recurrent 状态快照恢复。
  • agent 建了个前缀缓存，同时存 attention KV 和 DeltaNet 快照。

2. 内核和图捕获：55.6 → 659 tok/s（11.9 倍，最大的一段）

  • 每个 decode 步起一堆小内核，GPU 在等 CPU。
  • agent 把 decode、prefill、混合步都抓成 HIP 图。
  • 每步只 launch 一次。
  • 手写 fused MXFP4 MoE 内核、分块 DeltaNet prefill、split-K decode attention。
  • overlap 调度：GPU 跑当前步时，CPU 规划下一步。

3. 通信和并发：659 → 1,055 tok/s

  • 模型切四张卡，每层两个集合通信，每步约 120 次。
  • 把原生 all-reduce 换成 one-shot 版，跟残差加和 RMSNorm 熔合。
  • decode 图开到 batch 128，能跑 96 并发，超过 SGLang 的 961。

4. prefill、缓存和投机：1,055 → 2,242 tok/s

  • 快照淘汰 +27%：DeltaNet 快照每个约 47MB。

缓存是棵对话树，agent 在每个分支点都存了快照。 对话走过分支点后，旧快照就再也用不上了。 这些僵尸快照挤占内存，把活跃对话挤出去重算。 改成先淘汰分支点内侧的旧快照，prefill token 降约 40%。

  • MTP 投机解码 +16-20%：主模型一次验证草稿头猜的 token。

DeltaNet 层验证要跑递推和因果卷积，拒绝了还要回滚状态。 第一版图捕获版 replay 直接非法内存访问。 查出来是图引用了 Python 闭包的 tensor，capture 后被释放了。 修好后 2 个草稿 token，每步验证吐 2.68 个 token，接受率 84%。

  • 便宜 prefill 和集合通信：prefill 按 1536 token 分块 +9.3%。

prefill 序列无 padding 打包 +5.6%。 MoE 内核 32 行 tile +4.8%。 all-reduce 改成 reduce-scatter→RMSNorm→all-gather，+8-9%。

啥没用

  • BF16 热门专家缓存：覆盖 80-86% 的专家分配。

但比 MXFP4 内核慢 5-7 倍，还占 20GB。扔了。

  • 手写 dense GEMM、persistent MoE 内核、并行路由准备：持平或更慢。全扔。

图注：横轴是优化轮次，蓝色是每轮最好成绩，灰点是单次实测（含退化和被拒的候选），虚线是调优版 SGLang 的 961 tok/s 基线。四段加速：前缀缓存 4.3 倍、内核+图捕获 11.9 倍、通信并发上一截、prefill+缓存+投机冲到 2,242。

跟你研究方向的关联

  • AMD 卡实战手册：gfx942（MI300A）和 gfx950（MI350 级）的 AITER 内核支持差异，MI300X/MI350X 上跑 SGLang 会踩同样的坑。MoE 内核 gfx950-only 这个细节直接有用。
  • SGLang 评估的对照组：这篇给了"调优版 SGLang 在 AMD 卡上"的完整账本——MTP、GEMM 调优表、overlap 关掉反而好。你的 P/D 解耦评估可以抄它的测量方法论（同节点前后脚对照、±10% 噪声门）。
  • P/D 解耦的思路库：混合 prefill/decode 步图捕获、prefill 分块 1536、overlap 调度，都是 prefill-decode 资源调度的具体招式。
  • autotuner 的启示：agent 搜索本质上就是自动调参——假设-实现-评测闭环、结果挂 commit。它的"接受门"设计（held-out+双重对照）可以直接借鉴。
  • 投机解码：MTP 在这套系统里是 +16-20% 的稳定收益，接受率 84%。跟 Temperature2 那篇"接受率<50% 就亏"正好互补。

术语表

  • 好吞吐（goodput）：满足延迟 SLO 的响应吞吐，不是裸吞吐。
  • VibeSys：UW SYFI 实验室的多 agent 系统设计框架，从 VibeServe 原型来。
  • MI300A：AMD 的 CPU+GPU 一体封装芯片，内存统一编址。
  • gfx942/gfx950：AMD GPU 架构代号，942 是 MI300 系列，950 是 MI350 级。
  • MTP（多 token 预测头）：模型一次多猜几个 token 的草稿头，投机解码的一种。
  • Gated DeltaNet：线性注意力变体，状态固定大小、原地更新，不用存长 KV。
  • HIP 图：AMD 版的 CUDA 图，把一串内核 launch 录成一张图一次发射。
  • AITER：AMD 的 AI 算子库，类似 NVIDIA 的 CUTLASS 生态位。
  • MXFP4：4-bit 微缩放浮点量化格式，MoE 权重用的。
  • split-K：把一个 GEMM 的 K 维度拆成多份并行算，再归约。
  • 前缀缓存：历史请求的 KV 不扔，新请求复用，草稿纸留着下轮用。
  • TTFT/TPOT：首字耗时 / 每 token 耗时。

注意

  • 数字来自单实验室博客，非同行评审论文。VibeServe 有 arXiv 论文，引擎本身的细节以博客为准。
  • 对比基线是"被 VibeSys 移植调优过的 SGLang"，不是原生 SGLang——原生在这卡上跑不起来。
  • 优化目标只看峰值好吞吐，低并发延迟没优化，16 并发下反而退化。
  • 392.8 小时 agent 工时、105 小时 wall clock，成本不低。
