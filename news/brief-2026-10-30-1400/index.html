多模态大模型推理服务简报 · 2026-10-30（14点版）

14点版来了，这轮最硬的是一组实测数字。 OpenRouter 重写了供应商路由算法。 2400 万真实请求跑下来，首 token p50 快了 16.9%。 429 限流错误少了 46%，成本只涨 6%。 另一篇 LMSYS 博客跟你的 AMD 线直接相关。 他们在 MI355X 上用 SGLang 跑 agentic RL。 KV 缓存的账算得很细，值得你看一眼。

头条

OpenRouter 重写路由，不再唯价格论 OpenRouter 是个模型 API 聚合平台。 以前选供应商只看谁便宜。 现在算的是真实路由成本。 价格、排队等待、重试期望全算进去。 还保持缓存粘性，热缓存的请求不乱跳。 2400 万请求实测：首 token p50 快 16.9%。 吞吐涨 16.3%，429 错误少 46%。 代价是成本涨 6%，换来稳定性大涨。 你在搭 serving 的路由层，这套算法值得抄。 来源：https://openrouter.ai/blog/announcements/how-we-rebuilt-provider-routing/

框架更新

vLLM #57770：DSpark 打草稿又省了一笔 DSpark 是 DeepSeek 自家的投机解码方案。 投机解码是先让小模块打草稿、大模型改。 12点版报过它消掉了重复计算。 这轮继续抠：贪心打草稿的 argmax 换了。 以前全词表 torch.argmax 一把梭。 现在换成两段式 Triton 归约。 每个 decode 步要连选 5 次草稿。 省的算力直接翻 5 倍。 来源：https://github.com/vllm-project/vllm/pull/57770

vLLM #63761：Qwen3.5 注意力修了个溢出 Qwen3.5 的 prefill 路径上有个 int32 溢出。 Triton 核里 token 索引乘行步长，爆了上限。 长上下文跑 Qwen3.5 的人，这个修复对你有用。 来源：https://github.com/vllm-project/vllm/pull/63761

SGLang #47445：多模态 IPC 的精度保住了 IPC 是进程间通信，SGLang 内部传数据用的。 msgpack 是一种序列化格式，比 pickle 快。 切到 msgpack 后，多模态 payload 会丢精度。 dtype 来回转一圈就对不上了。 hidden states 和权重更新也一样。 现在修了，来回转不再丢精度。 你在做多模态推理，这个修复跟你直接相关。 来源：https://github.com/sgl-project/sglang/pull/47445

SGLang #47333：推测解码崩了会自己降级 ragged-verify 是推测解码的一种验证排布。 层级超过捕获网格时，以前直接抛错。 整个 scheduler 被炸掉，服务停摆。 现在自动回退到 eager 模式。 说白了：高速档挂了，自动切回慢速档保命。 来源：https://github.com/sgl-project/sglang/pull/47333

SGLang #46454：混元图 3 加了前缀缓存 HunyuanImage-3 是腾讯的图像生成模型。 这笔给它加了 prefix K/V cache。 KV cache 是解码时的草稿纸，存了算过的键值。 前缀缓存就是草稿纸复用，不用每次重算。 还顺手加了可选的 FA3 注意力和 think-prompt。 跑图像生成的 serving，这笔是纯加速。 来源：https://github.com/sgl-project/sglang/pull/46454

SGLang #46963：每个请求的账单更细了 rust-server 是 SGLang 的新前端。 以前 native /generate 返回里没有单请求统计。 现在 meta_info 里补上了 scheduler 的统计。 调优排队和延迟的人，看板又多了一块表。 来源：https://github.com/sgl-project/sglang/pull/46963

FlashInfer 四笔：量化 kernel 继续抠

#8031：Kimi-K3 的 fused MoE router 提速了。

在 GB300 上，单 token 路由一次 launch 搞定。 896 个专家里选 16 个。

#7976：NVFP4 量化延迟又降了一截。

NVFP4 是英伟达的 4 位浮点格式。

#5982：MXFP8 量化跟 GEMM 初始化重叠跑。

MXFP8 是另一种 8 位浮点量化。

#8029：SM120 的 MQA-logits，更多形状走调优 kernel。

MQA-logits 是注意力输出层的分块计算。 四笔全是 kernel 层的牙膏，持续挤。 来源：https://github.com/flashinfer-ai/flashinfer/pull/8031 来源：https://github.com/flashinfer-ai/flashinfer/pull/7976 来源：https://github.com/flashinfer-ai/flashinfer/pull/5982 来源：https://github.com/flashinfer-ai/flashinfer/pull/8029

TRT-LLM #20702：解耦 worker 的取消不卡了 PD 解耦里，取消的请求以前会卡住。 worker 在等 peer 就绪或 KV 接收，取消指令排后面。 现在空闲时直接推进取消，不用等下一批。 内存照样保留，等传输方确认安全再退。 跟你评估的 PD 解耦是同一条线。 来源：https://github.com/NVIDIA/TensorRT-LLM/pull/20702

访谈与深度

LMSYS 博客：MI355X 上用 SGLang 跑 agentic RL 这篇是 10/22 的，之前几期漏了，补上。 跟你的 AMD 硬件线直接相关。 模型是 Qwen3-30B-A3B，卡是 MI355X。 跑的是全异步 agentic RL。 SWE-bench 子集测下来。 pass@1 从 7.3% 干到 27.5%。 rollout 吞吐从 860 干到 3480 条轨迹每小时。 KV 缓存的账算得很实在。 每 token 约 96KB，64K 轨迹要吃 6.3GB KV。 有次没设上限，几条 100K+ 的生成把缓存撑爆。 99 个请求排队超时，一个都没跑出来。 教训：engine 侧必须设 64K 上下文上限。 长尾也是坑：84% 的轨迹跑满 turn 上限。 decode 时 batch 接近 1，GPU 大片空转。 你在 MI350X 上评估 SGLang，这篇的账本能直接抄。 来源：https://www.lmsys.org/blog/2026-10-22-miles-mi355x-agentic-rl
