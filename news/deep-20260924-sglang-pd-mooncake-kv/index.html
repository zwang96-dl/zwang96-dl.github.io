SGLang P/D 解耦的 mooncake KV 传输竞态：静默 corrupt 根因与修复

原文：AMD infera 项目补丁文档（GitHub）
https://github.com/amd-agi/infera/blob/HEAD/deploy/docker/patches/sglang_disagg/README.md
相关 issue：sglang#25583（症状相同，被 bot 自动关闭，无人跟进）

一句话

SGLang 开 P/D 解耦、用 mooncake 传 KV、长 prompt 切块、传输计算重叠——四个条件凑齐，decode 拿到的 KV 是半成品，输出悄悄变错，不报错也不崩。

人话解读

P/D 解耦把"读题"和"答题"分给两拨 GPU。读题那拨算完 KV，得搬给答题那拨，mooncake 就是搬运工。长 prompt 会被切成几块逐段读，读完一块搬一块。为了快，搬运和计算重叠进行：上一块在搬，下一块接着算。问题就出在这里：搬运工没等算完就动手，把"写了一半"的 KV 页传了过去。答题那拨拿到半成品，输出就错了。最阴的是它不报错、不崩溃，只是答案悄悄变坏——benchmark 跑出来的数字是脏的，你还蒙在鼓里。

触发条件（四条全中才中招）

  1. SGLang 开了 P/D 解耦（--disaggregation-mode prefill|decode）。
  2. KV 传输后端是 mooncake（mori / NIXL 不受影响）。
  3. prompt 长到触发 chunked prefill（超过一个 chunk）。
  4. 开了 overlap scheduling（传输和计算重叠）。

症状：怎么认出是它

  • 大海捞针测试：想捞 2183762，只捞出 2183，后面跟一串 think 标签重复。
  • corrupt 的边界正好落在 chunk 边界上，最后一个 chunk 里的 needle 永远是对的。
  • 同样模型、同样配置，单机聚合模式 9/9 全过，只有 P/D 模式翻车。
  • 不是崩溃、不是明显错答案，是"部分正确"——最难查的那种。

根因

prefill.py 里其实记了一个 CUDA event 做 barrier，注释写得明明白白：让传输线程等写完再读。但只有 mori 后端读了这个 event，mooncake 的 conn.py 里 wait_event 和 synchronize 一个都没实现，barrier 从没生效过。更糟的是，overlap 调度下传非尾块的那个调用，连 event 都没记。尾块为啥没事？它走采样路径，自带 copy_done.synchronize()，天然有 barrier。所以症状永远是"前面的 chunk 坏、最后一个 chunk 好"。

修复（三处，照抄 mori 的做法）

  1. disaggregation/common/utils.py：TransferKVChunk 加 wait_event 字段，让 barrier 跟着 work item 走。
  2. disaggregation/mooncake/conn.py：send() 接住并透传这个 event；transfer_worker 在读显存之前先 synchronize()。
  3. disaggregation/prefill.py：overlap 路径下传非尾块时，在 forward_stream 上补记一个 event。

三处必须一次全上，少一处照样 corrupt，半吊子补丁等于没打。代价是 transfer worker 线程会被 block，拿一点传输重叠换正确性，上游合入时得量化这个开销。

验证数据

环境：2×8×MI325X（gfx942），ROCm 7.2.0，sglang v0.5.16，GLM-5.2-FP8 一 prefill 一 decode，mooncake RDMA，overlap 开，chunk 大小 131072。

测试修复前修复后
大海捞针：3 种长度 × depth 10/50/905/99/9
大海捞针：29k depth sweep（9 个点）4/99/9
全量正确性套件（needle + humaneval-long + 长上下文 delta）needle 7/9全部通过

修完之后，chunk size 变回纯性能旋钮，不用再靠大 chunk + 高显存占比的 workaround 续命，prefill 的 overlap 调度也不用关了。

附带：/v1/responses 在 PD 下直接 400

同一个补丁集里的另一个修复。ResponsesRequest 模型缺 bootstrap_host / bootstrap_port / bootstrap_room 三个字段，pydantic 默认 extra="ignore"，代理传过来的标注被静默吞掉。scheduler 看到 bootstrap_room=None，直接 400 拒掉，日志里还看不出为啥。修完之后，Codex 这类默认走 Responses API 的 agent 负载才能进 P/D 部署。注意：harmony 内串工具循环的第二轮没修，会 fail fast；非 harmony 模型走不到那，不受影响。

跟研究方向的关联

你正在评估 SGLang 的 P/D 解耦，手里是 MI350X/MI300X。这份补丁的验证环境是 MI325X + ROCm 7.2，跟你的栈是同门，一线经验直接可用。做 PD 评估时，长 prompt 的正确性回归必须覆盖"mooncake + overlap + 切块"这个组合，否则静默 corrupt 会污染 benchmark 结论——数字看着正常，答案悄悄是错的。infera 本身就是 AMD 的 PD 部署方案，补丁脚本幂等、可直接拿去用。
