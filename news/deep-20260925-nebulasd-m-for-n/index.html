NebulaSD：投机解码的草稿和验证，各自组"人才市场"

原文：NebulaSD: Many-for-Many Speculative Decoding（arXiv:2609.29364，2026-09-24，香港大学 NICE Lab）
一句话版本：投机解码别再"固定搭档"。
草稿和验证拆成两个独立池子，谁有空谁上，容量全局共享。

人话解读

投机解码你很熟：小模型先打草稿，大模型批量改作业。

一轮能收好几个 token，decode 快不少。

以前的分布式做法是"固定搭档制"。

一个草稿 worker 绑一个验证 worker，请求也跟着绑死。

问题是这俩阶段脾气完全不一样。

草稿喜欢大 batch，batch 到 512 延迟几乎不涨。

验证喜欢小 batch，batch 一大延迟直接起飞。

绑在一起的结果：快的那个干等慢的。

就像实习生写完了，专家还在改上一份，实习生只能刷手机。

更惨的是，别的搭档可能正好反过来：专家闲着，实习生堵死。

但容量是锁死的，借都借不过来。

NebulaSD 的答案：拆了，改成"人才市场"。

M 个草稿 worker 是一个池，N 个验证 worker 是另一个池。

请求不绑任何人，每个 worker 干完一轮，就去池子里挑下一批请求。

哪个池子忙就多派人手，容量在全局流动。

跨 worker 换请求有个代价：KV cache（草稿纸）得跟着搬。

NebulaSD 用异步预取把搬运藏进计算里，大部分不在关键路径上。

对你意味着什么：这是"解耦"思想的又一次延伸。

你在 SGLang 上评估 P/D 解耦。 拆的是 prefill 和 decode。

这篇拆的是投机解码的草稿和验证，调度哲学一模一样。

核心方法

整套设计三招，招招冲着"别让容量闲着"去。

第一招：两个独立资源池。

M 个 draft worker 跑小模型。 N 个 target worker 跑大模型。

两边各自调度，互不绑定。

类比：原来是固定班组，现在是两个劳务市场。

第二招：worker 触发的 batch 重构。

worker 干完手头活，主动发信号给中央调度器。

调度器查三张表：谁有空、请求状态在哪、搬过去划不划算。

然后从共享请求池里现挑一批，拼成这个 worker 的下一个 batch。

跨阶段也没有 batch 亲缘关系：上一轮一起跑的，下一轮各奔东西。

第三招：异步 KV 状态准备。

请求换了 worker，KV cache（草稿纸）得提前送到。

做法是三件套：提前预取、增量写回、双缓冲。

每个 worker 配两块缓冲。 一块叫 Forward Bank，一块叫 Prefetch Bank。

算着这一批的同时，下一批的 KV 已经在路上了。

预测靠的是 profiling 表。 查这个 batch 多大、context 多长、大概要跑多久。

调度器按预测时间提前布局，运行时只看"真就绪了没"。

关键数据

实验配置先摆出来。

4 张 RTX 4090，2 个草稿 worker 加 2 个验证 worker。

草稿模型 Qwen3-1.7B，验证模型 Qwen3-8B。

proposal depth 4，就是一次打 4 个草稿 token。

512 个请求，草稿 batch 上限 128，验证 batch 上限 32。

核心指标：request-round 处理速率，一秒能走完几轮草稿加验证。

同机混跑：1109 轮每秒。

原生分布式（固定搭档）：1273 轮每秒。

NebulaSD：1915 轮每秒。

对固定搭档快 50.4%，对同机快 72.6%。

划重点：赢的不是单次算得快，是"气泡"被填上了。

看计算率：草稿 worker 从 73.8% 涨到 95.3%。

验证 worker 从 24.1% 涨到 86.3%。

验证端原来四分之三的时间都在闲着，现在被喂饱了。

batch 之间的空隙：草稿端 115ms 压到 4.4ms。

验证端 24ms 压到 4.5ms。

SM 活跃度从 30.1% 涨到 47.3%。

代价也要说清楚：单个请求分到的算力份额变薄了。

从 97.9% 降到 44.0%。

因为系统同时在伺候更多请求，每个人分到的少了。

论文说这是小规模部署的 trade-off，池子做大能缓解。

仿真验证了这句话：规模上去后，86% 的 SM 活跃度。

同时每个请求保住 92.8% 到 99.6% 的算力份额。

KV 增长敏感度：生成长度 128 和 256 时，收益还在。

1813 和 1626 轮每秒，照样碾压基线。

长度拉到 512，KV 搬运开始压不住，收益收窄。

跟你研究方向的关联

你在 SGLang 上评估 P/D 解耦，核心问题是"拆开之后怎么配最划算"。

NebulaSD 是同一道题的另一个版本。

P/D 解耦拆的是 prefill 和 decode，这篇拆的是草稿和验证。

调度哲学完全相通：阶段特性不同，就别硬绑在一起。

SARA 那篇笔记解决的是"prefill 和 decode 各配几张卡"。

这篇解决的是"draft 和 target 各配几个 worker"。

两边的配比公式可以互相借鉴。

这种"worker 闲了举手要活"的调度，值得你的自动调参系统抄。

它不是中央统一排班，是 worker 闲了自己举手要活。

这种事件驱动调度在负载抖动大时更稳。

KV 异步预取那套，也可以搬到 P/D 解耦里。

mooncake 传 KV 时，这个思路能藏掉一部分传输延迟。

一个提醒：这篇的收益依赖"请求足够多"。

并发低的时候池子吃不饱，动态调度的优势出不来。

你的评估里记得测低并发档，别只看打满的情况。

术语表

  • speculative decoding：小模型先打草稿，大模型批量验证。

一轮能多收几个 token。

  • draft worker：跑草稿小模型的 worker。

batch 大小对它影响不大。

  • target worker：跑验证大模型的 worker。

batch 一大它就变慢。

  • request round：一轮完整的"打草稿加验证"，论文的核心计量单位。
  • KV cache（草稿纸）：解码留下的键值缓存。

请求换 worker 时必须跟着搬。

  • batch reconstruction：每次从共享池现挑请求组 batch。

不跟任何 worker 固定绑定。

  • advance prefetching：提前把下批 KV 搬上 GPU。

从 host 内存预取。

  • double buffering：两块缓冲轮换，一块算着，一块装着下一批。
  • SM activity：流式多处理器活跃度，GPU 利用率的代理指标。
  • proposal depth：一次打几个草稿 token，这里是 4。
