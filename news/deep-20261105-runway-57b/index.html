Runway Characters：57B 视频扩散模型，4 块 H100 跑出 24fps 实时对话

  • 原文：https://arxiv.org/abs/2611.05642
  • 标题：Runway Characters: Serving a 57B Video Diffusion Transformer for Real-Time Conversation
  • 作者：Runway Research and Engineering Team（30+ 人）
  • 提交：2026-11-03，arXiv:2611.05642v1，cs.DC，18 页
  • 深读：19点版（2026-11-04）

人话解读

一句话：Runway 把 57B 参数的视频扩散大模型做成了实时视频通话。

场景是"视频对话角色"：虚拟人听你说话、边说边动，24fps 实时出画面。 每 166.7ms 必须生成 4 帧，一个人独占一次会话。 模型是自回归视频扩散 transformer，每步做 4 次去噪。 部署在 4 块 H100 上，输出 704×1088。

难在哪：batch size 只能是 1，没法靠堆 batch 摊成本。 每步要做 240 次 attention 调用，每次读 5788 个槽位的 KV cache。 只有 757 个 token 是新的，剩下全是重复读。 原代码里 29% 的时间在重复做整 cache 的维护活。

他们把 240.9ms 一步压到 159.3ms（1.51 倍），稳态 24.5fps。 加上融合 kernel 压到 147.4ms（1.63 倍），达到 FP8 峰值的 43%。 生产跑了七周，99.5% 的会话达标。

核心方法

1. 读时做的活，挪到写时做

这是全文的主线：原来每次读 cache 都要做的事，改成写 cache 时做一次。

  • 环形 cache（ring cache）：所有层共用一块大内存，按层切视图。

新帧用 index_copy_ 写进循环槽位。 写位置是个 device 上的 tensor，CUDA graph 重放时直接抓指针。 类比：黑板写满了不擦整块，循环着写格子。

  • RoPE 写时做：RoPE 是旋转位置编码，给 token 标位置的。

原来每次读 cache 都给全部 key 重算一遍 RoPE。 现在新 token 进 cache 前算一次，读的时候直接用。 每块前向省约 0.5GB 显存流量。

  • 位置重置的 delta 旋转：位置编号是循环的，每 42 步整体平移。

重置时只转一次 key，不用每次全量重算。 代价是每 42 步有一步慢（263ms），播放缓冲吃得掉。

  • FP8 写时量化：K 和 V 存成 float8_e4m3，只量化新帧。

原来每次调用都重算整 cache 的量化 scale。 scale 每会话校准一次：取前 6 步 bf16 cache 的最大值乘 1.5。 cache 维护从 69.7ms 压到 6ms。

2. 融合 kernel：把通信藏进计算

  • fused pre-attention：拆分、reshape、RMSNorm、RoPE、K/V 量化、写 ring。

用 CuTe DSL 写成 3 个 kernel，一气呵成。

  • GEMM 里直接做 all-reduce：all-reduce 是多卡求和同步。

下投影 GEMM 后本来要等一次 NCCL all-reduce。 他们把归约做进 GEMM kernel 里：tile 算完直接写进对称内存。 计数器到齐后，交换机里用 multimem.ld_reduce 原地求和。 后面的 tile 还在算，前面的已经在归约，通信基本不占关键路径。 改自 ParallelKittens/ThunderKittens 的融合 kernel。

  • 试过只换 NCCL 为 NVLink SHARP，只省 0.4ms，不划算，放弃。

3. 解码器独占一块卡

latent 转视频帧的解码要 114ms。 放去噪卡上跑，每步都拖后腿。 单独给 GPU 0，transformer 跑在 GPU 1–3（TP-3）。

4. 三段流水线重叠

稳态三步在飞：GPU 1–3 去噪 latent i。 同时 GPU 0 解码 latent i−1。 pacer 播放 latent i−2。 去噪、解码、播放全重叠，每步只剩 1.6ms 串行。

5. 固定排期的常数折叠

4 次去噪×60 个 block 的 AdaLN 调制参数，一次算完缓存。 AdaLN 是自适应层归一化，控制去噪强度的。 11.8ms 压到 0.8ms。

关键数据

  • 单 AR 步扩散耗时：240.9 → 159.3 → 147.4ms（基线/生产/融合 kernel）。
  • 步周期 p50：242.8 → 161.0 → 149.1ms。
  • 步周期 p90：245.2 → 163.4 → 151.7ms。
  • 持续帧率：16.4 → 24.5 → 26.4fps。
  • 单扩散卡算力：517 → 781 → 844 TFLOP/s。
  • 占 FP8 峰值：26.1% → 39.5% → 42.7%。
  • 生产 7 周（8/16–10/4）：播 1 秒以上的会话里，0.55% 平均 ≤23.5fps。
  • 帧准时率：99.52%/99.84%/99.98% 落在 1/10/100ms 槽内。
  • 单轮对话中位 2.13s（p10–p90 是 1.45–3.00s）。
  • 其中语音 agent 占 1.42s，pipeline 只占 0.49s。
  • 口型同步无退化：LSE-D 差值 ≤0.03，FP8 cache 没伤质量。
  • 对照：两个开源实时视频系统同条件下跑不到实时，或多 1 秒延迟，分辨率还只有 1/3 到一半。

数字全是作者自报，无第三方复现。

跟研究方向的关联

  • 多模态 inference serving 的生产级参考答案：这是少见的把视频扩散模型做到产品级实时的完整复盘。
  • KV cache 优化思路可抄："读时做→写时做" 是通用招式。

RoPE 和 FP8 量化一次做完，读的时候零开销。 你的 PD 评估里 prefill 侧的 KV 写入路径可以借鉴。

  • FP8 KV cache 无损证据：口型同步指标没降，说明 FP8 KV 在生产级质量门面前站得住。

跟你关心的 KV 压缩精度门直接相关。

  • 通信藏进计算：TP 的 all-reduce 融进 GEMM、交换机内归约。

PD 解耦里 KV 搬运的"通信计算重叠"账本可以参考这套打法。

  • batch-1 实时 SLO 的方法论：CUDA graph、固定排期常数折叠、device 侧写指针。

这些在 PD 的 decode 侧同样适用。

  • 质量门做法：SyncNet 口型指标 + 生产 7 周 telemetry 双保险。

评估时"先定质量门再谈加速"的流程值得抄。

术语表

  • AR step（自回归步）：每 166.7ms 生成 4 帧视频的一步。
  • 去噪（denoising）：扩散模型把噪声图修成清晰帧，一步做 4 遍。
  • pacer（节拍器）：按 24fps 准时推帧播出的组件。
  • RoPE（旋转位置编码）：给 token 标位置的编码方法。
  • TP-3（张量并行 3 卡）：模型权重切 3 份，每卡算一部分。
  • all-reduce：多卡把各自算的结果求和同步。
  • CUDA graph：把一串 GPU 操作录成一张图，一键重放。
  • FP8：8 位浮点，省显存省算力。
  • latent（隐变量）：压缩过的帧表示，解码器再展开成视频。
  • LSE-D/LSE-C：SyncNet 口型同步指标，越低越好/越高越好。
  • CuTe DSL：NVIDIA 写 GPU kernel 的模板语言。
  • NVLS：NVLink 交换机，支持在交换机里做归约。
