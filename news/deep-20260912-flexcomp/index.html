FlexComp：一个模型通吃所有压缩比

原文：FlexComp: One Model for Every Ratio in Context Compression
作者：Kaiyan Zhao、Zhongtao Miao、Akiko Aizawa、Yoshimasa Tsuruoka（东京大学 / 国立情报学研究所）
链接：https://arxiv.org/abs/2609.11192（arXiv:2609.11192，2026-09-11 发布）

一句话人话版

软上下文压缩（把长文本压成几个记忆 token）以前有个死规矩：训的时候定死压缩比，想换比例就得重训一个模型。

FlexComp 把这条规矩废了：训一次，推理时想压 15 倍还是 510 倍都行，还能按输入难度自动选松紧。

划重点：长上下文 serving 的显存救星，部署一个模型顶过去一大家子。

核心方法

第一招：Matryoshka（套娃式训练，高低压缩比兼顾）

  • 训练时不固定记忆 token 数 K，每次随机从 {1, 10, 34} 里抽一个。
  • 上下文切成 510 token 的块，K=1 就是 510 倍，K=34 就是 15 倍。
  • 一个模型见过所有压缩比，部署时任意档位直接切，不用重训。
  • 实测：一个套娃模型打平三个单独训练的专家，最差只掉 1.3 个 F1 点。
  • 四种设置里套娃模型反超专家，OOD（域外数据）上 9 组里 7 组更好。
  • 有个坑：套娃只能加在 SFT（监督微调阶段），pretrain 也加反而掉 2.3 个点。
  • 道理很简单：先学会"打包"这个基本功，再学"松紧自如"。

第二招：级联路由（先激进压缩，不行再重压）

  • 推理时先用最激进的 K=1 压，看解码器的自信度够不够。
  • 不够自信就升级到 K=10、K=34 重压，直到答案靠谱。
  • 自信度用"长度归一化的答案对数概率"，跟答对率相关性 0.56–0.58。
  • 说白了：先派实习生做，做不好再请专家，专家只接难活。
  • 代价是可能多压几次，适合文档压一次、反复被问的场景。

第三招：K 预测器（提前猜好用多少记忆 token）

  • 压缩前先过一遍编码器，用个两层小 MLP 猜这段文本要 K=1/10/34。
  • 只看上下文不看问题，离线算一次就能缓存，查询时直接用。
  • 整个头只有 210 万参数，是编码器的 0.17%，基本白送。
  • 单遍压缩-解码搞定，没有级联的重压开销，延迟敏感的 serving 就用它。
  • 训练标签不用人工标：模型自己在各档位跑一遍，取"刚好够用"的最小 K。

一个反直觉的发现

  • 压缩比和精度的关系在单个样本上不是单调的。
  • 有些题 1 个记忆 token 答对了，满预算反而答错。
  • 原因：多出来的细节把解码器带偏了。
  • 所以"按输入选预算"不是锦上添花，是真有必要。

关键数据

一个模型 vs 三个专家（MRQA 问答基准，F1 打分 0–100）

  • 三个压缩方法都试了：ICAE、500xCompressor、SAC。
  • 换掉 3 个专家只花最多 1.3 个 F1 点，大部分情况打平。
  • 500xCompressor 在 510 倍档位，套娃模型反超专家 3.72 个 ID 点。

级联路由：精度几乎不掉，压缩比拉满

  • 保留最温和档位 98% 以上的精度。
  • 平均压缩比最高冲到 266 倍（SAC 的最激进档）。
  • ICAE 最激进档：平均每输入只用 19.8 个 token，压缩 235 倍。
  • 精度只比最温和档掉 0.6 个点，域外数据甚至还略涨。

K 预测器：单遍 158–236 倍，精度掉不到 1 个点

  • ICAE 157.99 倍、500x 236.08 倍、SAC 158.96 倍。
  • ID 和 OOD 精度最多掉 0.7 个 F1 点。
  • 对照组"随机分配预算"掉 5 个点，说明赢在"分对了人"。

serving 实测：KV cache 砍半，吞吐 +47%

  • 条件：SAC 模型、batch 96、上下文 8192、生成 512。
  • 上下文 KV cache 从 1638MB 降到 811MB，砍掉 50.5%。
  • decode 吞吐从 3920 涨到 5764 token/s，提升 47%。
  • 上下文越长收益越大，因为压缩掉的正是大头。

跟你的研究方向怎么挂钩

直接对上你的痛点：长上下文 KV cache 开销

  • 你现在评估 SGLang 的 P/D 解耦。痛点之一是长上下文的 KV cache（解码时的草稿纸）吃显存。
  • FlexComp 是从另一头下手：上下文还没进解码器就先压成几个 token。
  • 8192 上下文直接砍掉一半 KV cache，这对 MI350 上跑大 batch 是实打实的容量释放。

"一个模型任意压缩比"对部署的意义

  • 以前 serving 端想兼顾质量和成本，得训 N 个模型、部署 N 个 endpoint。
  • 现在 1 个模型 + 推理时选档，阈值一调就是一条新的压缩-精度曲线。
  • 跟你的场景特别配：简单查询走 510 倍激进档，难查询自动升级。

跟 prefix caching / KV cache 压缩的配合

  • 这三招不打架，是叠 buff 的关系。
  • prefix caching（相同前缀的 KV 复用）管的是"重复计算"，FlexComp 管的是"上下文本身太大"。
  • 流程可以串起来：先 FlexComp 压上下文，再进 P/D 解耦的 serving 栈。
  • 注意顺序：压缩后的 token 序列变了，prefix cache 的命中逻辑要按压缩后的前缀算。
  • 另外 K 预测器是 query-agnostic 的，跟 prefix caching 的"离线预处理"思路天然合拍。

可以动手验证的两件事

  • 套娃训练只改 SFT 阶段的数据采样，方法无关，理论上能套到你用的任何压缩器上。
  • 级联路由的阈值是在验证集上扫出来的，不用重训就能调出 4 档工作点。

术语表

  • 软上下文压缩：把长文本压成几个记忆 token
  • Matryoshka：套娃式训练，高低压缩比兼顾
  • memory token：压缩后的记忆 token，冻结 LLM 直接消费
  • 压缩比：原文长度除以记忆 token 数，快递打包的松紧度
  • 级联路由：先激进压缩，不行再重压
  • K 预测器：提前猜好用多少记忆 token
  • MRQA：多数据集问答基准，6 个域内 + 6 个域外任务
  • F1：答对率打分，0–100 分制
  • OOD：域外数据，训练时没见过的任务分布
  • query-agnostic：只看上下文不看问题，可离线预处理
